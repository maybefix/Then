# Then の安全な変更の経路

機能の分離（挙動を変えずに場所だけ移す）と、不具合・既知の制限の修正（挙動を意図して変える）を、同じ土台の上で回す。土台は次の3つ。

- **戻せること**: 始める前にブランチとチェックポイント（コミットとタグ）を作る。
- **前後を比べられること**: 変更の前に package.json のテストを全部動かして記録し、変更の後と表で比べる。
- **本物で確かめること**: ふだんの Then と別の識別子で build した QA 用アプリを、一時ライブラリで動かして確かめる。

人が確かめるのは2回だけにする。**確認1** は調査と案をまとめた手順書を見てもらうとき、**確認2** は実施と確認が終わって push する前。そのあいだは止まらずに進め、途中の経過は短く伝える。

## 変えない前提

- 返事・経過・質問は日本語で書く。
- 何かを起動する前に、何を起動して、いつ止めるかを書く。止めてから次へ進む。最後に、残っているプロセスを数えて報告する（「動いたまま残っているもの: なし」は数えてから書く）。ブラウザを起動するテストは `scripts/lib/stop-browser.mjs` の `guardBrowser`／`stopBrowser` を通す。
- 画面に説明の文を足さない。起きることはボタンの文言で示す。
- 分離では、仕様・保存形式・UI・文言・Rust を変えない。不要な共通化もしない。見つけた癖や不具合は直さず、記録して残す。
- ファイルは CRLF。`sed -i` は使わない（Git Bash では LF に書き直される）。Edit を使うか、`\r\n` で分けて `\r\n` でつなぐ node で書き換え、`file <path>` で確かめる。
- `npm run build` と `npx tauri build` を同時に動かさない（どちらも `dist` を書き換える）。

## 経路

| 段階 | すること | 止まるか |
|---|---|---|
| 0. 始める | ブランチ、チェックポイント、「前」のテスト一式をバックグラウンドで | — |
| A. 調査と案 | 手順書 `docs/<TOPIC>_PLAN.md` に、仕組みの説明・依存関係・影響範囲・案を書く | — |
| **確認1** | 手順書の要点と、決めてほしいことを出す | 止まる |
| B. 実施 | 小さいコミットで実施する。1つごとに型検査とテスト | — |
| C. 自動テスト | 回帰テストを足して効くことを確かめ、「後」の一式を動かして前後を比べる | — |
| D. 実機確認 | QA 用アプリで、頼まれた項目と周りの機能を確かめる | — |
| E. まとめ | 手順書と KNOWN_ISSUES に結果を書いてコミットし、片付ける | — |
| **確認2** | 結果を報告し、push と PR をするか聞く | 止まる |

作業の種類ごとの細かい手順は、次の参照文書にある。始める前に、該当するほうを読む。

- 機能の分離・ファイル分割 → `references/separation.md`
- 不具合・既知の制限の修正 → `references/bugfix.md`
- 実機確認（どちらでも使う）→ `references/real-app-qa.md`
- 手順書のひな形 → `references/plan-template.md`

## 0. 始める

```bash
git switch -c <refactor|fix>/<topic>
git commit --allow-empty -m "checkpoint: <topic>を始める前の状態（main <hash>）"
git tag checkpoint/before-<topic>
```

続けてすぐ、「前」のテスト一式をバックグラウンドで動かす（20分ほど）。変更を書き始める前に動かしておけば、あとでチェックポイントへ切り替えずに比べられる。調査と手順書の作成は、そのあいだに進める。ソースは読むだけで、書き換えない。

```bash
node .claude/skills/then-safe-change/scripts/suite.mjs run before --out <scratchpad>/suite
```

「前」の一式で失敗したテストは、今回とは関係ない元からの失敗として手順書に書く。失敗の理由は毎回変わりうるので、決め打ちにせず、この記録を使う。

## A. 調査と案

調べるときは、全部を読む前に道具で場所を絞る。

- `scripts/symbol-uses.mjs <file> <names...>`: 名前ごとの出現行を出す。1回しか出ない関数は使われていない。
- `scripts/text-deps.mjs <source> [<名前や文言>...]`: ソースの文字列を直接確かめているテストを出す。移すと中身が同じでも落ちるので、先に一覧にする。
- `git log`、`docs/KNOWN_ISSUES.md`、関係する `docs/*_PLAN.md` で、過去の判断を確かめる。

手順書は `references/plan-template.md` のひな形で書く。説明は平易な言葉で書き、専門用語には意味を添える。利用者が「省略しない」と言う説明は、操作、内部で起きること、保存、他の機能との関係のすべてを含む。

書いているうちに見つけた仕様の癖（たとえば「元に戻すと末尾に戻る」）は、手順書の「今の挙動の癖」に書く。分離では直さない。確認1で、直すかどうかを利用者に決めてもらう。

## 確認1

手順書へのリンクと要点（何をどこへ動かすか／どう直すか、影響の重いところ、今回やらないこと）を短く書き、決めてほしいことを1つずつ選択肢にして出す。勧めるほうを先頭に置いて、理由を添える。答えをもらうまではコードを変えない。

## B. 実施

- 1つのまとまりを動かすたびに、`npx tsc --noEmit` と関係するテストを動かしてコミットする。失敗したら、そのコミットだけを戻せばよい。
- 分離のときは、`scripts/move-lines.mjs`（行番号と先頭・末尾の行の文字列を確かめて移す）で移し、`scripts/verify-move.mjs` で突き合わせる。lost が 0 で、added が意図した行だけなら、中身は変わっていない。詳しくは `references/separation.md`。
- 不具合の修正では、先に「今は失敗するテスト」を書いてから直す。詳しくは `references/bugfix.md`。

## C. 自動テスト

1. 回帰テストを足す。変えた処理を実際に動かすテストにする。文字列を確かめるだけのテストは、移した先で動くかを保証しないので足りない。
2. 足したテストが効くことを確かめる。直した処理や移した処理にわざと不具合を2つ入れ、テストが落ちることを見て、`git checkout -- <file>` で戻す。
3. 「後」の一式を動かして比べる。

```bash
node .claude/skills/then-safe-change/scripts/suite.mjs run after --out <scratchpad>/suite
node .claude/skills/then-safe-change/scripts/suite.mjs compare <scratchpad>/suite/suite-before.json <scratchpad>/suite/suite-after.json
```

「new failure」が出たら、まずそのテストを単独で2回動かす。1回目の一式でだけ止まり、単独では通ることがある（2026-10-23 の `test:ai-selection`）。単独でも落ちるなら、変更のせいとして調べる。

## D. 実機確認

`references/real-app-qa.md` の手順で行う。並べ方は、「後」の一式が終わってから QA 用アプリを build する（`dist` が重なるため）。build のあいだに、一時ライブラリの中身と確かめる項目の表を作っておく。

## E. まとめと確認2

- 手順書に、工程ごとの結果、確かめられなかったことと理由、残っている別の作業を書く。
- 不具合を直したなら、`docs/KNOWN_ISSUES.md` の状態を書き換える。新しく見つけた癖は記録する。
- `scripts/qa/qa-cleanup.mjs` で片付け、残りが全部 0 であることを報告に書く。
- 確認2: 結果を短く報告し、push して PR を作るかを聞く。push は外に出る操作なので、答えをもらってからにする。残っている別の作業は、別のセッションの候補として出す（main に取り込む前のブランチから始める必要があるなら、そう書く）。

## 道具

すべてリポジトリのルートで動かす。`<skill>` は `.claude/skills/then-safe-change`。

| 道具 | 使いどころ |
|---|---|
| `<skill>/scripts/symbol-uses.mjs` | 名前の出現行、使われていない関数や import、呼び出し位置より前での使用（`--call-site`） |
| `<skill>/scripts/text-deps.mjs` | ソースの文字列を確かめているテストの一覧 |
| `<skill>/scripts/move-lines.mjs` | 行の範囲を確かめてから、別ファイルへ移す（spec の形はファイルの先頭に書いてある） |
| `<skill>/scripts/verify-move.mjs` | 移したコードが元と同じかの突き合わせ |
| `<skill>/scripts/suite.mjs` | テスト一式の実行（`run`）と前後の比較（`compare`） |
| `<skill>/scripts/qa/qa-build.mjs` | QA 用アプリの build（Cargo.toml の改行の書き換えも戻す） |
| `<skill>/scripts/qa/qa-seed.mjs` | 一時ライブラリと QA アプリのアプリ状態を作る |
| `<skill>/scripts/qa/qa-session.mjs` | QA アプリを起動し、HTTP で操作を受け付ける（バックグラウンドで動かす） |
| `<skill>/scripts/qa/q.mjs` | 操作を1つ送る（eval / type / key / click / stop） |
| `<skill>/scripts/qa/qa-page.js` | 画面の中で使う手助けの関数（`window.qa`） |
| `<skill>/scripts/qa/qa-cleanup.mjs` | 片付けと、残っているプロセスの数え上げ |
