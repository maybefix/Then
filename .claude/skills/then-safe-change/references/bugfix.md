# 不具合・既知の制限の修正

挙動を意図して変える作業。分離と違い、確認1で「どう変えるか」を利用者に決めてもらうことが中心になる。

## 段階Aでやること

1. **記録を読む**: `docs/KNOWN_ISSUES.md` の項と、関係する手順書（`docs/*_PLAN.md` の「今の挙動の癖」や実機確認の結果）を読む。そこに書かれた「見込み」と「確かめた」を区別する。
2. **再現する**: できるだけ自動テストで再現する。操作の関数が `src/<feature>Actions.ts` や `src/<feature>Model.ts` にあるなら、`scripts/test-idea-thread-actions.mjs` と同じ形で、入れ物の state に対して呼べる。画面やウィンドウ間の連携が要るものは、QA 用アプリで再現する（`references/real-app-qa.md`）。再現の手順と、実際に起きたことを書く。
3. **原因を書く**: 原因の処理（ファイルと関数）、その処理が読む値と書く値、その処理を呼ぶもの。直したときに巻き込まれそうな処理（同じ値を書くほかの処理、同じ文言を確かめるテスト）も挙げる。`symbol-uses.mjs` と `text-deps.mjs` を使う。
4. **直し方の選択肢を2〜3個出す**: 案ごとに、利用者から見て何が変わるか、保存形式が変わるか（変わるなら、古いデータの読み込みをどうするか）、影響の重さ、手間を書く。勧めるものを先頭に置き、理由を書く。画面に説明の文を足す案は出さない。起きることは、ボタンの文言や操作の結果で示す。
5. **影響範囲**: 変えるファイル、変える挙動、変えない挙動。前後で結果が変わるはずのテスト（直したことで期待が変わるもの）を先に挙げておく。

手順書は `references/plan-template.md` のひな形を使う。工程2の説明は、その不具合に関係する仕組みだけでよい。

## 確認1で聞くこと

- どの直し方にするか（選択肢）
- 既存のテストの期待を変えてよいか（たとえば、「元に戻す」が付くことで変わる確認）
- 一緒に直すか、別にするか（同じ処理に関係する別の癖がある場合）

## 段階B〜D

1. **先に失敗するテストを書く**: 選ばれた直し方で期待する結果を回帰テストに書き、今のコードで落ちることを確かめてコミットする。テストの名前と文言は、何を直したかが分かるようにする。
2. **直す**: 小さく直し、型検査と、そのテスト・関係するテストを動かす。
3. **テストの期待を変える場合**: 変える確認の行と理由を、コミットの本文に書く。確認1で了承をもらった行だけを変える。
4. **一式の前後比較**: 「new failure」は、直したことで期待が変わったテストだけのはず。それ以外の新しい失敗は、単独で動かし直してから調べる。
5. **実機確認**: 再現の手順をそのままなぞり、直ったことを確かめる。周りの機能も確かめる（同じ値を書くほかの操作、保存、作品の切り替え、再起動後の復元）。

## 段階Eでやること

- `docs/KNOWN_ISSUES.md` のその項に、**修正:**（何をどう変えたか）、**確認:**（自動テストと実機で何を確かめたか）を足し、**状態:** を書き換える。
- 手順書の「今の挙動の癖」の該当行に、直したことを書き添える。
- 直していないが見つけた別の癖は、新しい項として記録する。
