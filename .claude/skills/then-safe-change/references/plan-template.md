# 手順書のひな形

`docs/<TOPIC>_PLAN.md`（例: `docs/IDEA_SEPARATION_PLAN.md`）として、段階Aでまとめて書く。各工程が終わるたびに状態の表を更新し、結果を足してコミットする。完成した見本は `docs/IDEA_SEPARATION_PLAN.md`。

```markdown
# <対象> <分離|修正> の手順書

<何を、なぜ。変えないもの（仕様・保存形式・UI・文言など）を1〜2文で。>

- ブランチ: `<branch>`
- 戻し先: タグ `checkpoint/before-<topic>`（コミット `<hash>`。中身は main `<hash>` と同じ）

| 工程 | 内容 | 状態 |
|---|---|---|
| 1 | 調査 | |
| 2 | 仕組みの説明 | |
| 3 | 依存関係 | |
| 4 | 影響範囲 | |
| 5 | 案 | |
| 6 | 人の確認（確認1） | |
| 7 | 実施 | |
| 8 | 自動テスト | |
| 9 | 実機確認 | |
| 10 | 完了（確認2） | |

## 工程1: 調査の結果
- コードがある場所（ファイルと行の範囲、行数）
- 気づいた点（使われていない処理、文字列を読むテスト、呼び名のずれ、など）

## 工程2: 仕組みの説明
### 言葉（専門用語と意味）
### 1. データの形
### 2. 利用者の操作と内部の処理（操作ごとの表）
### 3. 保存（保存先・いつ保存するか・読み込みと復元・切り替え）
### 4. ほかの機能との関係
### 5. 今の挙動の癖（直さないもの。工程9で実機で確かめる）

## 工程3: 依存関係
（分離: references/separation.md の「依存関係の書き方」の A〜H）
（修正: 原因の処理と、その処理を呼ぶもの・その処理が書くもの）

## 工程4: 影響範囲
### 4-1. 変更対象になるファイル（必ず変わる／条件しだいで変わる／変えない）
### 4-2. まとまりごとの影響（重さ: 高=データ消失、中=表示順や連携、低）
### 4-3. 機能ごとに起こりうる回帰不具合（既存テストで気づけるか）
### 4-4. 今の自動テストの状態（「前」の一式の結果）

## 工程5: 案
### 5-1. 方針
### 5-2〜. 移すもの／残すもの／UI 側へ移すもの（分離）、直し方の選択肢と勧め（修正）
### 決めてほしいこと（選択肢、勧めとその理由）
### テストの直し方と足すテスト
### 進め方とコミットの分け方
### 見込みと、今回やらないこと

## 工程6: 人の確認
（決まったこと、日付）

## 工程7: 実施
（コミットの表、行数の変化、元と同じであることの確かめ方、違う点の一覧）

## 工程8: 自動テスト
（足した回帰テストと、効くことの確かめ方。前後の比較の表。止まったテストの扱い）

## 工程9: 実機確認
（やり方、確認した項目と結果の表、癖を実機で確かめた結果、確かめられなかったことと理由、片付け）

## 工程10: 完了
（変わったもの、確かめたこと、残っている別の作業の表）
```

書き方のこつ:

- 説明は、読み手が画面を思い浮かべられる言葉にする。関数名は括弧で添える程度にする。
- 「見込み」（コードを読んでの推測）と「確かめた」（実際に動かした）を書き分ける。
- 行番号は、どのコミットの時点の番号かを書いておく（移すと行番号がずれる）。
