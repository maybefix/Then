### 気づいた点
- 収める処理は、ファイルを読んだ時点で、データそのものに対して行っている。その結果は 0.7 秒後にそのまま保存される。読む処理は、画面の大きさを知らない。

## 工程2: 仕組みの説明

### 言葉
- **資料のカード**: 本文の上に浮かべて置く、資料（テキスト・画像・PDF）や Idea の断片のカード。位置（x, y）と大きさ（width, height）を、作品の `.then/reference-layouts/default.json` に保存する。
- **本文の枠**: 本文のエディタを囲む `div.editor`（`editorShellRef`）。左右のサイドバーは含まない。
- **収める**: カードが枠の外に出ないよう、位置と大きさを詰めること（`clampReferenceCardToStage`）。幅は「枠の幅 − 24」まで、横位置は「枠の幅 − カードの幅 − 12」まで。高さと縦位置も同じ。
- **起動の画面**（`startupView`）: `"loading"`（「Then を読み込んでいます…」）、`"portal"`（起動画面）、`"editor"`（本文の画面）の3つ。本文の枠は `"editor"` のときだけ画面にある。

### 1. 作品を開いたときの流れ（起動直後）
1. 起動画面で「前回の執筆を続ける」を押す（`handleContinueFromPortal`）。画面は `"loading"` になる。
2. 前回の作品を開く（`restoreWorkspaceFromState`）。この途中で `projectFolder` が決まる。
3. `projectFolder` が変わったので、`loadReferences` の useEffect が動く。ここで本文の枠を測るが、画面はまだ `"loading"` で、枠の要素がない。`editorShellRef.current` は null なので、仮の 1200×800 を使う。
4. ファイルを読み、1200×800 で収めて画面の状態に入れる。0.7 秒後にその結果を保存する。
5. 作品を開き終わってから、画面が `"editor"` になる。カードはもう 1200×800 で収めたあとなので、枠より大きい位置のまま描かれる。

起動画面で作品を選んだとき（`handleOpenWorkspaceFromPortal`）も、画面が `"portal"` のまま作品を開くので同じ。起動画面を出さない設定（`skipStartupPortal`）のときは、読み込みの useEffect が `isHydrated` を待つので、本文の画面になってから測れる見込み（工程9で確かめる）。

### 2. 作品を切り替えたとき
本文の画面のまま作品を切り替えると、枠はもう画面にあるので、本物の大きさで収める。ただし、キャンバスの画面（`appMode === "canvas"`）では本文の列が `display: none` で隠れているので、枠の大きさは 0×0 と測られる。このとき収める計算は、幅 240・高さ 180・位置 (0, 0) になる。その結果が保存される（変更前の実機で確かめた）。

### 3. 保存
- 保存先: 作品の `.then/reference-layouts/default.json`。保存の前に今のファイルを `default.json.bak` へ写す。
- いつ: 読み込みが終わると `referenceLayoutLoadedRootRef` にその作品のパスが入り、それから `referenceLayout` が変わるたびに 0.7 秒後に保存する。読み込んだ直後も `referenceLayout` が変わるので、作品を開くたびに1回保存する。

### 4. ほかの機能との関係
- 左のサイドバーの「資料」の一覧は、同じ `referenceLayout.cards` を出す（位置は使わない）。
- Idea のスレッドの並び順（`ideaThreads`）も同じファイルにある。Idea の管理単位の切り替え（`alignIdeaLayoutToMode`）は、収めたあとに行う。
- カードをドラッグで動かすときは、左と上にだけ止まり、右と下には止まらない（`ReferenceLayer.tsx` 220–236 行）。

### 5. 今の挙動の癖
1. **起動直後は 1200×800 で収める**（今回の不具合）。
2. **枠が 1200×800 より大きくても、1200×800 の範囲へ引き戻す**（`loadReferenceLayout` の中の既定の大きさ。実機で確かめた）。
3. **キャンバスの画面のまま作品を切り替えると、カードが左上で 240×180 に縮む**（実機で確かめた）。
4. **作品を開くたびに、変わっていなくてもファイルを書き直し、予備のファイルも上書きする**。
5. **収めるときの基準の位置が、カードを描く層と合っていない**: カードを描く層（`.referenceLayer`）は、左のサイドバーを含む画面の左端が 0。収める計算は、本文の枠の幅だけを使い、枠の左端（サイドバーの幅）を足していない。左のサイドバーを開いていると、収めたカードの右端は、枠の右端よりサイドバーの幅だけ左に来る。新しく開くカードは、作業の画面（`workspaceRef`）の大きさで収めるので、また別の基準になる。

## 工程5: 案

### 5-1. 方針
本文の枠（または描く層）が画面にあって大きさが 0 でないことを確かめてから収める。仮の大きさ（1200×800）は使わない。調整用の定数は足さない。

### 5-2. 位置が今と同じになる場面と、変わる場面
- 同じ: 窓が 1200×800 以下で、本文の画面のまま作品を切り替えるとき（決めてほしいこと2で「今のまま」を選んだ場合）。
- 変わる（直すことそのもの）: 起動直後、キャンバスの画面のまま切り替えたとき、窓が 1200×800 より大きいとき。
- 変わる（2の選び方による）: 左のサイドバーを開いているとき。

### 決めてほしいこと
1. **直し方**
   - 案A: 読み込みでは収めず、本文の枠を測れるようになってから一度だけ収めて、データを書き換える。枠が画面に出て大きさが 0 でなくなるのを待つ（`ResizeObserver`）。手間は小さい。今と同じく、窓を広げても、一度収めたカードは元の位置へ戻らない。
   - 案B: データは収めず、カードを描くときだけ収める。ファイルの位置は利用者が動かしたときしか変わらない。窓を縮めたときもその場で収まり、広げ直すと元の位置へ戻る。描く処理とドラッグの起点が変わるので手間が大きく、窓の大きさを変えたときにカードが動く（今はない動き）。
2. **収める範囲**
   - 今のまま: 枠の幅と高さだけを使い、原点は層の左上。左のサイドバーを開いていると、カードはサイドバーの上に寄る（実機で x=12）。
   - 本文の枠の位置に合わせる: 層の中での枠の左上から右下までに収める。カードが本当に本文の枠の中に入る。サイドバーの上に置いたカードも、開き直すと本文の枠へ動く。
   - カードを描く層に合わせる: 画面の外へ出たカードだけを戻す。サイドバーの上に置いたカードは動かない。新しいカードを開くときの範囲（作業の画面）に近い。
3. **作品を開くたびの書き直し（`.bak` の上書き）**: 一緒に直す（読み込んだまま変わっていなければ保存しない）／別にする／記録のみ。

### テストの直し方と足すテスト
- `scripts/test-stored-state-model.mjs` の「cards are clamped into the stage」は、`normalizeReferenceLayout` に大きさを渡して収める確認。収める処理を分けた関数へ移すので、この確認も分けた関数の確認へ移す（確かめる値は同じ）。
- 足すテスト: 読み込みから収めるまでを、枠がない・0×0・本物の大きさの3つで動かし、収めるのは本物の大きさのときだけで、1200×800 を使わないこと、変わらないときは保存しないことを確かめる。
