# バインダーのAI調査機能 実装範囲と手順書

作成日: 2026-10-16  
状態: 実装前の設計・作業手順。本文の新規機能は未実装。  
対象: Windows版Thenの既存バインダーとアイデア追加ポップアップ

対象リリース: v0.7.0。原稿用紙モード、ポップアップからの資料追加・AI調査依頼、スレッドの並べ替えを含む全体範囲は、[v0.7.0実装計画](V0.7.0_IMPLEMENTATION_PLAN.md)で管理する。

## 1. 目的と実装方針

バインダーへ調査依頼を追加すると、一つのAIが回答し、その内容をMarkdown資料として同じスレッドへ保存する。原稿全体の読み取りや自動編集は行わない。利用者自身がAPIを設定することを前提とする。

実装を小さく保つため、既存の入力欄、スレッド、資料ファイル、資料カードを流用する。追加する中心機能は、調査の実行管理、Windowsでの認証情報保管、接続先ごとの変換処理とする。汎用プラグインAPIや独自のAI実行基盤は作らない。

到達点はGemini、OpenAI、Claude、ローカルLLMの四系統への対応とする。ただし、四系統を同時に実装し始めず、一つの接続先で入力から資料保存まで完成させ、その契約に残りの接続先を合わせる。

## 2. 実装する範囲

| 項目 | 初期版の仕様 |
| --- | --- |
| 起点 | バインダーとアイデア追加ポップアップの入力欄で「調査」を選び、質問を追加する。既存Ideaにも「調査する」を用意する |
| 送信内容 | 入力した質問。追加質問では、利用者が選んだ直前の調査一件も含められる |
| 動作モード | 「説明・相談」と「Web検索付き調査」。検索できない接続先では後者を選べない |
| 接続先 | Gemini、OpenAI、Claude、ローカルLLM。設定した一つだけを一回の依頼に使用する |
| 出力 | 質問、回答、クリックできる出典、日時、接続先、モデルを記載したMarkdown資料 |
| 表示 | 元の質問には実行状態と回答資料への操作を表示し、長い全文は既存資料カードで読む |
| 操作 | 停止、失敗後の再試行、再調査、回答からの追加質問、資料を開く |
| 保存 | 質問は既存Idea、実行記録は作品内の専用JSON、回答は既存資料フォルダへ保存する |
| 認証 | 利用者のAPIキーをWindows資格情報マネージャーへ保管する |
| 利用量 | APIから得られたトークン数・検索回数を記録する。取得できない値は不明として扱う |
| 実行数 | アプリ全体で一件ずつ処理する。複数依頼は待機列へ入れる |

「説明・相談」はモデルの知識による回答であり、Webで確認済みとは表示しない。「Web検索付き調査」も、APIが実際に検索したか、検索が失敗したかを結果に記録する。検索を依頼しただけで「調査済み」と判定しない。

### 2.1 今回の対象外

- 原稿、スレッド全体、作品フォルダの自動読み取り・送信。
- 本文の書き換え、PlotやCanvasの自動操作、複数AIの分担。
- AIへのファイル添付、画像・PDF解析、ベクトル検索、RAG、任意のツール実行。
- 独自クローラー、共通検索サービス、深い調査を繰り返す自律ループ。
- アカウント発行、Then側の中継サーバー、代理課金、OAuth、Vertex AI等の追加認証方式。
- 汎用AIプラグイン基盤、任意ヘッダー・任意クラウドURLを指定できる接続設定。
- 回答の逐次表示、詳細な料金ダッシュボード、自動の円換算。
- 会話履歴の無制限送信、モデルの自動切り替え、異なる接続先への自動再試行。
- ライブラリホームなど、作品を開いていない場所からの調査。

## 3. 操作と送信の規則

### 3.1 新規依頼

バインダーの一覧・スレッド詳細にある入力欄へ、既存レイアウトに収まる「調査」切り替えを追加する。通常のIdea追加は維持する。調査を選んだときだけ「説明・相談 / Web検索付き調査」を表示し、追加ボタンは「調査を依頼」に変える。

調査切り替えの初期値はオフとし、一件追加した後もオフへ戻す。入力中の文字変更、フラグの表示、画面表示だけでは通信しない。ボタンまたは既存の確定操作で依頼を追加したときに一度だけ送信する。日本語IMEの確定Enterで送信されない既存の挙動を維持する。

質問の保存と実行記録の作成を先に完了し、その後に通信する。キー未設定など送信できない場合も質問は残し、設定後に「実行」を押せるようにする。既存Ideaの「調査する」も同じ処理へ接続する。

クイックIdeaモーダルへの資料追加・AI調査依頼もv0.7.0の実装範囲に含める。バインダーと共通の依頼処理を呼び出し、質問の保存と受付が完了してからモーダルを閉じる。モーダルを閉じても受付済みの調査は続行し、状態と回答はバインダーで確認できる。作品の切り替え・終了時は、後述の停止規則に従う。

ポップアップの資料追加は、バインダーの既存ファイル追加・新規テキスト資料作成と同じ処理を使う。添付した資料をAIへ自動送信する機能は含めない。資料追加と調査の文脈指定を混同しないようにする。

### 3.2 回答と追加質問

回答を通常のMarkdown資料として同じスレッドへ追加する。資料の並びは既存の先頭追加に合わせ、元の質問から「回答を開く」で直接移動できるようにする。新しい回答が届いても、執筆画面の切り替えや資料カードの強制表示は行わない。

追加質問では、対象の回答一件を選択して新しい質問を作る。送信前に、追加する文脈として「元の質問と選んだ回答」を確認できるようにする。初期版はこの一件だけを含め、親の親やスレッド全体へ自動的にたどらない。回答が編集されている場合は現在の資料を使い、送信時点の内容を記録する。

追加質問は各社の長期セッションを使わず、質問と選択した文脈から独立したリクエストを作る。プロバイダー固有の暗号化履歴や会話IDの永続管理を初期版へ持ち込まない。外部資料の文章は参考情報として渡し、そこに含まれる指示をツール実行へ結び付けない。

### 3.3 再調査と移動・削除

再調査は新しい実行IDと新しい資料を作る。既存の回答資料は上書きしない。元の質問を編集しても自動再送しない。

実行中・待機中の質問や所属スレッドを移動・削除するときは、先に該当する依頼を停止する。停止が確定してから既存操作を行い、遅れて届いた回答で項目を復活させない。完了済みの質問の移動は既存操作を使い、次の依頼は現在の所属先へ作る。資料自体の移動・削除は既存仕様を維持する。

作品間の転送は、既存Ideaと資料の転送規則に従う。実行記録や送信権限は転送せず、転送先で自動実行しない。

スレッド一覧内の並べ替えは、移動・削除と区別する。スレッドIDと所属が変わらないため、調査を停止・再送せず、結果を引き続き同じスレッドへ保存する。

## 4. 保存と実行状態

### 4.1 保存先

| データ | 保存先 | 方針 |
| --- | --- | --- |
| 質問 | 既存のIdea保存先 | IdeaFragmentの本文をそのまま使う |
| 調査フラグ・実行記録 | `<project>/.then/research/jobs.json` | 新設。作品ごとに分離し、Rust側で読み書きを直列化する |
| 回答資料 | `<project>/.then/references/imports/research-<jobId>.md` | 既存の資料列挙・表示・編集の対象にする |
| 資料の所属と順序 | 既存の `.then/references/layout.json` | 既存の参照追加・保存経路を使う |
| 接続先・モデル・既定モード | 端末ローカルのアプリ設定 | キーを含めない。作品に絶対パスや端末情報を持ち込まない |
| APIキー | Windows資格情報マネージャー | 作品・アプリ設定JSON・localStorageへ保存しない |

調査フラグは、現在の作品の実行記録とIdeaのIDから求める。既存Ideaのスキーマへフラグを追加する方法は初期版では採らない。現行の `normalizeIdeaThreads` とRustの `IdeaFragmentConfig` は既知フィールドを作り直すため、追加フィールドが保存途中で落ちる改修を避けられる。

専用JSONは、一時ファイルへの書込と読戻し確認を経て置き換え、直前の正常な内容をバックアップする。生成Markdownも完成した内容を一時ファイルへ書いてから確定する。既存の保存補助処理を確認して流用し、同じ作品への更新はRust側で直列化する。

Ideaの保存設定が端末共通（profile）でも、作品を開いている間は手動で調査できる。調査状態と回答資料はその作品だけに置き、別作品で同じ共通Ideaを表示しても送信や状態共有を行わない。作品を開いていない場合は調査操作を無効にする。

### 4.2 実行記録の最小フィールド

`schemaVersion` を持つ専用ストアに、次を保存する。ネットワーク処理へReactの現在状態を直接参照させない。

| フィールド | 用途 |
| --- | --- |
| `id` | 実行ID。重複処理と資料ファイルの識別に使う |
| `originThreadId`, `originFragmentId`, `originStorageMode` | 質問の所属。作品ルートは実行時に捕捉し、作品内JSONへ絶対パスを保存しない |
| `questionSnapshot`, `contextSnapshot`, `parentJobId?` | 実際に送信した内容と追加質問の関係 |
| `provider`, `model`, `mode` | 依頼時の接続設定。待機中の設定変更で別のAIへ送らない |
| `status`, `phase`, `createdAt`, `updatedAt` | 実行状態と復旧判断 |
| `resultPath?`, `searchPerformed?`, `usage?`, `errorCode?` | 出力、検索の実施、利用量、機密情報を含まないエラー |
| `pendingResult?` | 回答受信後、資料保存を再試行するための正規化済み結果。保存完了後に除去する |

通常はキーを保持しない接続設定を参照し、送信直前にRust側で現在のキーを取得する。キー削除・差し替えは待機中の依頼にも反映し、削除済みキーをメモリへ抱えて実行を続けない。

### 4.3 状態と復旧

画面上の状態は「待機・調査中・完了・失敗・中止・中断」の六つとする。内部の `phase` で通信と保存を区別する。

| 条件 | 処理 |
| --- | --- |
| 新規依頼 | 質問と記録を保存し、現在の作品の待機列へ追加する |
| 通信完了 | 正規化した回答を一時的に永続保存し、資料保存へ進む |
| ファイルまたは参照の保存失敗 | 回答を保持して「保存を再試行」を表示する。AIへ再送しない |
| 保存と参照追加が完了 | 完了にする。再通知されても同じ資料を重複追加しない |
| 作品切り替え・作品を閉じる | 実行中を停止し、待機列を中断する。次の作品で実行を継続しない |
| アプリ再起動 | 未完了を中断として復元する。自動通信しない。受信済み回答があれば保存のみ復旧できる |
| キー未設定・認証失敗・制限超過・通信失敗 | 原因を分類して表示する。自動で有料リクエストを繰り返さない |
| 利用者が停止 | ローカルの要求と後続処理を中止する。送信済み分の課金が取り消されるとは表示しない |
| 検索ツールだけが失敗・無検索・出力上限で終了 | 正常完了と同一に扱わず、未検索・一部回答などの結果状態を資料にも残す |

実行ID単位のロックと、作品切り替え世代の照合を行う。遅延した応答を新しい作品のstateへ適用しない。ファイル名と保存先はThenが決め、AIが返したパスは使わない。

資料ファイル、実行記録、資料参照の三つを完全な一括トランザクションにはしない。実行IDを使い、同じ保存処理を繰り返してもファイルと参照が一つになるようにする。受信済み回答を記録し、Markdown保存、参照追加、完了記録の順で進める。既存ファイルがある復旧処理では内容を検証し、利用者による編集を上書きしない。

初期版では保存復旧を作品を開いた後の明示操作で行う。既存の資料照合処理が未所属資料をインボックスへ追加する場合も、同じファイルを二重登録しない。保存直後の終了、参照だけ欠けた状態、ファイルだけ欠けた状態を試験する。

## 5. 接続先の対応範囲

### 5.1 共通契約

接続処理の入力は、質問、任意の文脈一件、モデル、動作モード、出力上限とする。出力は回答本文、出典と本文中の参照関係、実際の検索実施状態、利用量、完了・一部回答の区別とする。キー、任意URL、任意ヘッダーを質問から受け取らない。

共通処理は実行状態、停止、保存、表示を担当する。接続先ごとの処理はリクエスト作成、レスポンス解釈、引用変換、エラー分類だけを担当する。まず必要な一往復を実装し、将来機能のための汎用エージェント抽象化は行わない。

### 5.2 接続先ごとの方針

| 接続先 | 説明・相談 | Web検索付き調査 | 初期版の接続方式 |
| --- | --- | --- | --- |
| OpenAI | 対応 | 対応モデルの組み込みWeb検索 | APIキー、Responses API。一連の動作を最初に完成させる接続先 |
| Claude | 対応 | 対応モデルのWeb search tool | APIキー、Messages API。検索の利用回数上限も設定する |
| Gemini | 対応を計画 | Google検索のGrounding。保存・表示条件の確認後に有効化 | Gemini APIのAPIキー。Vertex AIは対象外 |
| ローカルLLM | 対応 | 初期版は非対応 | ローカルで既に起動したOpenAI互換のChat Completionsエンドポイント |

ローカルLLMの受け入れ確認にはOllamaを使う。接続先とモデル名は利用者が設定し、Thenからサーバー起動やモデルのダウンロードは行わない。初期版のURLはloopback（`127.0.0.1`、`localhost`、`[::1]`）に限定する。リダイレクトは追わず、任意のLAN・外部サーバー対応は後続に分ける。

ローカルで生成した説明を「Web調査済み」とは表示しない。ローカルLLMへWeb検索を追加するには別の検索経路が必要になるため、四系統の文章生成対応と、四系統のWeb検索対応を同じ完了条件にしない。[Ollama互換API](https://docs.ollama.com/api/openai-compatibility)・[OllamaのWeb検索](https://docs.ollama.com/capabilities/web-search)

モデルの選択肢は、実装時に確認した少数の推奨値とモデルIDの手入力で始める。モデル一覧の自動取得や全モデルの機能判定は作らない。対応能力は接続先と検証済みモデルの小さな表で管理し、未検証モデルで検索を使う場合は実際の応答で判定する。検索非対応時に通常回答へ黙って切り替えない。

### 5.3 Geminiの事前確認

2026-10-16に確認したGemini API追加規約には、Google検索を使った回答について、保存の例外、表示、変更に固有の条件がある。利用者が個別の回答を保存できる例外もあるが、Thenによる自動資料化、既存資料の編集・検索・転送までそのまま適合すると、この手順書では判断しない。アプリの対象用途についても確認する。[Gemini API追加規約](https://ai.google.dev/gemini-api/terms#grounding_with_google_search)

工程0で、通常回答と検索付き回答の保存・表示・編集・再送を分けて適合を確認する。必要な検索候補表示などを、出典一覧だけで代用しない。条件が整理できない間は該当能力を公開せず、Gemini全機能が完了したとは扱わない。他の接続先と共通部分の実装は進められる。

Geminiだけのために全資料へ期限削除や別管理体系を導入しない。既存資料の扱いを大きく変える必要がある場合は、代案と追加工数を提示して仕様を見直す。

### 5.4 引用と利用量

出典はAIが本文に書いたURLだけに頼らず、APIが返す引用情報から本文へリンクを組み込む。各社で位置や形式が異なるため、Markdown変換後も根拠との対応が残るようにする。回答の表示には各社の必要な帰属表示を含める。[OpenAI公式ドキュメント](https://developers.openai.com/api/docs/guides/tools-web-search)・[Claude Web search tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/web-search-tool)・[Gemini Grounding](https://ai.google.dev/gemini-api/docs/google-search)

利用量は取得できた実数を保存する。検索回数、入力・出力トークンの不明値をゼロへ変換しない。初期版は料金を自動計算せず、設定から各社の料金ページを開ければよい。

## 6. 認証・通信と表示

Windows専用の初期版では、既存の `windows` crateから資格情報APIを利用する方針とする。`CRED_TYPE_GENERIC`、端末内の永続化を使い、資格情報名はThenと接続先を識別できる形式に固定する。独自暗号化、マスターパスワード、独自の鍵ファイルを作らない。[Windows CREDENTIALW](https://learn.microsoft.com/en-us/windows/win32/api/wincred/ns-wincred-credentialw)

| 対象 | 必須の扱い |
| --- | --- |
| キー入力 | 設定画面からRustへ渡すために一時的に保持し、保存・キャンセル・閉じる操作で入力stateを破棄する |
| キー参照 | フロントエンドへ返すのは設定済みかどうかだけ。保存済みキーを読むコマンドは公開しない |
| 設定操作 | 保存、差し替え、削除、接続テスト。接続テストがAPI呼び出しを伴うことを表示する |
| ログ・エラー | 認証ヘッダー、キーを含むURL、送受信全文を通常ログへ出さない。API本文をそのまま例外として画面へ返さない |
| クラウド通信 | 公式HTTPSエンドポイントをRust側で固定し、認証情報は送信直前に付与する。リダイレクトで別ホストへ転送しない |
| ローカル通信 | loopback URLを検証し、クラウド用キーを流用しない。任意ヘッダーを設定させない |
| 出力表示 | raw HTMLを実行せず、出典リンクはHTTP/HTTPSを許可する。生成された外部画像を自動取得しない。一般資料の既存リンクとの互換性も確認する |
| 呼び出し元 | 新しい通信・資格情報コマンドは本体の調査機能に限定する。既存プラグインAPIへ公開せず、iframeの隔離を維持する |
| 限度 | 入力長、出力トークン、応答サイズ、総処理時間、検索回数をコード内の小さな設定表で制限する |

資格情報マネージャーは保管先を提供するもので、同じWindowsユーザーとして実行される悪意あるプログラムからの完全な隔離を保証する設計ではない。今回の目標は、作品共有や通常ログへの混入、画面側への不要なキー露出を減らすこととする。

入力長超過は送信前に知らせ、文脈を黙って切り捨てない。出力上限による一部回答は、その旨を資料に表示する。タイムアウトや停止はローカルの処理を止める機能であり、プロバイダー側の実行・課金終了を保証しない。

上限の初期値案は、質問8,000文字、追加文脈24,000文字、出力8,192トークン、応答2MiB、クラウド180秒、ローカル300秒とする。検索回数をAPIで制御できる接続先では最大5回から始める。これらはThen側の設計値であり、実装時に対応モデルの制限と試験結果で調整する。検索回数を制御できない接続先で、同じ上限を保証しない。初期版で詳細設定画面は増やさない。

通信はRustのHTTPクライアントを一つ使い、必要なREST処理を薄く実装する案を基本とする。各社SDKを一律に四つ追加したり、Node/Pythonの補助プロセスを同梱したりしない。SDK採用の方が実装と保守を減らせる箇所があれば、その接続処理内だけで比較する。

既存の `create_reference_text_file` は空ファイル作成、`save_reference_text` は内容保存を行う。生成資料用には、実行IDで決めたファイルへ内容を安全に保存する小さな処理を設け、命名・パス検証・列挙には既存処理を使う。空ファイルを作成してからAPIを呼ぶ方式にはしない。

資料参照の更新は既存のReact側の更新経路へ統一する。Rustから同じ `layout.json` を独立に書き換えて、自動保存と競合させない。完了イベントは作品と実行IDを照合し、最新のlayoutへ関数形式で適用する。完了扱いは参照の保存確認後に行う。

## 8. 実装手順

### 工程0: 開始条件と接続契約

1. 作業ブランチと未コミット差分を確認し、既存作業を保護する。本書作成時にはテーマ関連と `src/types.ts` に既存差分があったため、実装開始時に再確認する。
2. 本書と既存のIdea・資料統合仕様を読み、追加画面を増やさない方針を確認する。
3. 各社公式資料から、実装に使うモデル、検索方式、出力上限、引用形式、保存・表示条件を確認する。確認日と採用値を接続先ごとの短い表へ残す。
4. Geminiの公開条件を整理する。未解決事項はその接続先に限定し、他の実装を止めない。
5. 共通入出力、状態遷移、保存先を定義し、キーを使わない固定レスポンスの接続先をテスト用に用意する。

完了条件: 四系統の能力の違いと確認が必要な条件が明記され、実APIなしで後続工程を検証できる。

### 工程1: 通信なしで資料化を完成させる

1. 実行記録の読込・保存と旧作品での未作成状態を実装する。既存のIdeaスキーマは変更しない。
2. 既存入力から質問を保存し、調査依頼一件を作る共通処理を用意する。
3. テスト用の回答をMarkdown資料へ保存し、同じスレッドに既存資料参照として追加する。
4. 再通知・保存再試行・再起動復旧で重複や上書きが生じないことを検証する。
5. 資料カードで長い回答、見出し、表、コード、出典リンクを確認する。

完了条件: APIキーなしで「質問 → 回答資料 → 再起動後の参照」が成立する。

### 工程2: Windows認証と通信の共通処理

1. 資格情報マネージャーへの保存・差し替え・削除・設定済み照会を実装する。

3. エラーを認証、制限超過、通信、モデル非対応、検索失敗、出力不完全へ分類する。
4. 接続設定を端末ローカルへ保存し、キーが混入しないことを検証する。

完了条件: テスト用資格情報で保管の実動作を確認し、キーを画面・JSON・通常ログへ返さず要求を送れる。

### 工程3: OpenAIで一連の実動作を完成させる

1. Responses APIで「説明・相談」を接続する。
2. Web検索付き依頼、検索実施状態、引用、利用量を共通結果へ変換する。
3. 待機列、停止、保存再試行、作品切り替えの処理を接続する。
4. 利用者が設定したキーで、短い説明、出典付き調査、追加質問を各一件確認する。有料の実API試験は通常CIから分離する。

完了条件: 通常の執筆を続けながら調査し、結果を資料として読み、再起動後も確認できる。

## 9. 検証

### 9.1 自動テスト

| 対象 | 確認する振る舞い |
| --- | --- |
| 状態 | 一件一回の送信、明示再試行、保存のみ再試行、停止後の遅延応答無視、再起動で自動通信しない |
| 作品分離 | 作品Aの応答が作品Bへ保存されない。profileの同一Ideaでも作品ごとに独立する |
| 保存 | 実行IDの重複、書込失敗、参照保存失敗、途中終了、ユーザー編集済み資料の保護 |
| 接続変換 | 正常、拒否、空応答、検索非対応、検索ツール失敗、引用なし、出力上限、未知フィールド |
| キー | テスト用資格情報の作成・取得・削除、未設定、差し替え、JSON・例外への混入防止 |
| 表示 | 危険なURL、raw HTML、外部画像の自動取得、長い回答、表、引用リンク |
| 制限 | 入力超過、応答超過、タイムアウト、loopback以外への接続拒否、リダイレクト拒否 |

APIは通常テストではモックを使う。新規テストは振る舞いを検証し、ソース中の文字列があるだけの検査を中心にしない。資格情報の実動作は専用のダミー名を使う明示的なWindows試験へ分離し、試験後に削除する。開発者の既存キーは参照しない。

### 9.2 手動受け入れ試験

- 通常Ideaの追加、IME確定、編集、並べ替え、資料追加が従来どおり動く。
- ポップアップから資料追加・AI調査依頼ができ、入力内容と追加先が保持される。受付後に閉じても同じスレッドへ回答が届く。
- 調査中にスレッド一覧を並べ替えても、依頼の再送や回答の取り違えが起きない。
- 各接続先で説明・相談を実行し、選んだモデルと回答が資料に残る。
- クラウド各社で、検索の実施と本文・出典の対応を実データで確認する。
- ローカルLLMではWeb検索を選べず、通常回答を検索済みと表示しない。
- 長い回答を受信中も本文入力を続けられ、回答後に画面が勝手に切り替わらない。
- 追加質問で送る内容が、指定した質問と回答一件だけである。
- 実行中の停止、キー削除、作品切り替え、質問・スレッド削除、アプリ終了を確認する。
- 保存失敗から、AIへ再送せず回答資料を復旧できる。
- 回答資料を編集・移動・削除しても、再調査で旧資料を上書き・復活させない。
- 作品を別のフォルダへコピーして回答資料を開ける。キーはコピーされず、勝手に通信しない。
- 調査機能を使わない環境では、キー設定や接続失敗が通常の執筆・資料操作を妨げない。

### 9.3 関連する既存チェック

実装後に `npm run build`、`npm run test:binder`、`npm run test:v066-idea`、`npm run test:project-portability`、新設する調査テスト、`cargo check` と関連Rustテストを実行する。既存コマンドの実行場所と引数は `package.json` とテスト実装に合わせる。UIには明色・暗色と狭いサイドバーでの確認を含める。

## 10. 作業を増やさない判断基準

既存画面・資料・設定で表現できるものは流用する。共通化は二つ目の接続先で必要になった部分に限定する。通信の逐次表示、料金計算、モデル自動取得は、基本動作の完成に必要でなければ追加しない。

優先順位は、質問と回答が残ること、再送・取り違えを防ぐこと、各社の引用を保つこと、操作の仕上げの順とする。資料保存の復旧と作品切り替えの検証は、UIの装飾より先に行う。

次の場合は、その工程の仕様を見直す。独自認証サービスが必要になる、別ランタイムの同梱が必要になる、一社の事情で全資料の保存方式を変える、未依頼の原稿や資料を読む必要が出る、検索を共通化するために独自クローラーが必要になる場合である。これらを黙って追加実装しない。
