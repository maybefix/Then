# 現在段落を使うネイティブTSF入力の接続試験

2026-10-21 / ブランチ `codex/native-tsf-ime`

## 通常画面を使う限定リリースビルド

`npm run build:native-ime-limited` で `artifacts/native-tsf-limited/Then-TSF-Limited-r2.exe` を作成する。通常のThen画面・release最適化・埋め込んだフロントエンドを使い、開発サーバーや保存しない試験画面は使わない。同じ文書・設定・位置で右下の入力方式を切り替えて比較する。設定領域は `local.then.native-tsf-limited` として通常版から分かれる。入力方式はこの限定版の設定領域に保持する。

初回の限定ビルドは `frontendDist` にWindowsの絶対パスを渡したため、TauriにURLとして解釈され、ディレクトリ一覧を開いていた。相対パスへ修正し、通常画面の `index.html` と入口JSのアセット名がEXEに埋め込まれていることをビルド後に検査する。

コピー／切り取り／貼り付けは、ブラウザのClipboard APIからWindowsのUnicodeクリップボードへ変更した。これにより、ネイティブ入力へフォーカスを移した状態での `NotAllowedError` を避ける。クリップボード処理の待機はワーカースレッドで行う。読み書き完了までに選択や文書が変わった場合は、切り取りの削除や貼り付けを適用しない。

カーソルは、空のDOM Rangeから座標が取れない場合に隣接する実文字の矩形を使い、縦書きの横線・横書きの縦線を作る。表示層の重なり順も修正した。切り替え後は実際のWindowsフォーカス状態とRust側のキー・IME・編集カウンターを表示し、接続要求だけでTSF入力中と表示しない。

自動検証：カーソル矩形6ケース、段落置換108ケース、ブラウザが非フォーカスでClipboard APIが必ず `NotAllowedError` を返す条件でのコピー／切り取り／貼り付け、表示・再接続・破棄、Windows TSFプロトコルのテストに成功。実WindowsクリップボードのGUI操作確認とは区別する。

フォルダー一覧の起動確認後、ユーザーが物理EscapeキーでComputer Useを停止したため、それ以降はGUIを操作していない。修正ビルドの実画面でのカーソル・コピー・実IMEと性能差は未確認。

## 起動・比較

リポジトリのルートで実行する。

```powershell
npm run experiment:native-ime
```

`Then TSF Input Experiment` という別ウィンドウが開く。アプリ識別子は `local.then.native-tsf-experiment`。普段のThenとは別の保存領域・WebView2プロファイルを使う。最初に開く画面は保存しない合成文書で、実際の `VerticalTextEditor` を使っている。

1. 右下の「入力：標準」を押すと「入力：TSF試験」に切り替わる。本文をクリックして入力する。
2. 必要なら「日本語入力ON」で試験用TSF接続のひらがな入力を有効にする。
3. 上部で短文／10万字以上、縦横、ページ／連続、原稿用紙を切り替える。
4. 「入力：TSF試験」を押すと標準入力に戻る。
5. 「接続状態」は、その接続で処理したキー数、IMEに消費されたキー数、属性・座標への問い合わせ回数などを表示する。ボタンを押すと本文からフォーカスが外れるため、`focused` は入力中の証拠として使わない。

「通常画面で比較」は、同じ隔離アプリの通常のThen画面へ移る。通常画面でファイルを開いて編集すれば保存操作は通常どおり有効なので、比較用のファイルを使う。通常起動では `native-ime=1` が付かず、TSF接続と試験パネルはインストールしない。

## 接続した経路

```text
ProseMirrorの現在段落・選択・DOM Rangeの実座標
    → Tauri IPC → RustのTSFコンテキスト／標準テキストストア
    → Windows IME
    → ITfTextEditSink → 段落内の最小差分をPMトランザクションへ
```

文書モデルと描画は引き続きProseMirror。ブラウザの組み込みEditContextは使わず、Rust側がIME接続を担当する。縦書き属性は `TSATTRID_Text_VerticalWriting`、座標は `ITfContextOwner::GetTextExt` で渡す。文字座標の計測対象とネイティブの文字列バッファは現在段落に限定する。

Windowsの小さな子ウィンドウが入力フォーカスを持ち、TSFが消費したキーはIMEへ渡す。通常の文字もTSFの選択範囲へ挿入し、その編集通知をPMへ戻す。消費されなかった操作キーは既存のPM・アプリのキーハンドラへ渡し、矢印移動や通常の削除・クリップボード操作の補助を行う。複数段落をまたぐ選択では標準入力へ戻す。

変換の下線とキャレットを試験用の層で表示する。変換中のページ追従にはPMの選択を使い、連続表示の追従もネイティブ入力中はアプリ側で行う。スクロール、レイアウト変更、フォント読み込み、ウィンドウ移動・DPI変更で座標を通知する。

同期要求と解除要求を直列化し、接続ごとのID、PM側の世代、ネイティブ側の編集連番と受領確認で古い通知を除外する。TSFの自己書き戻しが遅れて通知される場合も、同期済みの状態と比較して二重適用を防ぐ。

## 実行した検証

- `npm run build`：TypeScript・Viteビルド成功。
- `npm run test:native-ime`：段落置換108ケース、サロゲートペア、逆向き選択、変換のUndo/Redo、138,089字の文書で前後の段落ノードを維持。
- `cargo test --offline --manifest-path src-tauri/Cargo.toml --lib native_ime::imp::tests -- --nocapture`：Windowsの実TSFストアと編集通知、受領前の古い要求による上書き防止、自己書き戻し通知の抑止、縦横の属性、DPI変換した実座標、日本語・絵文字の挿入を検証。
- 試験用Thenのウィンドウ起動、標準／TSFの切り替え、短文画面への文字入力を観察。ただし、その文字がRust経路を通ったことの最終版での実機確認はまだできていない。

前段の独立したRustプローブでは、実Google日本語入力による再変換中の縦書き属性・文字座標の問い合わせと候補ウィンドウの表示を記録した。これは今回のThen統合版の入力試験とは区別する。

## この試作で未確認の点

再起動後、Computer Useのウィンドウ有効化が失敗し、一度の再取得でも `GetCursorPos failed: アクセスが拒否されました。 (0x80070005)` となった。このため、統合版での通常の日本語入力・候補配置と、同じIMEを使った標準入力との配置一致は未確認。

10万字での実IME入力・タイプライター追従の性能差も未測定。長い一段落では文字ごとの座標計測が増える。全文DOMの描画・レイアウト負荷は残る。

縦中横・ルビ・装飾を含む変換、変換中のファイル切り替え、選択置換、ドラッグ、全ショートカット、クリップボード権限、タッチキーボード、アクセシビリティ、Microsoft IMEなどの相互運用は受け入れ検証が必要。変換下線は範囲全体の下線で、IMEの文節ごとの装飾はまだ再現していない。現行の表示・操作との完全な同等性や高速化の達成を示すものではない。

## 主な実装

- `src-tauri/src/native_ime.rs`：TSF所有、Windows入力、座標・属性、編集通知、受領確認と単体テスト。
- `src/editor/nativeIme.ts`：現在段落との同期、PM差分更新、接続ライフサイクル、試験パネル。
- `src/NativeImeQaApp.tsx`：保存しない試験文書と表示条件の切り替え。
- `scripts/run-native-ime-experiment.mjs`：別アプリ識別子での起動。
