## 工程1: 調査の結果

- 閉じ方は2つ。上の帯の閉じるボタン（`src/components/layout/WindowControls.tsx` の `appWindow.close()`）と、OS からの閉じる（Alt+F4、タスクバー）。どちらも Rust の `WindowEvent::CloseRequested` になる。
- Rust の閉じる処理（`src-tauri/src/lib.rs` の `main_window.on_window_event`）は、`CloseRequested` を受けると、保存の記録を閉じ（`save_journal::close_all()`）、窓の位置と大きさを保存し（`save_main_window_state`）、つながった子の窓（Canvas など）を閉じる。閉じるのは止めないので、そのまま窓が消える。
- 画面の側（JavaScript）には、閉じる要求を受け取る登録（`onCloseRequested`、`tauri://close-requested`）がどこにもない。
- 画面の側の遅延保存（`window.setTimeout` で待ってから書く）は、行番号は `b0b018c` の時点の `setTimeout` の行で次のとおり。どれも、待っているあいだに窓が消えると書かれない。

## 工程2: 仕組みの説明

### 言葉
- **遅延保存**: 書き換えのたびにすぐ書かず、少し待ってからまとめて書く。続けて書き換えると待ち直す。
- **閉じる要求**: 閉じるボタンや Alt+F4 で、OS から窓へ「閉じたい」と届くこと。Tauri では `CloseRequested`。止めることもできる。
- **保存の記録（journal）**: 本文の変更を、原稿を書き換える前に Rust の側へ残しておく仕組み。落ちても戻せる。

### 1. 今の流れ（閉じるボタンを押したとき）
1. 画面: `appWindow.close()` → Rust に閉じる要求が届く。
2. Rust: 保存の記録を閉じ、窓の位置を保存し、子の窓を閉じる。窓が消える。
3. 画面の側で待っていたタイマーは、実行されずに消える。

### 2. 今の挙動の癖
1. **閉じる直前の遅延保存が書かれない**（この修正の対象。見込み。工程9の前に実機で再現する）。上の表のどれも。
2. 作品を切り替える直前の 0.7 秒以内の Idea の編集が書かれない（`docs/KNOWN_ISSUES.md` の既存の項、`docs/IDEA_BUGFIX_PLAN.md`）。同じ「待っている保存を、消す前に書き切らない」形だが、きっかけが作品の切り替えで、処理の場所が違う。今回は直さない。
3. Canvas などの子の窓は、親を閉じると Rust が閉じる。子の窓の側の遅延保存も、同じく書かれない見込み。今回は確かめない。

## 工程3: 原因

閉じる要求から窓が消えるまでのあいだに、画面の側へ「待っている保存を今書いて」と頼む段がない。遅延保存はそれぞれの useEffect やフックがタイマーを持っていて、外から「今すぐ書く」を呼べる入口もない。

## 工程5: 案

### 決めてほしいこと

**1. 閉じるまでの段取り**
- **Rust が閉じるのを止めて画面に知らせ、答えか時間切れを待ってから閉じる。** 勧め。Rust は `CloseRequested` で閉じるのを止め、画面へ「閉じる前」を知らせる。画面は待っている保存を書き切ってから Rust に「書き終えた」と答える。Rust は答えを受けるか、2 秒たったら、今の閉じる処理（保存の記録・窓の位置・子の窓）をしてから窓を消す。画面が固まっていても 2 秒で閉じる。
- 画面の側で閉じる要求を受け取り（`onCloseRequested`）、書き切ってから窓を消す。手間は少ない。ただし画面が固まっている・落ちているときは閉じられなくなる（Tauri が閉じるのを止めたままになる）。Rust の今の閉じる処理は要求の時点で走るので、窓が消える時点（`Destroyed`）へ移す必要がある。
- アンカーだけ、保存する中身を Rust へすぐ送り、Rust が待って書く（閉じるときは Rust が書き切る）。アンカーは直るが、ほかの遅延保存は直らない。

**2. 書き切る範囲**
- **アンカーと、上の表の画面の側の遅延保存すべて（本文を除く）。** 勧め。原因は同じで、閉じる直前の Idea・資料のレイアウト・設定の変更も同じように失われる。保存ごとにコミットを分ける。本文は保存の記録で戻せるので、今回は書き切らない。
- アンカーだけ。仕組みは入れ、ほかの遅延保存は記録して残す。

**3. 時間切れ**
- **2 秒。** 勧め。今の保存はどれも小さな JSON の書き込みで、ふだんは 0.1 秒もかからない見込み。
- 5 秒。

### `test:ai-selection` の落ち（原因はテストの準備の競争で、今回の変更ではない）

- 落ちるのはいつも通常の表示の「TSF入力中（フォーカスは受け皿）」と「選択の外を右クリック…」の2つ。「長い範囲」の後の `drag("乙","丙")` が、右のサイドバー（プロット）の上を押している（「乙」が x=2354、サイドバーは 2100〜2400）。
- 配置を記録すると、落ちる回は設定が既定（タイプライタースクロールが入）に戻っていた。タイプライタースクロールが入だと本文の左右に 2400px の余白が付き、本文が横に流れる。「長い範囲」で `reveal` が「壬」を見せるために流し、そのあと「乙」はサイドバーの下（x≈2343）に来る。`reveal` は 0〜2400 の中なら流さないので、サイドバーに隠れたまま押す。
- 設定が戻るわけ: テストの `open` は、1回目の読み込みから 1.2 秒後に `localStorage` を消してテストの設定を書き、読み込み直す。アプリは読み込みの後 0.7 秒待ってから既定の状態を `localStorage` に書く（`src/App.tsx` のアプリ状態の保存）。この書き込みが、テストが書いた後、読み込み直しが終わる前に入ると、テストの設定を既定の状態で上書きする。読み込み直した後はタイプライタースクロールが入になる。
- 確かめたこと: `localStorage` への書き込みを、読み込み直しをまたいで記録した。通る回は、アプリの書き込み（1回目の読み込みの 1119ms）がテストの書き込み（1249ms）より前で、差は 0.13 秒しかない。テストの書き込みを 0.6 秒に早め、読み込み直しを 1.5 秒遅らせて、アプリの書き込みを必ず後にすると、同じ2つが同じ形で落ちる（「乙」x=2343、本文の左右の余白 2400px）。これは前の build（`7d5fbfb`）でも後の build（`dde032e`）でも同じだった。
- 今回の変更との関係: アプリ状態の保存は `schedulePendingSave` に移したが、待つ時間（0.7 秒）も、待ち直す条件も同じ。ブラウザでは閉じる前の知らせ（`then-before-close`）を受けないので、書き切りも走らない。1回目の読み込みでアプリが書く時刻を、前と後の build で交互に 50 回ずつ測ると、中央値は 865ms と 867ms、1.1 秒を越えた回はどちらも 3 回で、差はなかった。前の 36 回中 0 回・後の 43 回中 5 回の差は、交互に流していない回が多く、読み込みが遅い回の数の違いと見ている（テストの1回目の読み込みは、起動したばかりのブラウザで遅くなりやすい）。
- 直し方の候補（利用者が決める）: テストの `open` で、アプリが書き終えるのを待ってから消す（または読み込み直しの前に `localStorage` の書き込みを止める）。`reveal` が、右のサイドバーに隠れた文字も見えていないとみなす。どちらもテストだけの変更で、アプリは変えない。今回は直していない。
