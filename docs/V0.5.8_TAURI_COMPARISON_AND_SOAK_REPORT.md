# Then v0.5.8 Tauri実機比較・長時間安定性テストレポート

- レポート作成日: 2026-08-09
- 試験実施日: 2026-08-08
- 対象ブランチ: `codex/v0.5.8-performance`
- v0.5.8対象コミット: `7c3d9b3f9acb711233b57aa991e15d528e3e3cf9`
- v0.5.6比較コミット: `c198f6034d19b33f172921983c1743f525c0b387`
- 総合判定: **性能改善は確認。ただし、初回入力の取りこぼしと長時間編集時のメモリ増加により、現状のまま正式リリースすることは推奨しない**

## 1. 結論

v0.5.8は、特に長文で「入力してから文字数・サイドバーが最新状態になるまで」の時間を短縮している。10万字ではステータス反映のp95が50.4%、サイドバー反映のp95が57.7%短縮した。50万字でもステータス反映のp50が54.2%、サイドバー反映のp50が59.5%短縮した。25回入力中のワーキングセット増分も、50万字で約1,243MiBから約87MiBへ減少した。

一方、ProseMirrorの編集DOMそのものが更新されるまでの時間は一貫して改善していない。10万字のp50は17.2%遅く、50万字のp50は6.6%、p95は67.7%遅かった。ただし50万字の最大値はv0.5.6の426.4msに対しv0.5.8は168.6msであり、少数標本のp95だけで長文入力全体が悪化したとは断定できない。再測定が必要である。

機能回帰テストと短時間の保存整合性は合格した。全6ケースでエディター内容と保存ファイルのSHA-256が一致し、見出し数、本文文字数、ステータス、サイドバー文字数も最終的に一致した。

しかし、次の二点はリリース阻害要因である。

1. ファイルを開いた直後の最初の一文字がエディターDOMにだけ入り、アプリ状態・保存状態・サイドバーへ反映されない。二文字目で追いつくが、一文字だけ入力して終了した場合は保存されない可能性がある。
2. 2時間予定のv0.5.8耐久試験は31.4分で安全上限に達し中止した。強制GC直後のJavaScriptヒープが約21.7MiBから約1,200.5MiBへほぼ直線的に増加した。DOMノード数は約9,700～9,950で安定しており、単純なDOMリークではないが、編集履歴またはアプリ状態に関連する保持が疑われる。

したがって、v0.5.8は「改善効果を検証できた開発版」としては有効だが、現状の正式リリースは推奨しない。

## 3. Tauri実機ベンチマーク方法

各バージョンで同一内容の10,000字、100,000字、500,000字の原稿を開き、末尾へ一文字ずつ入力した。ファイルを開いた直後の初回入力挙動を独立して記録した後、25回入力し、最初の5回をウォームアップとして除外した20標本からp50、p95を算出した。

計測点は次の三段階である。

- editor: ProseMirror編集DOMの文字数が変わるまで
- status: ステータスバーの全文字数が変わるまで
- sidebar: サイドバーのファイル文字数が変わるまで

各ケースの終了時に保存し、エディター本文と保存ファイルをSHA-256で比較した。測定はWebView2のChrome DevTools Protocolを使用したため、人間のキーボード入力そのものの遅延ではなく、入力イベント後のアプリ内反映時間を示す。

## 7. 発見した副作用・問題

### 7.1 高: ファイルを開いた直後の初回入力がアプリ状態へ反映されない

10,000字、100,000字、500,000字の全ケース、両バージョンで再現した。初回の一文字入力後はProseMirror DOMだけが1文字増え、サイドバーは旧値のまま、保存状態も`status-saved`のままだった。v0.5.6ではステータス表示だけは1文字増え、v0.5.8ではステータスも旧値のままだった。

ソース確認では、ファイル読込時に`src/App.tsx`の`suppressNextEditorUpdateRef`を`true`へ設定している一方、`VerticalTextEditor`は初期内容を生成時に直接受け取るため、抑止対象となるプログラム由来の`onUpdate`が必ず発生するとは限らない。その場合、フラグが残り、最初のユーザー入力を`handleTextChange`が破棄する。

二文字目以降の通知にはProseMirror文書全体が含まれるため、その時点で最初の文字もアプリ状態へ回収される。しかし、一文字だけ入力して保存・終了した場合は、その一文字が未保存になる可能性がある。これはv0.5.8で新規に生じたとは限らず、v0.5.6にも存在する共通不具合だが、正式リリース前に修正と専用回帰テストが必要である。

### 7.2 高: 長時間の編集・Undo履歴負荷でGC後ヒープが増え続ける

v0.5.8に対して2時間の耐久試験を計画した。100,000字の主原稿へ一文字挿入してUndoする操作を750ms間隔で反復し、10回ごとにRedoと再Undo、5回ごとに保存、100回ごとに別ファイルへ往復した。毎分Chrome DevTools Protocolから強制GCを実施し、GC後のヒープとDOMノード数を採取した。

試験は31.4分、1,684反復、32回のファイル切替まで進んだ後、GC後ヒープが1,250,000,000 bytesの安全上限を超えたため中止した。

| 経過 | 反復 | GC後JSヒープ | ワーキングセット | DOMノード |
| ---: | ---: | ---: | ---: | ---: |
| 0.07分 | 1 | 21.7MiB | 462.7MiB | 9,763 |
| 5.28分 | 273 | 211.3MiB | 690.6MiB | 9,907 |
| 10.50分 | 548 | 405.2MiB | 897.8MiB | 9,857 |
| 15.73分 | 820 | 596.3MiB | 1,055.8MiB | 9,801 |
| 20.96分 | 1,090 | 783.6MiB | 1,084.9MiB | 9,941 |
| 25.12分 | 1,324 | 950.0MiB | 1,224.7MiB | 9,809 |
| 31.40分 | 1,684 | 1,200.5MiB | 1,452.4MiB | 9,929 |

DOMノード数とdocument数は安定しており、強制GC後もヒープだけが増えた。したがって、テスト側の切断済みDOM保持では説明できない。ProseMirror/Tiptap履歴、増分索引の過去文字列、React状態または別の非DOMオブジェクト保持が候補だが、この試験だけでは原因を断定できない。ヒープスナップショットの比較が必要である。

耐久試験中の反映時間はeditor p50 40.8ms / p95 58.5ms、status p50 52.4ms / p95 74.9ms、sidebar p50 80.7ms / p95 115.7msだった。メモリ増加による明瞭な応答悪化やタイムアウトは中止時点まで確認されなかった。

中止時も主原稿100,000字、補助原稿20,000字、5,000字のSHA-256はすべて開始時と一致した。これは挿入・Undo・保存が最終的に原状復帰したことを示す。データ破損で中止したのではなく、メモリ安全上限で中止した。

### 7.3 中: 500,000字で編集DOM更新p95が悪化

前述のとおりv0.5.8のeditor p95は91.7msから153.8msへ悪化した。文字数・サイドバー反映は改善しているため、増分集計とは別に、ProseMirrorのトランザクション、描画、測定ノイズのどこに差があるか切り分ける必要がある。20標本では結論が不安定なため、100～200標本程度で再測定すべきである。

### 7.4 テスト範囲不足: 自動IME composition試験は無効

CDPの`Input.imeSetComposition`をQA版v0.5.6へ直接送ったところ、QA版WebViewが黒画面になった。直ちにそのQAプロセスとハーネスを停止し、通常版Thenが起動していないこと、QAプロセスとデバッグポートが残っていないことを確認した。通常版Then、通常設定、原稿データへの影響はない。

これは通常のWindows IME操作ではなく、WebView2へDevTools Protocolでcompositionを強制注入した試験である。このため「Thenの通常IME入力で黒画面になる」とは結論できず、反対にIME互換性が合格したとも言えない。自動composition試験は無効とし、今後は実キーボードまたはWindows UI Automationを使う必要がある。同じCDP注入は再実施しない。

## 8. QAハーネス側で除外した誤差

初期の高負荷耐久試験でDOMノード数とヒープが急増したが、QAハーネスがファイル切替前の`window`イベントリスナーを解除しておらず、切断済みDOMを保持していたことが判明した。ハーネスの`disconnect`でroot/windowリスナーを解除するよう修正し、以後はGC後DOMノード数が約9,700～9,950で安定した。

この修正前に得た39分間のメモリ値はアプリ評価から除外した。修正後の31.4分試験で観測した非DOMヒープ増加のみを有効な結果として扱う。ハーネス起因の現象と製品起因の可能性がある現象を混同しないためである。

## 10. リリース判断と次の試験

正式リリース前の必須条件は次のとおりである。

1. 初回入力抑止を、ユーザー入力を識別して破棄しない方式へ修正し、「一文字入力して即保存・終了」のTauri回帰テストを追加する。
2. 10万字原稿で編集・Undoを続けた際のヒープスナップショットを開始時、5分、15分で比較し、保持型と保持経路を特定する。
3. メモリ修正後に同じ条件で2時間を完走し、GC後ヒープが定常化すること、3ファイルのSHA-256が一致することを確認する。
4. 50万字editor遅延を100～200標本で再測定する。
5. 実際のWindows IMEで、変換開始・更新・確定・取消・長文変換を手動またはUI Automationで確認する。

短時間の性能改善と機能同値性は十分に確認できたが、長時間安定性試験は未完走である。v0.5.8を破棄する必要があるとまでは判断しないが、上記二つの高重要度問題を解消せずに正式版へ昇格させるべきではない。
