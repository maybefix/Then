# 段落差分計測QA版：入力処理の性能比較

2026-10-10。**段落の再計測削減とJavaScript処理時間の短縮は確認できたが、入力全体の安定した高速化は認定しない。** メインスレッドの処理負荷と次フレームまでの遅延には改善・悪化が混在し、ページ表示の実行間変動も大きかった。採用保留を継続する。

先にインストール済みThen 0.6.6そのものでも、非表示コメントによる184pxのページ開始位置不一致を再現した。元の設定ファイルは復元済み。[原因とインストール済みビルドの確認記録](PARAGRAPH_FLOW_PAGE_OFFSET_DIAGNOSIS_2026-10-10.md)を参照。この既存問題の修正・配布はしていない。

## 比較条件

- 変更前 `before-dist` と統合QA版 `after-dist`。診断用ビルドは使わず、変更前のmain JavaScriptはインストール済み0.6.6とSHA-256が一致。
- 隔離したheadless Edge `154.0.4258.62`、画面1600×1000。各実行で新しいブラウザプロファイルを使用。
- 同じ決定的原稿、初期102,185文字・2,139段落。見出し、会話、ルビ、太字、空段落を含む。ライブラリ・原稿・関連ファイルはメモリ上のmock backendを使用し、本文のAST・文字数・サイドバー更新も通常のフロントエンド経路を動かした。
- タイプライタースクロール、行番号、現在行ハイライト、改行記号、空白を含める文字数設定を有効化。縦書き／横書き×連続／ページ表示。
- 文書中央で1文字入力、続いて段落分割。操作ごとに12回ウォームアップし、別の24回を測定。段落分割はProseMirrorのEnterキーマップを使用。
- 各条件3反復。実行順は変更前→QA、QA→変更前、変更前→QA。24実行、48測定区間、計1,152入力（別に576回のウォームアップ）。
- 設定・初期読み込み・ウォームアップ・全文照合を時間に含めない。入力後の非同期処理と最後の800msの待機区間は含める。geometry APIのラッパー、CPU profiler、traceは付けない。

既存問題が発生する非表示コメントはこの性能原稿には含まれない。その問題を含む機能検証は別に記録している。本比較は統合した入力処理のブラウザ測定であり、ネイティブWebView2・OSのIME経路・初回起動費用の性能測定ではない。

## メインスレッドの処理負荷

CDP `Performance.getMetrics` の `threadTicks` を使用。表は各測定区間の `TaskDuration` 差分を24入力で割った値の、3反復の中央値（ms/入力）。変化率は「QAの中央値÷変更前の中央値−1」。正は増加、負は短縮。

| 方向・表示 | 操作 | 変更前 | QA | 中央値の変化 |
| --- | --- | ---: | ---: | ---: |
| 縦・連続 | 1文字入力 | 164.5 | 166.3 | +1.1% |
| 横・連続 | 1文字入力 | 155.0 | 174.6 | +12.7% |
| 縦・ページ | 1文字入力 | 169.9 | 167.4 | -1.4% |
| 横・ページ | 1文字入力 | 173.9 | 165.6 | -4.8% |
| 縦・連続 | 段落分割 | 318.0 | 310.1 | -2.5% |
| 横・連続 | 段落分割 | 303.4 | 306.3 | +1.0% |
| 縦・ページ | 段落分割 | 624.2 | 593.2 | -5.0% |
| 横・ページ | 段落分割 | 633.6 | 582.6 | -8.1% |

これはrendererメインスレッドの処理指標。Web Worker等を含む全プロセスのCPU合計や、1文字が画面に表示されるまでの経過時間とは異なる。

## 削減できた部分と残る負荷

QA版の実際の段落再計測は、全反復・全表示条件で1文字入力が1操作1段落、段落分割が2段落。測定入力中の全体再計測は0回だった。

段落分割の `ScriptDuration` は中央値で約13〜32%短縮した。

| 方向・表示 | ScriptDuration 変更前→QA（ms/入力） | スタイル再計算 変更前→QA（ms/入力） |
| --- | ---: | ---: |
| 縦・連続 | 63.9 → 51.9 | 37.1 → 36.6 |
| 横・連続 | 61.0 → 53.2 | 41.8 → 42.2 |
| 縦・ページ | 137.0 → 104.5 | 381.8 → 377.3 |
| 横・ページ | 126.8 → 86.8 | 402.2 → 394.6 |

1文字入力のScriptDurationの中央値の短縮は約0.2〜9.2%。段落分割、特にページ表示ではJavaScript以外の負荷が大きい。座標の取得数が減っても、今回の入力全体の結果には同じ比率の改善は出ていない。スタイル再計算内のどの規則・更新が主因かは、この計測だけでは特定しない。

## 正しさの確認と判断

全48測定区間で、入力後の本文が期待した文字列と完全一致し、本文・サイドバーの文字数増分も一致した。QA版の24測定区間では全文実測との段落座標・ページ用計測値の差は最大0px。ページ表示のQA版では保存済みページ分割とoffsetも全文再計算に一致した。これらの照合は時間測定後に実施した。

今回の原稿条件では機能照合を通過し、差分計測自体は機能している。ただし負荷・遅延の結果は混在し、実行間変動も残るため、性能改善を理由とする採用・配布は保留する。非表示コメントの既存問題も未修正。本番へのデプロイ、インストーラー作成、インストールは実施していない。

## 保存先と再現

追加の原因確認トレースでは、QA版・縦書きページ表示の測定対象Enter 6回に対し、対象要素数52,841〜52,866の `UpdateLayoutTree` が6回発生した。各イベントの経過時間は約470〜693ms。段落再計測は同じ区間で12段落（1操作2段落）、全体再計測0回だった。局所化した段落計測と、大規模なスタイル再計算が別に存在することを直接確認した。Layoutの大きなイベントでもdirtyObjectsは21、partialLayoutはtrueであり、全文の組版・レイアウトをすべてやり直していると一括して説明するのは不正確。主な残存負荷はスタイル再計算である。

入力ごとに `verticalTypewriterEditor` のinline style変更が記録され、スタックはページ位置更新経路を通っていた。記録は `input-root-cause-trace.json` と `input-root-cause-summary.json`。トレースによる負荷が加わるため、この追加試験の所要時間を上記の性能比較値へ混ぜない。

`artifacts/paragraph-flow-qa-2026-10-10/input-comparison/` に実行計画・比較assetのSHA-256を含む `plan.json`、24個の個別測定JSON、ログ、集計 `summary.json` を保存した。各JSONには入力ごとの同期処理・第1／第2RAF遅延の生値、CPU指標、文字列・文字数・geometry照合結果、QA版のキャッシュ統計がある。

```powershell
node scripts/compare-paragraph-flow-input.mjs
```

個別測定は `scripts/benchmark-paragraph-flow-input.mjs` が共通のブラウザ起動ハーネスを使って実行する。通常版dist・QA実行ファイル・ユーザープロファイルは本性能比較で変更していない。
