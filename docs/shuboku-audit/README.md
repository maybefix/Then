# Shubokuテーマ監査

Shuboku Light / Dark を、既存テスト、実アプリの40画面、独立したCSS状態比較から調べた。一般機能のテスト15本は通ったが、選択状態を示す見た目に明確な不具合がある。継続していたプロット検査の失敗は、実装の枠残りとは別の、テストの古い条件が原因だった。

この作業は洗い出しと監視手段の追加。テーマの配色・レイアウトや既存の失敗テストは変更していない。

## 優先度つきの確認結果

| ID | 優先度・分類 | 対象 | 問題と根拠 | 推奨する対応 |
|---|---|---|---|---|
| SHU-01 | P1・操作状態 | 明暗 | コマンドパレットの選択中と非選択で、背景・文字色・枠・outline・影がすべて同じ。実アプリの `paletteSelection.visuallyDistinct=false`。キーボードで選択を動かしても実行対象を見分けられない。 | `--accent-soft: transparent` を前提に、選択行専用の朱のマーカーなどを明示する。新しいコンポーネントにも同じ選択表現を適用する。 |
| SHU-02 | P2・選択表示 | 明暗 | テーマ選択のchecked/uncheckedの計算済みスタイルが同じ。Senの`.themeOption`の指定が、通常の選択枠とハローを消す。radio自体はopacity 0。標準テーマでは枠・ハローに差がある。 | `.themeOption:has(input:checked)`とキーボードフォーカスの表示をSen側で定義する。見える選択マークを用意する。 |
| SHU-03 | P2・可読性／共通由来 | Light | 未着手のファイル名、字数、保存状態、補助説明などに`--text-faint`が使われ、白地で約3.12:1。実画面の通常表示で20テキスト標本が4.5未満。Standardでも同系統の薄さがあるのでSen固有とはしない。 | ファイル名など主要情報を「薄い装飾」と同じトークンで描かない。共通CSSの意味づけとSen Lightの値を両方見直す。 |
| SHU-04 | P2・可読性 | Dark | バインダーの選択フィルター「すべて」（`.ideaChip.isActive`）が約3.45:1。朱文字と朱16%の塗りが重なる。 | Senでは塗りを紙面色に戻し、朱の枠・マーカーで選択を示すなど、二色の方針に合うコントラストを確保する。 |
| SHU-05 | P2・中央線 | 明暗 | 縦書きは墨24%が筆画と背景の色差を約76%に下げる。横書きはより詳細度の高い共通ルールが勝ち、`--accent-soft: transparent`となるため線が不可視。 | 縦横共通の専用トークンで線色を決め、個別の`border-color`と共通の`border-top-color`の競合をなくす。 |

| SHU-07 | P3・新UIへの適用漏れ | 明暗 | コマンドパレットは角丸10px、`0 24px 60px rgba(0,0,0,.45)`の影を維持する。Senの`.modal`などの平面化対象に`.commandPalette`が含まれない。 | パレットをSenのポップアップ表現に統合する。角丸・影をハードコードする共通コンポーネントも監視する。 |

P1は先に操作状態を回復したい項目、P2は通常利用に影響する項目、P3は外観方針の判断が必要な項目として分類した。色差保持率80%は前回の中央線監査で置いた開発用の暫定基準。4.5:1は通常文字の参考値であり、この監査だけでアプリ全体のWCAG適合を宣言するものではない。

## 根本原因

1. `--accent-soft`と`--control-hover`を透明にする一方、選択・ホバーを朱の罫線に置き換える対象が一部の既存クラスだけになっている。後から追加されたコマンドパレットやテーマ選択の状態表示が抜け落ちる。
2. Sen固有CSSだけを読むと「影・グラデーションなし」に見えるが、その後に読み込む共通ダークルールと、コンポーネントの固定値が方針を上書きする。
3. 既存のテーマテストはCSSの正規表現が中心で、現在のDOMの選択状態・計算済みスタイルを保証していない。古いクラスの要求は誤検知を生み、実際の選択表示の消失は検出できていない。

## 不具合と断定しなかった項目

- **選択行の3pxずれ**: 簡略化したCSSフィクスチャでは3px動くが、実アプリでファイルを開いた比較ではLight/Darkとも0px。確定不具合から除き、構造変更時の監視候補とした。
- **プロット入力のフォーカス枠なし**: 題名・本文はフォーカス前後とも枠/影/outlineがない。実際にはテキストキャレットがあるため、これだけで操作不能や違反とはしない。見え方の改善候補として残す。
- **朱と墨に状態色を集約すること**: 執/推/完などの記号や文言で状態も区別しているため、二色に寄せる方針そのものは不具合としない。
- **プロット面の枠残り**: 現行の表示では再現しなかった。古いテストのエラーメッセージを、枠が残る証拠として扱わない。

## 監視コマンド

```powershell
npm run audit:shuboku
npm run audit:shuboku -- --check
npm run audit:shuboku:browser
npm run audit:shuboku:tests
```

`audit:shuboku`は状態表示・平面処理・プロットの枠・文字コントラストの測定を保存する。`--check`は確認できた契約違反がある場合に終了コード1。現状は不具合を検出するため1を返す。実画面監査と一般テストは別コマンドなので、短いCSS検査が通るだけで全機能を合格扱いにしない。

推奨する修正順は、パレットとテーマ選択の状態表示 → 読める情報色とバインダーの選択チップ → 中央線の統一 → 共通ダーク処理とパレット外観の方針整理 → 古い正規表現検査の置換。修正後はこの同じ測定と画像で再確認する。

## 確認範囲

実画面は、Senの明暗で各17状態（通常縦書き、ファイルを開く、テーマ選択、横書き、縦横ページ表示、原稿用紙、UI 150%、プロット入力、バインダー、校正、プロパティ、設定、コマンドパレット、本文検索、コンテキストメニュー、集中表示）を確認し、標準テーマ2種類で各3状態を比較した。架空の原稿・メモとメモリ内IPCを使用。

別窓Canvas/Export、プラグイン、PDF/画像カード、全設定タブ、全フォント・全倍率、OSの高コントラスト設定、実ファイルへの保存結果は今回の視覚監査の範囲に含めない。一般テストの成功はこれらの視覚確認の代用にはしない。

参考: [W3C: Contrast Minimum](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)。文字色と背景色による参考コントラスト値の説明。
