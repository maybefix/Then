### 気づいた点

1. **リンクを読む処理は、今どこにもない。** `@[[…]]` を扱うのは移行の Rust（`idea_migration.rs`・`plot_migration`）だけで、エディタは `@[[…]]` も `[[…]]` も特別に扱わない（KNOWN_ISSUES 2026-11-14 の項）。`[[名前]]` の記法は 3-2 で入る。3-1 で作るのは、読む処理と索引、書き換えの処理になる。
2. **`@[[パス]]` は、移行で作ったノートにある。** 見本データでは `@[[第一章/a.md]]`・`@[[.then/references/imports/港の写真.png]]` の形で、パスは作品のフォルダからの相対、区切りは `/`。1-6 の「プロット（移行）」と 2-4 の Idea から作ったノートに入る。画像・PDF を指すものもある（2-5 で `<素材フォルダ>/資料/…` に書き換え済み）。
3. **手元の作品（`Documents/Books` の7作品、2026-11-15 に読むだけで数えた）には、本文の `@[[` も `[[` も0件。** 最大はテスト_snapshot検証用の20ファイル・約23万字。書き換えで既存の文章が変わる心配は、今の手元のデータにはない。
4. **全ファイルの読み込みは、今すでに2回走っている。** ファイル一覧（Rust）が txt・md を全部読んでハッシュを取り、検索の索引（JS）がもう一度全部を `read_text_file` で読む。どちらも作品を開いたときだけでなく、改名・移動・作成・削除で一覧が変わるたびに走る。リンク索引をファイルに残しても、この2回は減らない（減らすには検索の索引もファイルに残す必要があり、3-1 の範囲の外）。リンク索引を残すことで得られるのは、作品を開いた直後から索引がそろっていること（リンク元の数が、全部読み終わるまで欠けない）と、読み直しが変わったファイルだけで済むこと。
5. **アプリに戻ったときに、ファイルの一覧も本文も読み直していない。** ほかのアプリで足したファイルは、次に一覧が変わるまでバインダーに出ず、検索の索引も古いまま（今の癖 Q1）。3.3 の 3.（戻ったときに更新日時を見る）は、リンク索引の分だけ新しく作ることになる。
6. **プロジェクト全体の置換が、本文の書き換えの手本になる。** 開いていないファイルはハッシュを比べてから書き、開いているタブは本文を差し替える。改名での書き換えも同じ作法に揃えられる。ただし、開いている（表に出ている）タブは本文をまるごと差し替えるので、カーソルが先頭に戻る見込み（今の癖 Q2。コードからの見込みで、工程9で確かめる）。

## 工程2: 仕組みの説明

### 言葉

| 言葉 | 意味 |
|---|---|
| リンク | 本文やフロントマターに書いた、別のファイルを指す印。2種類ある |
| パスのリンク `@[[パス]]` | 作品のフォルダからの相対パスで指す。移行で作ったノートにある。画像・PDF も指せる |
| 名前のリンク `[[名前]]` | ファイル名（拡張子を除く）で指す。Obsidian と同じ書き方。`[[名前|表示]]`・`[[名前#見出し]]` も同じ行き先。同じ名前が2つあるときだけ `[[人物/汐見]]` と素材フォルダからのパスを付ける（3.5b）。3-2 で書けるようになり、3-3 でフロントマターの `materials` に入る |
| リンク索引 | ファイルごとに「どこへリンクしているか」を並べた表。逆引き（リンク元）は表から作る |
| 行き先のないリンク | 指しているファイルがないリンク。削除したとき、まだないノートを書いたときに生まれる |
| 解決 | リンクの文字から、指しているファイルを決めること |

### 1. データの形（案）

ファイル1本ごとに次を持つ。

```
{ path, modifiedAt, size, links: [{ kind: "path" | "name", raw, target, from, to }] }
```

- `raw` はリンクの中の文字（`第一章/a.md`、`汐見`、`人物/汐見`）。`from`・`to` は本文の中の位置（書き換えに使う）。
- 解決した行き先（ファイルのパス、または「なし」）はファイルに残さず、読み込んだあとにファイルの一覧から毎回決める。一覧が変わるたび（改名・削除・復元）に行き先が付け直されるので、削除で「行き先のないリンク」になり、ゴミ箱から戻すと元に戻る。
- 読む範囲（3.2 に揃える）:
  - パスのリンク `@[[…]]`: すべてのファイルのすべての行（決めてほしいこと 1）。
  - 名前のリンク `[[…]]`: ノート（`role: "material"`）は本文のすべての行。原稿は `//` で始まるコメント行だけ（[COMMENT_OUT_SPEC.md](COMMENT_OUT_SPEC.md) の 1.1。行頭の空白のあと `//`。`\//` は本文）。
  - どちらのファイルも、フロントマターの中の `[[…]]`（3-3 の `materials`）。
  - `@[[` で始まるものは名前のリンクとして数えない。

### 2. 利用者の操作と内部の処理（案）

| 操作 | 内部で起きること |
|---|---|
| 作品を開く | Rust が残しておいた索引を読み、一覧の各ファイルの更新日時と大きさを比べて、違うものと新しいものだけを読み直す。消えたファイルの分は外す。結果を書き戻し、画面へ渡す。検索の索引とは別に、裏で動く |
| 打つ | 何もしない |
| 保存（自動保存を含む） | 保存が終わったファイル1本の中身からリンクを読み直す。リンクが前と同じなら画面の state は変えない（描き直しを起こさない） |
| ほかのアプリで直して Then に戻る | 戻ったときに、Rust が作品の txt・md の更新日時と大きさだけを見て、違うものを読み直す（中身は読まない）。変わったものがなければ何もしない |
| 改名（ファイル・フォルダ） | 索引から、そのファイル（フォルダならその中のファイル）を指すリンクを探し、新しい名前・パスに書き換える。開いていないファイルは Rust が書く。開いているタブは画面側で本文を書き換える（工程5の 5-4）。通知は「「汐見」をリネームし、3ファイルのリンクを書き換えました」（書き換えがなければ今の通知のまま） |
| 移動 | パスのリンクを新しいパスに書き換える。名前のリンクは、名前が変わらないので書き換えない（同じ名前が増えて行き先が決まらなくなるときは決めてほしいこと 4） |
| 削除 | 何も書き換えない。指していたリンクは行き先のないリンクになる |
| ゴミ箱から戻す・チェックポイントから戻す | 一覧が変わるので、行き先が付け直される。戻したファイルの中身は更新日時で読み直す |

### 3. 保存

- 保存先: 決めてほしいこと 5。勧めはアプリのデータフォルダ（`<app_local_data>/link-index/<作品パスのハッシュ>.json`）。作品フォルダには何も足さない。
- 書くとき: 作品を開いて読み直しが終わったとき、保存で変わったとき、戻ったときに変わったとき。小さいので丸ごと書き直す（`atomic_file.rs` の書き方）。
- 壊れていた・形が古いときは、捨てて全部読み直す。索引は作り直せるものなので、失っても困らない。

### 4. ほかの機能との関係
