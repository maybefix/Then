# 全文同期・太字の処理内訳

2026-10-10。前の説明は、処理全体の時間差から「正しい装飾を保持する費用」と説明していたが、増加の原因を内訳で検証していなかった。この説明を、以下の比較と実行記録に基づく説明へ訂正する。アプリ本体は変更せず、計測スクリプトと記録を追加した。

## 同じ正しい結果を出す更新方法の比較

保存済みの修正後本番ビルドを使用。Edge、約10万文字・2,139段落、縦書き、タイプライター・行番号・現在行・改行記号を有効。各操作の前にページを初期化し、同じ生成原稿の同じ段落へ移動する。一段落の末尾に「追」を1文字追加し、元の位置へカーソルを戻す。

- 全文同期：文書をJSONへ変換し、一文字を追加して`setContent`する。
- 範囲更新：同じ位置に`tr.insertText`で一文字を挿入する。

両方とも装飾を保持する修正後の実装で測定した。3回、各10操作、先頭2操作を時間集計から除外。各回の中央値をさらに3回の中央値で集計した。CPUプロファイラー・幾何計測のラッパーは、この性能比較では無効。

| 指標 | 全文同期 | 範囲更新 |
| --- | ---: | ---: |
| 同期呼び出し | 62.8ms | 13.0ms |
| 操作から2回目のRAFまで | 214.4ms | 97.1ms |
| スクリプト時間（CDP） | 53.0ms | 43.3ms |
| スタイル計算（CDP） | 26.86ms | 0.28ms |
| レイアウト（CDP） | 18.46ms | 4.89ms |

| スタイル計算回数 | 6回 | 2回 |
| 最終段落装飾の欠落 | 0 | 0 |

2回目のRAFまでの時間は3回全てで短縮（214.4→108.4、237.1→86.7、186.1→97.1ms）。画面への厳密な提示時刻ではない。CDPのCPU指標は呼び出し直前から評価結果を取得する直後までで、RAF待ち時間とは集計区間・時間の種類が違うため、表の値を足して待ち時間の内訳にはしない。

別の診断実行では、3回の追加後の文書JSON・選択JSON・全装飾の位置と属性をSHA-256で照合した。全文同期と範囲更新は3項目全て一致した。本文と選択だけを一致と判定して、表示処理の欠落を見逃す比較ではない。最終スクリプトは各追加後の全文も期待値と比較し、実行末尾で二つの方法の指紋の一致を検査する。

**この一文字変更で増えた時間の一部は、全文置換という更新方法による。正しい結果を保つ別の経路で、スタイル計算とレイアウト、待ち時間を減らせた。増加の全てを安定性の必然的な費用と説明するのは誤り。**

## 実行記録で確認した処理

原因を追う診断実行は性能比較から分離した。ソースマップ付き本番ビルド、CPUサンプリング250μs、Chromiumのタイムライントレース、1msを超えた幾何読み取りの呼び出し元を採取した。計測自体の負荷があるため、以下の絶対時間を上表へ混ぜない。

全文同期では、スタイル計算・レイアウトに加えて`PrePaint`が約40.1ms/操作を使い、範囲更新では約1.5msだった。描画する箇所を準備するブラウザの処理でも差が出ている。合成へ渡す`Commit`も全文同期44.5ms、範囲更新28.7msを記録した。内部のどの無効化規則が`PrePaint`・`Commit`の差を起こしたかまでは分解していない。

アプリ側では、行番号・現在行の`renderVisualLines`が重い。CPUサンプリングの子処理を含む時間で、全文同期61.0ms、太字40.6ms、範囲更新33.9ms/操作。ソースの3932行からの処理で、文書や装飾集合が変わると3966行から全段落を走査し、3983行からキャッシュ済み断片の座標も組み立て直す。断片を取得し直さない段落にもこの集計は実行される。太字・範囲更新にも残る負荷として、実行サンプルとソースが一致した。

全文同期の同期区間には、ProseMirrorの`selectionToDOM`→DOMの`collapse`が約34.0ms/操作を占めるCPUサンプルもあった。アプリの`prepareImeLayoutTarget`（4287行）の`getBoundingClientRect`も、各操作で6.5〜9.3msを使った。本文更新後、選択やIMEのための位置を読む経路でブラウザ処理が走っている。

トレースの主スレッド区間は、入れ子を二重加算せず、スタイル・レイアウト・描画準備・描画・Commitをスクリプト実行の区間から分離した。ただし「スクリプト」区間には、別のイベントでタグ付けされないDOM APIのネイティブ処理も含む。CPUサンプリングの関数別時間は子処理を含める場合があり、上記の各関数の時間を合計しない。

## 太字と旧版比較の扱い

太字も操作開始時に原稿を初期化した。修正後の独立した太字操作は、同期呼び出し20.3ms、2回目のRAFまで121.2msが3回の中央値だった。全文同期の後に太字を測定した以前の175.8msとは測定手順が違うため、アプリが再度高速化された値として扱わない。

旧版も比較したが、操作の繰り返しで2,135段落の装飾が消えた。各シナリオの開始時は装飾が正しいが、2回のウォームアップ後は既に不正な表示状態である。旧版の安い時間と修正後の時間の差を「安定性の費用」と認定する根拠には使わない。

今回、更新経路によって避けられる負荷と、修正後にも残る行番号集計・描画処理を区別できた。全文同期・太字に残る全ての負荷の因果関係を解明した、あるいはIMEも解消した、という判定ではない。
