# タイプライター・効率化の副作用調査

> 以下は修正前の調査記録。後続の実装・差分一致試験・修正前後の性能比較は [装飾更新の実現性・性能検証](DECORATION_MAPPING_VALIDATION_2026-10-10.md) に記録する。当初ここに記載した「全文置換時の全再構築」は採用せず、変更のない段落の装飾保持と範囲更新を検証した。

2026-10-10。対象は現在の作業コピー（HEAD `3ea1ad0` と、調査開始時に存在した未コミットのタイプライター修正版）。実際に起動中のThen／インストール済みWebView2を直接検証した結果ではない。

## 判定

**本文破損は今回の確認範囲で再現しなかった。ただし、昨日の装飾差分更新には表示の副作用がある。** 本文全体を更新する操作で無関係な段落の見出し・太字などの装飾が消える問題と、空行のUndo／Redoで段落装飾が消える問題を、本番ビルドのEdgeで確認した。

タイプライタースクロール自体は、縦書き・横書きで最終位置、選択の維持、手動ホイール・ドラッグ開始時の停止が一致した。長文IMEの重さは残る。副作用のない状態と断定できる結果ではない。

本調査で追加したのは検証スクリプト・結果JSON・この記録。アプリの実装、原稿、インストーラーは変更していない。調査前からあった未コミットの修正も保持した。

## 1. 本文全体の更新で、無関係な段落の装飾が消える（優先度高）

`src/VerticalTextEditor.tsx:3269` の `replaceRange` は、一部の置換でも `setContent(textToDoc(next), false)` で文書全体を置き換える。太字・圏点・見出し設定、右クリックの切り取り／貼り付け、校正候補の適用などがこの経路を使う（`src/App.tsx:6021`, `6171`, `6195`, `9632`）。全操作を個別にUIで実行したわけではないが、同じ経路を呼ぶことをコードで確認した。

再現は、見出しと太字段落を交互に12段落作り、7段落目だけを変えた文書を `setContent` で反映し、選択を戻す操作。実ブラウザで、変更していない2〜5段落目・9〜11段落目から `pm-line`、見出しクラス、太字や記号を隠すspanが消えた。`**太字**` や `# 見出し` が通常の文字として露出する。本文文字列は維持されている。

原因は `patchWindowDecos`（`src/VerticalTextEditor.tsx:1624`）。全文置換の写像で装飾が失われても、再生成の対象はテキスト差分・隣接行・現在行などに限られる。変更のない段落が対象に入らない。見出しサイズなども変わるため、折り返しやスクロール位置に波及する可能性があるが、その二次影響の量は未計測。

修正候補は、全文置換のように写像の影響範囲がテキスト差分を越える場合に全再構築すること。日常の1文字入力に対する差分更新は維持できる。

## 2. 連続空行のUndo／Redoで段落装飾が抜ける（優先度中）

最小原稿は `a\n\n\nb`。

1. 最初の空段落でEnter。
2. `a` の段落へカーソル移動。
3. Undo。
4. 再び `a` の段落へカーソル移動。
5. Redo。

実際のEnterキー処理と履歴コマンドで、最初の空段落から `pm-line blank` が消えた。Undo／Redo後の本文は正しい。この最小例では段落寸法も同じだったため、直ちに目立つ見た目の崩れが出るとは限らない。`blank` は空段落の最小幅／高さに関わるため、表示状態の不一致として修正対象にするのが妥当。

同じ内容の空段落が並ぶと、内容比較による差分位置と、写像で装飾が失われた位置が一致しない。差分と隣接行だけを再生成する方法では漏れる。こちらも差分だけでなく写像の影響範囲を考慮するか、安全な全再構築へ戻す条件が必要。

## 確認できた範囲

- 本番の差分更新を有効にしたモデル比較：3シード、5,027トランザクション。IME、ルビ、太字、表、コード、コメント、複数段落置換、段落分割／結合、複数ステップを含む。本文とUTF-16位置の比較は一致。装飾不一致は最小例2件とランダム操作中5件。装飾不一致の後だけ全再構築を基準に戻し、同じ欠けの持ち越しを重複計上しない。
- 本番Edge：上記2件のDOMでの再現を確認。初回のフォーカス試験は、別の入力欄が存在しない場合にも成功扱いになっていたため根拠から除外する。後続の検証では実際の検索入力欄を開き、本文へ戻した際の範囲選択維持を確認した。
- 既存の関連テスト18本は成功。タイプライター4本、Idea入力欄、性能、本文差分、非同期／同期リスク、選択計数、表示範囲、IME表示行、位置復元、ページ復旧、表IME、表移動、コメント、コード、Idea UI。
- `npm run build` 成功。既存のバンドルサイズ警告あり。
- プラグイン基盤テストは通知の重なり順の正規表現で失敗。テストは `z-index: 7` を期待するが、HEADでも現在でもCSSは `11`。今回の差分に由来する失敗ではない。他のプラグイン処理をすべて検証済みとする根拠にはしない。

## スクロールと残る負荷

本番Edge、1600×1000、DPR 1、CPU制限なし、模擬ライブラリ。文字数はベンチマークの指定値で、生成原稿の実際の長さには多少の上振れがある。各条件1回であり、厳密な修正前後比較ではない。

| 条件 | フレーム間隔95％点 | 最大 | 最終中央誤差 |
| --- | ---: | ---: | ---: |
| 約10万文字・縦書き・改行20回・行番号／現在行／改行記号あり | 178.7ms | 216.4ms | 0.41px |
| 約10万文字・縦書き・IME確定15回・同じ表示補助あり | 960.1ms | 1038.8ms | 0.19px |
| 約3万文字・横書き・段落移動15回・同じ表示補助あり | 15.4ms | 42.6ms | 0.22px |

いずれも本文・スクロール前後の選択が一致し、入力を行った条件ではUndo／Redoの本文復元も一致。ホイール／ドラッグ開始後の勝手な追従もなかった。行番号と現在行の位置は、入力・リサイズ・フォント変更後のキャッシュなし再計測に対して0.5px以内。

約10万文字のIME試験では最大81pxの1フレーム移動も観測した。短い原稿で滑らかでも、長文・多くの表示補助・連続IME確定では停止や大きな移動が残り得る。この結果だけで「昨日より悪化した」とは判断しない。Windowsの候補ウィンドウを伴う実IME操作、インストール済みWebView2、長時間連続使用は未確認。
