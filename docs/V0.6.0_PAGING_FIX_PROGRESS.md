## 案1: 内容アンカーによる表示位置復元（バグ1）

ページ寸法が変わると、スクロール量（px）から現在ページを割り出す方式では無関係なページへ落ち、ホスト位置とビューポートが食い違って白紙ページが見えていた。

- `pagedAnchorPosRef` に「現在ページ先頭の文書位置」を記録する。記録は `requestPagedScrollSettle` の安定確定時（`capturePagedAnchor`）。縦書きはページ右上、横書きは左上を `posAtCoords` で引く。
- `syncPageMetrics` のレイアウト差分検出ブロックから `requestPagedAnchorRestore` を呼ぶ。初回計測（`DEFAULT_PAGE_LAYOUT` からの遷移）は除外する。
- `requestPagedAnchorRestore` は、アンカーが属するページへ、目標ページと実スクロール位置が一致するまで最大12フレーム追従する。React側のページ面サイズ更新が遅れて総ページ数が変わるため、1回のスクロールでは確定しない。
- 復元中に `capturePagedAnchor` が途中経過を新しいアンカーとして記録しないようガードしている。

ウィンドウリサイズ・ペイン開閉・UI表示倍率・ページ送り方向切替はすべてこの1箇所を通るため一括で解消される。

**検証**: 縦書き縦送りで10ページ目（第045段落）表示中に1280×720→900×560へ縮小し、第045段落を含む45/176ページへ復元。1100×720へ戻す往復でもアンカー段落を維持。横書き横送りでも950×620へのリサイズでアンカー第045段落を維持（15/50ページ）。いずれもホストとビューポートの重なりが正で、白紙状態は発生しない。

## 案2: 文字設定変更でのページ再同期（バグ2）

ページ表示中の `.pm-root` はCSSで寸法固定されているため、フォント変更ではResizeObserverが発火せず、総ページ数が古いまま後半ページへ到達できなくなっていた。

- `VerticalTextEditorProps` に `textLayoutSignature: string` を追加。App側でフォント・見出しフォント設定・文字サイズ・行間・文字表示幅（縦横）を `|` 連結して渡す。
- 同期エフェクトを2つに分割した。`text` のみのものと、`editorDisplayMode` / `pageFlowDirection` / `writingMode` / `textLayoutSignature` で案1の復元まで行うもの。初回マウントは同期のみ（初期ビューポート復元との競合回避）。
- `handleFontLoadingDone` にも復元を追加し、Webフォント読込完了をカバーした。

**検証**: 縦書きで文字サイズ15→21pxにして総ページが即座に45へ更新（Rangeのunion寸法からの実測期待値45と一致）、アンカー段落も維持。横書きで15→22pxでも91ページへ更新され期待値と一致。

## 案3: composition中のページ追従（バグ3）

変換中テキストがページ境界を越えると、確定まで画面外のまま入力が見えなかった。

- `handleCompositionUpdate` で、キャレットが表示域外に出た場合のみ断片表示（CSS変数）を切り替えて追従する。DOMツリーに触れないためcomposition状態は壊れない。
- **座標はDOM選択（`window.getSelection()` のrange矩形）から読む。** ProseMirrorの `state.selection` はcomposition中にDOM実キャレットより遅れるため、`coordsAtPos` では機能しなかった（実装途中で実測により判明）。
- **表示域に入るまで最大8フレーム追従する。** 断片位置の再正規化は1フレームにつき1ページ分しか進まないため、1回の補正では足りないことを実測で確認した（6ページ目から2ページ分の追従が必要なケース）。

**検証**: 6ページ目最終段落の末尾から長い読み仮名を入力し、compositionupdate 1回で6→8ページへ追従、変換中テキストが表示域内（caretTop=133）に入ることを確認。compositionend後も正常なページ・行番号へ復帰する。

## 検証ハーネス（ブラウザペインが非表示のとき必須）

`document.hidden === true` だと rAF・scrollイベント・smoothスクロールが止まり、偽バグを観測する。エディタ画面へ入った後に以下を流し込む。

```js
// rAFをsetTimeoutで代替、scrollToをauto化してscrollイベントを同期発火
if (!window.__rafShimmed) {
  window.__rafShimmed = true; window.__rafMap = new Map(); let nextId = 1e9;
  const origCancel = window.cancelAnimationFrame.bind(window);
  window.requestAnimationFrame = (cb) => { const id = nextId++;
    window.__rafMap.set(id, setTimeout(() => { window.__rafMap.delete(id); cb(performance.now()); }, 16)); return id; };
  window.cancelAnimationFrame = (id) => { if (window.__rafMap.has(id)) { clearTimeout(window.__rafMap.get(id)); window.__rafMap.delete(id); } else origCancel(id); };
}
if (!window.__scrollPatched) {
  window.__scrollPatched = true; const orig = Element.prototype.scrollTo;
  Element.prototype.scrollTo = function(opts) {
    if (opts && typeof opts === 'object') orig.call(this, {...opts, behavior: 'auto'}); else orig.apply(this, arguments);
    this.dispatchEvent(new Event('scroll')); };
}
```

観測は `.verticalTypewriterScroller` の scrollTop/scrollLeft、`--paged-host-y` / `--paged-fragment-y`、`.pagedEditorSheet` の枚数、ホストとビューポートの重なり、`.visibleLineNumberLayer` の行番号を同時に見る。

ブラウザモードでは起動時ポータルの「新しい原稿を始める」からエディタへ入り、本文は `ClipboardEvent('paste')` で流し込む（localStorage の `markdown` はブラウザランタイムでは復元されない）。設定モーダルのタブ切替はReactの再描画を挟むため、タブをクリックした直後の同じ評価内でそのタブのlabelを探すと失敗する。別々の呼び出しに分けること。

## 追記（2026-08-28 夜）: 最終ページで本文だけが下へずれる件の原因と修正

画面録画（開いてから最終ページまでスクロールすると、最終ページで本文だけが一瞬下へずれる）の原因を特定して直した。前回までの案1〜4はこの症状には効いていない。

### 原因

ページ枠 `.verticalTypewriterEditor` が `overflow: hidden` だった。hidden は**スクロールコンテナ**なので、

- キャレット表示（focus / ProseMirror の scrollIntoView）
- スクロールアンカリング（中の transform を動かすと、見た目を保とうとして逆方向へ補正する）

でブラウザがこの枠自身を内部スクロールする。`host.scrollTop` が付くと、その量だけ本文が段送りの transform とは無関係にずれる。

さらに `syncPageMetrics` の `verticalBaseOffset` が、この「ずれた描画位置」を `getBoundingClientRect` と `getComputedStyle().transform` から逆算して補正していた。補正を書く → アンカリングが打ち消す → 次のフレームで同じ量だけ大きい補正を書く、という自己参照ループになり、`--paged-fragment-y` だけが毎フレーム余白1つ分ずつ動いて描画は固まったままになる。ページ番号は正しいのに本文だけが余白1つ分（実測 57〜68px）下に残り、`requestPagedScrollSettle` が諦めるかスクロールが端で0にクランプされた時点で正しい位置へ飛ぶ。これが録画の症状。

実測（Tauriの実ウィンドウ、`?view=paged-open-qa`）:

| 状態 | host.scrollTop | 描画ズレ(paintedError) | 表示していた内容 |
| --- | --- | --- | --- |
| 修正前・文末にキャレット | 4565.6 → 685.6 | +57px 固定 | どのページ番号でも最終ページの本文 |
| 修正後 | 常に 0 | 0 | ページ番号どおり |

`paintAnomaly`（描画座標 − レイアウト座標）は全フレームで `-host.scrollTop` と一致しており、原因はこれ1つで説明できる。

### 修正

1. `src/App.css`: ページ表示時のページ枠を `overflow: clip` + `overflow-anchor: none` にした。clip は非スクロールなので、キャレット表示もアンカリングも枠を動かせない。キャレット表示は外側の `.verticalTypewriterScroller` に向かうため、ページ送りの仕組みと矛盾しない（文末カーソルでファイルを開くと最終ページが正しい位置で開く）。
2. `src/VerticalTextEditor.tsx`: `verticalBaseOffset` を `root.firstElementChild.offsetTop`（transform を含まないレイアウト座標）から求めるようにした。`getComputedStyle(root).transform` からの逆算をやめたので、書き込む値が次の計測に混ざる自己参照がなくなる。段送り1つ分以上の値は計測異常として捨てる。保険として、枠に内部スクロールが残っていたら 0 に戻す。

### 検証

`?view=paged-open-qa` のハーネスを更新（`host.scrollTop` / 描画とレイアウトのズレ / 表示中の行番号を毎フレーム記録し、文末で開く→先頭まで戻す→最終ページまで送る、を自動実行）。実ウィンドウ865フレームで `paintedError` `paintAnomaly` `layoutError` `host.scrollTop` すべて 0。ページ番号と表示内容も一致。

`npm run build` と回帰7系統（v060-paged-recovery / v059-visibility / v058-high-risk / v0510-ime-visual-lines / v0511-focus-mode / v0511-themes / performance）は成功。`test:v059-visibility` の断片基準に関する固定文言を新実装（レイアウト座標 + clip）に合わせて更新した。

## 追記2: ページ枠の下辺が消える件

ページ枠をスクロール領域と同じ大きさで置いていたため、`scroller.clientHeight` の丸め（実測 714.9 → 715）で枠の下辺が0.1pxだけクリップ外へ出て、下の線だけが描かれていなかった。上下は窓のふちに貼り付いた見え方にもなっていた（左右はエディタ枠の36px余白があるぶん紙らしく見えていて、上下だけ詰まっていた）。

ページ寸法をスクロール領域から外余白 20px を引いた大きさにし、面・ページ枠・ホストをその余白ぶん内側へ寄せた。スクロール量（`(index) * (ページ高 + gap)`）は変えていないので、スナップ位置がずれないよう `.pagedEditorSheet` に `scroll-margin: var(--paged-outer-margin)` を持たせている。窓が狭いとき（幅480px・高さ360px未満）は余白を0にして本文の面積を優先する。

実測（QAウィンドウ 1400×840、dpr1.25）: ページ枠はスクロール領域の四辺から上20.0 / 下19.9 / 左20 / 右20 の位置に収まり、全周が見える。ページ送りの往復（9→1→9）で描画ズレ・内部スクロールとも 0。ページ寸法が縮むぶん、同じ文章のページ数はこの窓で 8 → 9 に増える。

## 追記3: 変換中にページを2つ飛ばす件（録画 20260828-1429）

録画のタイムライン（30fps・ページ番号は画面下の表示）:

| フレーム | ページ | 画面 |
| --- | --- | --- |
| 1–49 | 15 / 18 | 変換中の「ああ…」がページ15の最終列に見えている |
| 52–58 | 16 → 17 | 2ページ進む |
| 60–109 | 17 / 18 | **変換中テキストは右上隅に4文字だけ、本文領域の外にはみ出して見える** |
| 112–409 | 16 / 18 | 戻ってくる。ここでは変換中テキストが列として読める |
| 421– | 15 / 18 | 確定・削除後 |

### 原因

変換中の前編集テキストは、WebView側で段（multicol fragment）へ分割し直されない。長い読みを打つと1本の行のままページ枠の下へはみ出し、DOMキャレットは確定後の位置より1〜2ページ先の座標を指す。`handleCompositionUpdate` はその座標のページへ追従するので、変換中テキストがほとんど見えないページ（録画では17）へ飛び、確定と同時に本来のページ（16）へ戻る、という往復になる。

追従そのものは案3で入れたもので、変換中テキストが完全に画面外へ出るのを防ぐ意図は正しい。問題は追従距離に上限がないこと。

### 修正

`compositionStartPage`（変換を始めたページ）を記録し、変換中の追従先を **開始ページ〜開始ページ+1** に制限した。1ページ分の追従は残るので「次ページへ流れた変換中テキストが見えない」バグは再発しない。飛びすぎて往復する挙動だけが消える。

### 検証の限界

`?view=paged-open-qa&scenario=ime` に合成composition（DOMのテキストノードへ直接追記して compositionupdate を投げる）を追加したが、**合成では前編集がふつうに段へ分割されるため、実IMEで起きる2ページ飛びを再現できない**（追従先は制限の有無にかかわらず 3→4 の1ページ）。したがって今回の上限は、録画から読み取った挙動に対する防御であって、合成テストで差が出るものではない。実IMEでの確認が必要。

前編集が段へ分割されない件そのもの（変換中の本文がページ枠の下へはみ出す）はエンジン側の挙動で、アプリからは直せない。確定すれば正しい位置へ収まる。

ページ送りの回帰（961フレーム）は描画ズレ・内部スクロールとも 0、枠の位置も上20.8 / 下19.5 で変化なし。
