### 原因

## コード上の原因

1. src/VerticalTextEditor.tsx:4036 の startInitialCaretSettle は、装飾とスクロール範囲が2フレーム安定すると終了する。500msは最大時間であり、500msのあいだ監視し続ける処理ではない。安定判定の extent も scrollWidth / scrollHeight だけで、clientWidth / clientHeight は含まない（4080行）。
2. src/VerticalTextEditor.tsx:5198 の visualLayoutObserver は本文rootとscrollerのサイズ変更を監視するが、キャッシュ無効化・行表示更新だけを行う。centerAnimation.invalidate() は進行中のアニメーションの測定を無効化するだけで、終了済みのアニメーションを開始しない。初期位置補正も再開しない。
3. src/VerticalTextEditor.tsx:5396 の handleResize はセンタリングを呼ぶが、window.resize のイベントにだけ接続されている。サイドバーなどにより本文欄だけが変わる場合には呼ばれない。

初期の位置合わせが先に終わり、その後に本文欄のサイズが確定する順番で発生する。上記の再現では、縦書きのスクロール量は幅変更前後で -32283 のまま残り、window.resize 通知後に -32416 へ補正される。

## 関連して見つかった経路

src/VerticalTextEditor.tsx:5407 の handleFontLoadingDone でも、連続表示の再センタリングを要求していない。5502行の document.fonts.ready からの初期補正は初期調整の許可中かつ500ms以内に限られる。

src/utils/verticalMetricFonts.ts の useVerticalMetricFontFamily は、Tauriからフォント情報を非同期取得した後、縦書き用のフォント別名へ切り替える。起動後にフォントの組版条件が変わる経路は存在するが、今回の確定した再現は本文欄の幅変更によるもので、フォント処理を添付画像の原因と断定していない。

## 修正方針

初期補正中の本文欄サイズ変更とフォント確定を、初期位置復元の処理へ接続する。カーソルを寄せる起動と、保存済みviewportを復元するタブ再訪は、それぞれの位置復元方針を維持する。ユーザーが手動スクロール・クリック・入力を始めた後は初期補正を再開しない。固定待ち時間だけを増やす変更では、2フレームの安定終了後に起きる変更を解消できない。

修正時には今回の150ms/800ms条件に加え、遅いフォント確定、タブ再訪時のviewport復元、初期補正中の手動スクロール・IME入力を回帰確認する。
