# Windowsビルドの負荷削減と実機検証

2026年11月4日、Codexデスクトップ版を開いたまま、同じWindows PCでNSISの生成、インストール、起動、メニュー操作を確認した。

Thenの画面データを埋め込む処理をRustライブラリから実行ファイル側へ移した。Cargoが作るライブラリの依存一覧から画面データが外れた。通常の最適化設定を固定してメニュー文字を加え、次に削除した。どちらも実行ファイル側のコンパイルは1回、ライブラリ側は0回。実行ファイルが参照したライブラリは同じファイルで、SHA-256と更新時刻が一致した。

| 計測項目 | 分割前のrlib版 | 分割後、メニュー文字だけ削除 |
| --- | ---: | ---: |
| フロントエンド生成からNSIS生成まで | 7分54.5秒 | 1分43.7秒 |
| rustc単体のピーク専有コミット | 2,075 MiB | 1,206 MiB |
| rustc単体のピーク物理メモリ | 1,466 MiB | 671 MiB |
| ビルド中のCドライブ空き容量の最大減少 | 662 MiB | 136 MiB |

両側はこのPC上の実測。分割前のrunはcrate-type切り替え後、分割後は既に分割済みのライブラリを再利用したrunなので、時間とディスク値はそれぞれの工程全体を比較した値。Rustコードや依存関係を変えた初回は、引き続きライブラリをコンパイルする。

最初の分割比較では、試験用PowerShellのswitchが引数区切りの扱いによって有効になり、初回が意図と異なる最適化設定になった。引数の束縛を単独で再現し、そのswitchを削除した。採用した結果は、その後に同じ設定で取り直した文字の追加・削除の2回。最適化だけを弱めた実験の専有コミットは2,047 MiBで、通常最適化の2,075 MiBと大きく変わらなかった。

Windows用ライブラリ出力をrlibに限定した。従来構成が生成したstaticlibは約129 MiBだった。通常のnpmビルド入口でCargoを1ジョブにし、Windowsセッション内の同時実行を名前付きmutexで止める。実際に候補版ビルドの最中に2本目を呼び、拒否されたことを確認した。

最終版は検証専用の製品名とデータ識別子を使い、同じPC上で直前の検証版にNSISで上書きした。同梱バイナリーとインストール先のバイナリーはSHA-256一致。実際のWebView2でメインJavaScriptがtext/javascriptで読み込まれ、執筆画面が描画され、上部メニューボタンの文字が空・アイコンは表示・クリックでメニューが開くことを確認した。最終インストーラーのSHA-256は fe0bf2e4befa04d7b6570053c90a81a9ee1ee5bb1ff80b582e33c74ad51d9363。

Codex側では、この調査で起動した補助プロセス2つを終了し、専有メモリ100,089,856バイト（約95 MiB）のプロセスが消えたことをPIDで確認した。最終ビルド中のCodex画面系は約1.9 GiBの専有メモリを使っていた。上表の減少はRustのコンパイル工程での実測である。

検証用インストールをアンインストールし、今回の一時出力と使わなくなったRust生成物を整理した。整理直前・直後でCドライブの空き容量は979,869,696バイト（約934 MiB）増えた。検証済みNSISをartifacts/build-resource-20261104に保存し、照合した。

計測と検証の詳細は windows-build-comparison.json、final-library-reuse.json、frontend-only-cargo-evidence.json、windows-qa-cleanup.json に記録した。
