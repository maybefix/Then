## 工程1: 調査の結果

行番号は 7af84f7 の時点。

- 削除の後半: `src/projectEntryActions.ts` の `trashProjectEntry`（663〜737行）。消したファイルが開いていたら、一覧の最初のテキストファイルを読み、`loadDocumentIntoEditor(document, { replaceActive: true })` を呼ぶ（713行）。
- タブの置き換え: `src/App.tsx` の `replaceActiveTabWithDocument`（1751〜1767行）。
- タブの ID はファイルのパスから作る（`src/editor/documentTabState.ts` の `createFileDocumentTab`、`id: file:<パス>`）。同じファイルなら、新しく作ったタブも前からあるタブも ID が同じになる。
- 気づいた点: `replaceActiveTabWithDocument` の「同じファイルを開いている別のタブは畳む」というコメントの処理（`tab.id === nextTab.id || tab.path !== document.path` で残す）は、ファイルのタブでは一度も畳めない。同じパスなら ID も同じなので、どのタブも1つ目の条件で残るため。

## 工程2: 仕組みの説明

### 言葉

- **作業中のタブ**（`activeTabId`）: いま本文に出ているタブの ID。
- **置き換え**（`replaceActive`）: 作業中のタブの場所に、別のファイルを入れること。保存・名前を付けて保存・チェックポイントからの復元・削除のあとに使う。
- **古い値**: React では、関数はそのときの描画の値を覚えている。同じ処理の中でタブの一覧を書き換えても、関数の中の `activeTabId` は書き換える前のまま。

### 削除のあとに起きること（確かめた。2-3 の実機確認）

| 順 | 処理 | 結果 |
|---|---|---|
| 1 | 消したファイルのタブを一覧から外す（701行） | 作業中のタブが一覧からなくなる |
| 2 | 一覧の最初のテキストファイル B を読む | |
| 3 | `replaceActiveTabWithDocument(B)` | 作業中のタブ（古い値）は一覧にないので、B の新しいタブを末尾に足す |
| 4 | 同じファイルのタブを畳む | B がすでに開いていると、前からあるタブも新しいタブも ID が同じなので両方残る |

画面では、B のタブが2つ並び、どちらも選ばれた状態で出る。B を改名して作品を切り替えて戻ると、片方が古いパス（もうないファイル）を指したまま残っていた。

前からある B のタブで書きかけ（保存していない）だった場合は、ファイルから読んだ B と書きかけの B が同じ ID で並ぶ（コードを読んでの見込み。実機では確かめていない）。

### 同じ置き換えを使うほかの操作（コードを読んでの見込み）

| 操作 | 場所 | 2つになるか |
|---|---|---|
| 名前を付けて保存で、別のタブで開いているファイルに上書きする | App.tsx 5474行 | なる。作業中のタブは一覧にあるので場所は置き換わるが、別のタブの同じファイルが残る |
| 新しいタブ（未保存）を保存して、開いているファイルと同じ名前を選ぶ | App.tsx 5439行 | なる（同じ理由） |
| チェックポイントから復元し、作業中のファイルが復元に入っていない | App.tsx 5025行 | 復元の最初のファイルがほかのタブで開いていればなる |

### 今の挙動の癖（直さないもの）

- 削除のあとに開くのは、消したファイルの近くではなく、作品の一覧の最初のテキストファイル。新しいタブは末尾に足す。
- 開く処理（`openDocumentInTab`）は、パスを大文字小文字まで同じかで探す（2026-11-14 の項）。

## 工程3: 依存関係

- 呼ぶもの: `loadDocumentIntoEditor`（`replaceActive: true` のとき）。その呼び出しは projectEntryActions.ts 713行（削除）、App.tsx 5025・5218行（復元）、5439・5474行（保存）。

## 工程5: 案

### 直し方の選択肢

**案1（勧める）: タブの置き換えそのものを直す。**
置き換えの一覧の作り方を次のようにする。

1. 作業中のタブが一覧にあれば、その場所に新しいタブを置き、同じファイルのほかのタブは畳む（パスは `isSamePath` で比べる）。
2. 作業中のタブが一覧にない（削除で外した）とき、同じファイルのタブがすでにあれば、新しく作らずにそのタブへ切り替える。書きかけはそのまま残す。
3. どちらもなければ、末尾に足す（今と同じ）。

削除のほか、保存・名前を付けて保存・復元で同じことが起きる道も一度に閉じる。描画と切り離した関数にするので、テストで直接確かめられる。

**案2: 削除の後半だけ直す。**
削除で次に開くファイルがすでにタブで開いていれば、そのタブへ切り替える。手間は一番小さいが、保存・復元の道は残る。

### 決めてほしいこと

1. 直し方: 案1（勧める。原因が置き換えの処理にあり、ほかの操作でも同じことが起きるため）／案2。
2. 削除のあと、まだ開いていないファイルを開くときのタブの場所: 今と同じ末尾（勧める。今回は2つになるのを直すだけにする）／消したタブがあった場所。

### テストの直し方と足すテスト

- 足す（新しい `scripts/test-replace-active-tab.mjs`、package.json に `test:replace-active-tab`）: 置き換えの一覧の作り方を直接動かす。
  - 削除で作業中のタブを外したあと、開いているファイルを置き換えに渡す → タブは1つ、書きかけが残る。
  - 開いていないファイル → 末尾に1つ足す。
  - 作業中のタブを、別のタブで開いているファイルで置き換える（名前を付けて保存） → 作業中の場所に1つ。
  - ふつうの保存（同じファイルで置き換える） → 一覧は変わらない。
- 期待を変える既存のテスト: なし（`test:project-entry-actions` の削除の確かめは、案1ではそのまま）。

### 進め方とコミットの分け方

1. 今は落ちるテストを書いてコミットする。
2. 置き換えの一覧の作り方を `documentTabState.ts` に移して直し、App.tsx から使う。
3. 「後」の一式、わざと不具合を入れて落ちることの確認、QA 用アプリで削除・名前を付けて保存を確かめる。

### 見込みと、今回やらないこと

- やらない: 削除のあとに開くファイルの選び方、大文字小文字の違いで2つ開ける件（`openDocumentInTab`、2026-11-14 の項）。
