## 2. Cloudflareの使い方

新規構築ではWorkers Static Assetsを第一候補にし、Astroが生成したHTML・CSS・JavaScript・画像を配信する。初版ではSSR、DB、認証、サーバー側APIを必要としない構成にする。

Cloudflareは新規プロジェクトにWorkersを推奨している。Pagesの利用終了を意味するものではないが、過去の「AstroならPages」という記事だけを根拠に選ばない。[Cloudflare Pagesの現行案内](https://developers.cloudflare.com/pages/)

Static Assetsへのリクエストは無料・無制限で、Assetsの保存にも追加料金はない。Workerスクリプトの実行は別の料金・制限になるため、静的配信だけで済むページに実行処理を挟まない。特に`run_worker_first`を不用意に有効にしない。[Static Assetsの料金と制限](https://developers.cloudflare.com/workers/static-assets/billing-and-limitations/)

推奨は無料枠での開始。静的配信が無料でも、ビルドサービスや他の機能には別の上限がある。CIを選ぶ段階で最新の条件を確認する。[Workers Buildsの料金と制限](https://developers.cloudflare.com/workers/ci-cd/builds/limits-and-pricing/)

独自ドメインの取得・更新はホスティングと別で、一般に年単位となる。ユーザーの「年払いは嫌」がドメインにも及ぶかは未確認。まずサービス付属のURLで公開準備を進め、ドメインの購入は別途判断する。[Cloudflare Registrarの登録期間](https://developers.cloudflare.com/registrar/get-started/register-domain/)

## 3. サイトの構成

推奨するURL構成は次のとおり。実際のドメインは未定。

| URL | 内容 | 実装 |
| --- | --- | --- |
| `/` | 個人サイトのホーム・制作物への入口 | Astro |
| `/about/` | 自己紹介 | AstroとMarkdown |
| `/articles/` | 記事一覧 | Astro |
| `/articles/<slug>/` | 個人記事 | Markdownから静的生成 |
| `/then/` | ThenのLP | 既存HTML・CSS・JavaScript・素材をそのまま配信 |

個人サイトから既存LPへリンクする。LPは現在のファイルをそのまま渡して使い、今回の作業でデザイン・コピー・画像を作り直さない。個人サイトの共通ヘッダーや記事レイアウトも適用しない。公開先に応じたファイル配置と必要なリンク調整だけを行う。

Astroを使う主な理由は、個人サイトのレイアウトの共通化とMarkdown記事の管理。現在のLPはすでに静的HTMLなので、Astroへ移すだけで大幅に高速化するとは考えない。[Astroのコンポーネント](https://docs.astro.build/en/basics/astro-components/)、[Content collections](https://docs.astro.build/en/guides/content-collections/)

### 個人サイトのデザイン検討

個人サイトのデザインを決める工程を、実装とは別に設ける。現在のThenのLPをそのまま使うことは、個人サイト全体の見た目が決まっていることを意味しない。個人サイトの配色や書体をThenのLPに揃えるかどうかも未決定。

最初にホームと記事ページの画面案を作り、制作物と記事への入口、文章の読みやすさを確認する。その方向性をもとに記事一覧、自己紹介、共通ナビゲーションを整える。フロントマターや記事取り込みの改修とは並行して検討できる。

| 検討対象 | 決める内容 |
| --- | --- |
| ホーム | 自己紹介、制作物、記事の配置と優先順位。ThenのLPへの入口 |
| 記事ページ | 本文の幅、書体、文字サイズ、行間、見出し、画像、コードなどの表示 |
| 共通部分 | サイト名、配色、ナビゲーション、記事一覧、自己紹介ページ |
| スマートフォン | ホームの並び方、メニュー、本文や画像の表示 |

画面案には実際に掲載する文章や代表的なMarkdownを使い、内容を入れた状態で検討する。個人サイトのデザイン作業に、既存LPの再デザインは含めない。

## 5. ライブラリと記事原稿

Thenの実際の保存構造を維持する。本文のMarkdownは作品フォルダ内にあり、`.then`にはIdea、Plot、Canvas、資料、チェックポイントなどが入る。[Thenの保存場所](C:/Users/uest/Documents/then/README.md:135)

```text
ライブラリ/
├─ .then/
├─ 開発日記/
│  ├─ .then/
│  ├─ Thenを作った話.md
│  └─ 2026年/
│     └─ 改良したところ.md
└─ 読書メモ/
   ├─ .then/
   └─ 最近読んだ本.md
```

取り込み処理は作品直下とその下のサブフォルダにあるMarkdownを扱う。ライブラリ直下にも通常の原稿がある場合は、それも扱える設計にする。サイト用の固定フォルダへ原稿を移動させる必要はない。原稿の列挙から`.then`などの管理用ディレクトリを明示的に除外する。

初版は1ファイルを1記事として扱う案。作品内の複数原稿を1記事に結合する機能は別の要件なので、自動で結合しない。作品の執筆状態と記事の公開指定も別の意味を持つため、Thenの「完成」から公開状態を推測しない。

AstroのContent collectionsは任意のローカルフォルダから読み込める。ただし、Cloudflare側のビルドからWindows上のライブラリを直接読むことはできない。原稿をビルド環境へ渡す経路が必要になる。[ローカルコンテンツの読み込み](https://docs.astro.build/en/guides/content-collections/)

### 推奨する初版の公開手順

最初はローカルで原稿の収集と静的ビルドを行う構成を推奨する。

1. Thenで既存の原稿を編集し、同じファイルのプロパティで公開情報を設定する。
2. 明示的な公開準備コマンドで、設定したライブラリから公開対象だけを収集する。
3. 一時的な生成フォルダに記事と必要な素材を出力する。このフォルダは手で編集しない。
4. Astroで個人サイトを生成し、LPを公開出力の`/then/`へ配置する。
5. ローカルのプレビューで確認し、公開コマンドでCloudflareへ配信する。

生成フォルダは原稿の管理場所を増やすためのものではない。毎回原稿から再生成し、内容の修正はThen側だけで行う。本文や記事情報の手動コピーは運用に入れない。

自動保存でサイトが公開される設計にはしない。公開指定とデプロイは分ける。Git連携を導入するときは、Cloudflareへ渡すリポジトリや生成物を決める。ライブラリ全体を公開リポジトリへ入れることを前提にしない。[Cloudflareの外部CI/CD](https://developers.cloudflare.com/workers/ci-cd/external-cicd/)

## 6. 記事のフロントマター案

記事情報は本文と同じMarkdownに保存する。以下の項目はサイト側で定義する案であり、Astroが自動的に公開判定してくれるわけではない。

```markdown
---
slug: making-then
date: 2026-10-16
publish: true
tags:
  - 開発
  - Then
---

# Thenを作った話

本文……
```

| 項目 | 推奨する扱い |
| --- | --- |
| `slug` | 公開URLを固定する識別子。原稿のファイル名やフォルダ名から独立させる |
| `date` | 掲載日。ファイルの更新日時から自動で置き換えない |
| `publish` | YAMLの真偽値`true`のときだけ公開対象。省略・`false`は対象外 |
| `tags` | 任意の文字列リスト |
| `title` | 任意の上書き用。通常は本文最初のH1を使い、なければファイル名から取得する案 |
| `description` | 任意の記事説明 |

タイトルを毎回フロントマターとH1の両方へ入力させない。記事ページでは取得したタイトルと本文H1の表示重複を避ける。公開URLの重複、必須項目の欠落、日付や真偽値の型違いは公開前にエラーとして表示する。`"true"`という文字列を真偽値と同一扱いしない。

公開用の原稿処理には、Then独自記法への対応も必要。ルビ、圏点、縦中横などを標準Markdownとしてそのまま解釈できるとは考えない。またThenの`//`コメントがサイトに露出しないようにする。URLやコードブロック内の`//`まで消すような一括置換は避け、対象記法を判別して処理する。変換を初版で支援しない記法は、診断を出して扱いを明示する。[Then独自記法](C:/Users/uest/Documents/then/docs/THEN_SYNTAX_GUIDE.md)

画像は公開対象の記事が参照するものだけを取り込む。初版で許容する参照形式と範囲を決め、相対パスを公開用URLへ書き換える。`.then`内の画像を扱う場合も、本文から明示参照された素材として限定的に解決し、管理フォルダ全体を公開しない。未対応の画像参照は黙って欠落させず、公開準備時に知らせる。

## 7. 実装の順序と確認条件

| 順序 | 作業 | 確認する結果 |
| --- | --- | --- |
| 1 | Thenのフロントマター改善 | 本文とプロパティが同じMarkdownに保存され、本文入力性能を損ねない |
| 2 | 記事取り込みと変換 | 既存の複数作品・サブフォルダから対象原稿だけを扱える |
| 3 | 個人サイトのデザイン検討 | ホームと記事ページの画面案で、構成と見た目の方向性を決める。1・2と並行して進められる |
| 4 | Astroの個人サイト実装 | 決めたデザインでホーム、制作物一覧、記事一覧、記事ページが生成される |
| 5 | 既存LPの配置 | 現在のファイルを`/then/`で配信し、素材とリンクが正しく解決する |
| 6 | Cloudflareへの公開準備 | 出力内容を確認し、ローカルと公開先で同じページが動く |

公開の確認では、記事URL、画像、LPのタブ・メニュー・画像拡大、404、狭い画面での表示を確認する。記事を非公開に変えた場合に、前回生成したHTMLが残らないことも確認する。管理データや下書きが記事一覧、RSS、検索用データ、配信ファイルに混入しないよう、すべての出力で同じ公開判定を使う。
