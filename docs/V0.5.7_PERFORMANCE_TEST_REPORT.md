# Then v0.5.7 詳細テストレポート

- 実施日: 2026-08-08
- 対象ブランチ: `codex/v0.5.7-performance`
- 対象実装起点: `59e97a3 perf: add experimental v0.5.7 incremental updates`
- 対象バージョン: `0.5.7`
- 総合判定: **合格（確認済みの初回索引競合を修正後）**

## 1. 結論

v0.5.7で導入した増分AST、プロジェクト集計、サイドバー集計、チェックポイント競合判定、キャンバスのフレーム集約について、主要な計算結果は従来の完全再構築と一致した。500回の決定的ランダム編集、最大50万字のマークアップ原稿、プロジェクト121ファイル、サイドバー24文書、スナップショット50件、ポインターイベント1,000件を検証し、データ破損・見出し欠落・文字数誤り・エクスポート破損は確認されなかった。

テスト中に、**初回プロジェクト索引中に編集中ファイルを更新すると、遅れて反映される索引バッチが最新ASTを古いASTで上書きし得る**競合を再現した。原因は通常入力の単発更新と初回索引の一括更新に鮮度判定がなかったことである。初回索引バッチ専用の鮮度ガードを追加し、現在のindexed ASTと同時刻またはそれ以前に作成されたバッチASTを拒否するよう修正した。古いバッチ拒否、同時刻拒否、より新しいバッチ受け入れの回帰テストはすべて合格している。

## 5. 性能測定

マークアップを多く含む原稿の中央1行へ1文字を追加し、増分更新と完全再構築を同一プロセス内で交互に測定した。独立した2プロセスで測定し、各プロセス内の中央値の範囲を示す。Windows上の実時間にはスケジューリングやGCによる振れがあるため、絶対時間だけでなく比率も併記する。

| 原稿サイズ | 行数 | 増分更新 | 完全再構築 | 比率 | 短縮率 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 10,000字 | 313 | 0.31〜0.48ms | 1.53〜2.58ms | 18.6〜20.0% | 80.0〜81.4% |
| 100,000字 | 3,126 | 2.88〜14.34ms | 19.95〜102.11ms | 14.0〜14.4% | 85.6〜86.0% |
| 500,000字 | 15,626 | 38.86〜73.17ms | 345.49〜571.33ms | 11.2〜12.8% | 87.2〜88.8% |

v0.5.6では編集中ASTとProject AST用に完全解析を二重実行していたため、AST経路だけを比較すると改善幅はさらに大きい。ただし、これはAST処理単体の値であり、ProseMirrorからの全文文字列化、React更新、文字数計算、DOM描画は含まない。

### 5.1 残る全文処理

v0.5.7でも一文字入力ごとに次のO(n)処理が残る。

- ProseMirror文書からプレーンテキストへの変換
- 改行正規化と行分割
- 変更範囲を探す前方・後方走査
- 文書全体のtext/semantic hash
- 見出し階層の再構築
- 全文文字数、表示文字数
- 現在キャレットまでの行番号計算
- 更新中文書のサイドバー用prefix集計

したがって「全文評価を完全に廃止」した実装ではない。高コストなMarkdownインライン解析を変更行へ限定し、同じ本文の二重解析を除いた実装である。50万字ではAST単体で38.86〜73.17msとなり、60Hzの1フレーム16.7msを超えるため、超巨大単一ファイルでは入力時の引っ掛かりが残る可能性がある。

## 7. 確認された副作用・リスク

### F-01: 初回索引バッチが最新の編集中ASTを上書きし得る（修正済み）

- 重要度: **中**
- 状態: **再現後に修正・回帰確認済み**
- データ損失: なし
- 対象: `src/App.tsx` の初回索引バッチと編集中ASTのProject AST反映

修正前の再現順序:

1. 初回索引が編集中ファイルのAST Aをバッチへ保持する。
2. バッチ反映前にユーザーが入力し、編集中AST BがProject ASTへ反映される。
3. 遅れてバッチが反映され、AST AがAST Bを上書きする。
4. 次の入力または再索引までProject ASTだけが古い状態になる。

修正前の影響:

- ファイルツリー内の見出しが一時的に古くなる。
- ファイル、フォルダ、プロジェクト文字数が一時的に古くなる。
- プロジェクト検索が編集中ファイルの最新本文を見つけない可能性がある。
- エディタ本文、保存キュー、実ファイルは別経路であり、原稿データ自体は失われない。

実装した対策:

- 通常入力などの単発更新は従来どおり常に適用する。
- 初回索引の一括更新だけ `preserveNewerIndexed` を有効にする。
- 現在のindexed ASTの `indexedAt` がバッチAST以上なら、そのバッチ要素を破棄する。
- pending→indexed、error遷移、より新しいindexed ASTは従来どおり適用する。
- 深度テストで古いバッチ、同時刻バッチ、より新しいバッチの3境界を固定する。

### F-02: 索引進捗表示が最大12件単位で進む

- 重要度: 低
- 状態: 仕様上の副作用

React state更新を12件単位へまとめたため、従来の1ファイル単位より進捗表示の粒度が粗くなる。索引結果には影響しない。

### F-03: キャンバスドラッグに最大1フレームの表示遅延が加わる

- 重要度: 低
- 状態: 仕様上の副作用

pointermoveをrequestAnimationFrameへまとめたため、60Hz環境では最大約16.7msの表示遅延が生じ得る。pointerup時にflushするため最終位置は失われない。

### F-04: 本文文字数表示はeffect経由で1回遅れて更新される

- 重要度: 低
- 状態: コード構造上の可能性、実画面で不整合は未確認

重複全文集計を除くため、`handleTextChange` 内の即時文字数更新を削除し、`editorText`変更後のeffectへ一本化した。このためReactの描画タイミングによっては、旧値が1描画だけ見える可能性がある。実画面テストでは本文・サイドバーとも最終値へ正しく更新された。

### F-05: 本番版で詳細診断ログを取得できなくなる

- 重要度: 低
- 状態: 意図した副作用

folder/heading D&D診断ログを開発ビルドだけへ限定した。本番性能とログ量は改善するが、配布版での現地調査材料は減る。必要ならユーザー設定で一時的に診断を有効化できる仕組みが別途必要となる。

## 8. 潜在リスク

### R-01: render中のref更新

`activeDocumentAstCacheRef.current` は `useMemo` の計算中に更新される。React Concurrent Renderingで破棄されたrenderのASTがrefへ残る可能性がある。次回更新時も行内容を比較するため、500回の差分テストでは結果不整合は起きなかったが、Reactのrender purityという観点ではeffectまたは専用キャッシュ層へ移す方が安全である。

### R-02: 大規模単一ファイルではフレーム予算を超える

50万字で増分AST単体が38.86〜73.17msだった。従来より大幅に速いが、エディタ全体では追加の全文処理もあるため、超巨大文書で完全に滑らかな入力を保証する値ではない。

### R-03: 初期JavaScript bundleは依然大きい

- v0.5.7 main bundle: 823.64kB、gzip 255.05kB
- Viteの500kB警告あり
- 事前評価時のv0.5.6: 約822.21kB、gzip約254.4kB

今回の追加による増加は小さいが、起動性能に対するコード分割は未対応である。

## 11. リリース判断

開発版・試験版として配布し、入力性能と実プロジェクトでの挙動を評価する用途には進められる。確認された中重要度の競合は修正済みである。正式版へ昇格する前には次を推奨する。

1. Windows WebView2で日本語IMEと実プロジェクト索引を組み合わせた確認を行う。
