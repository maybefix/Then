# 投稿用テキストエクスポート実装記録

## 2026-09-13: Phase 1

作業ブランチ: `codex/web-novel-text-export`

`WEB_NOVEL_TEXT_EXPORT_IMPLEMENTATION_PLAN.md` のPhase 1として、
`src/export/submission/` にUI・Tauriから独立した変換コアを追加した。

- ASTの行境界と空行を保持し、選択順で変換する中立モデル。
- カクヨム、なろう、プレーンのserializer。
- モノルビの個別出力と、Intl.Segmenterによるなろう傍点の書記素分割。
- 見出し除外、ファイル間区切り、末尾改行1つ、CRLF/LF変換。
- source名・行番号付きの装飾解除、未知注記、記号競合、ルビ上限、入れ子警告。
- 入力sourceとASTの不変性、および変換結果の固定値テスト。

文字数はUnicodeコードポイント単位（空白・出力記法を含む）とし、改行を1字として数える。
既定のファイル間区切りはLF3つ（本文間に空行2行）。フロントマターはホスト側で除去済みの本文を受け取る。
未知の青空文庫注記は投稿形式では原文を保持、プレーンでは除去し、いずれも警告する。
入れ子装飾は内容を推測して書き換えず、警告とともに内容を残す。

### 仕様確認

2026-09-13に計画の公式参照先を確認。
[カクヨムの記法](https://kakuyomu.jp/help/entry/notation) は計画どおり。
[なろうのルビ](https://syosetu.com/helpcenter/helppage/helppageid/42) には親文字・ルビ各10文字の上限と一部記号の制限が明記されているため、計画を補う警告とfixtureを追加した。自動分割はしない。

### 検証と次の段階

`npm run test:submission-export`、`npm run test:export`、`npm run build` を実行。
1万行のAST生成＋なろう変換は初回測定約240ms。実際のUI接続後に応答性を測定し、Worker化や再生成頻度を判断する。

この時点ではPhase 2（用途切り替え・プレビュー・設定保存・コピー）とPhase 3（Rust保存コマンド）は未実装だった。Phase 2の進捗は後述。

### 性能測定とWorker化

`npm run benchmark:submission` を追加。Node v24.16.0で、日本語本文・ルビ・傍点を含むfixtureを1回ウォームアップ後、5回測定した中央値。

| 行数 | 入力UTF-16単位数 | AST生成 | なろう変換 |
|---|---|---|---|
| 100 | 3,200 | 3.0ms | 1.4ms |
| 1,000 | 32,000 | 23.3ms | 6.4ms |
| 10,000 | 320,000 | 249.1ms | 72.3ms |

長文の同期処理が画面を止める可能性があるため、AST生成とserializerを専用Workerへ移した。
これはCPU処理を画面スレッドから移す判断であり、変換自体の高速化やブラウザ描画時間の改善を測定したものではない。

- パネルごとにWorkerを所有し、閉じると終了する。
- source配列が変わったときだけ本文を送信し、設定変更時はWorker内のASTを再利用する。
- 変換中はコピー・保存を無効にし、古い要求の結果はプレビューへ反映しない。
- Workerエラーは表示し、再試行で作り直す。Worker APIのない環境のみ同期処理へフォールバックする。
- 本文・変換結果をlocalStorageへ保存しない。
