## 2. Obsidianから参考にする範囲

ObsidianのPropertiesは、プロパティを名前・型・値で編集し、値をMarkdown先頭のYAMLに保存する。文字列、リスト、数値、チェックボックス、日付、日時、タグがあり、表示・非表示・YAMLソース表示を選べる。入れ子は通常のProperties UIでは扱わず、ソース表示を案内している。[公式Properties仕様](https://obsidian.md/help/properties)

同じプロパティ名の型をVault内で共有する設計、プロパティ間を移動できるキーボード操作、テンプレートによる項目追加も参考にする。Thenでの型共有の範囲は未決定で、ライブラリ内で共有する案と作品ごとに定義する案を比較する。異なる作品で同名の項目を使った際に、値を勝手に変換しないことを優先する。[型・テンプレート・キー操作の仕様](https://obsidian.md/help/properties)

公開されている`obsidian-api`は主にAPIの型定義で、Properties本体の実装コードではない。公式仕様、操作感、公開APIを参考にしてThen側で実装する。Obsidian内部の未公開APIに依存する設計にはしない。[Obsidian API](https://github.com/obsidianmd/obsidian-api)

## 3. 初版のUI要件

通常表示は「型のアイコンまたは選択欄／プロパティ名／値」の行形式とする。折りたたんだ状態では、有効なトップレベル項目数とエラーの有無を表示する。YAMLが未設定の原稿にも、大きな空欄や固定された記事用フォームを常時表示しない。

| 型 | 入力UI | 保存時の扱い |
| --- | --- | --- |
| 文字列 | 1行入力 | 数字や`true`に見える文字列も型を維持する |
| 数値 | 数値入力 | 数値として保存。空欄を自動で0にしない |
| 真偽値 | チェックボックス | `true`／`false`。未設定・nullを自動でfalseにしない |
| 日付 | 日付入力 | `YYYY-MM-DD`。タイムゾーン変換で日付をずらさない |
| 日時 | 日時入力 | タイムゾーン付き・なしの扱いを決め、勝手なUTC変換をしない |
| リスト | 項目の追加・削除ができる入力 | 初版は文字列リストを中心に扱い、混在型の値を壊さない |

追加時は既存キーの候補と型を選べるようにし、同一ファイル内の重複キーを防ぐ。名前変更、値変更、削除を個別に行えるようにする。型変更で情報が失われる場合は、自動で変換を確定しない。

フォーム表示とYAMLソース表示を切り替えられるようにする。複数行の文字列、入れ子、アンカーなど、フォームで扱えない構造はそのまま保持し、ソース編集へ案内する。画面に出せない項目を保存時に落とさない。

Tab／Shift+Tabで項目間を移動でき、キーと値を編集できること。追加・削除後のフォーカス位置を定め、項目を追加したらその場で入力できるようにする。Escapeや本文へ戻る操作を用意する。Undo／Redoはプロパティ操作にも必要で、本文のUndo履歴を消さない。具体的なキー割り当ては既存のショートカットと照合して決める。

件数や構文エラーは行数から推測せず、解析結果で表示する。ソース編集が一時的に不正になった場合は、入力文字列を保持してエラーを表示する。フォーム側から不正なソースを上書きしない。

## 4. 保存形式と二重管理の回避

本文とプロパティの値は、現在と同じ1つのMarkdownを保存先にする。サイト用の記事情報JSONを別途手入力させない。フォームとソース欄は同じフロントマターを編集する2つの表示方法とする。

型の選択や項目テンプレートなど、YAML値だけでは表せないUI設定は、必要に応じてThenの設定に保持してよい。ただし記事のタイトル、日付、公開指定などの値をその設定にも重複して持たせない。設定を失ってもMarkdownの本文と値を読み出せること。

日付と普通の文字列のように、YAMLの値だけでは入力UIの意図が決まらない場合がある。型の推定、明示指定、保存済みの型設定の優先順を決める。曖昧な値は文字列として扱い、推定だけで既存原稿を書き換えない。

本文変更時には、元のフロントマターの原文を保持する。プロパティ変更時には、本文の文字列を変更しない。改行、本文先頭の空行、メタデータのコメント、未知のキー、順序を不要に変更しない。BOM、LF／CRLF、空のフロントマター、閉じ区切り欠落も明示的に扱う。

YAMLを単純にJavaScriptオブジェクトへ変換して全体を再シリアライズするだけでは、コメントや書式を失う可能性がある。コメントやソース位置を保持できる構文木を使い、必要なら編集した値の範囲だけを更新する。候補は`yaml`パッケージのDocument API。採用・バージョンは実装時に決める。[yamlのDocument APIとコメントの扱い](https://eemeli.org/yaml/)

このライブラリにもコメントの再配置などの注意点がある。導入すれば完全に原文が保たれると考えず、実ファイルで確認する。扱えない構造を検出した場合は、原文を保持してソース編集へ戻す方針を取る。

不正なYAMLは、意味を解釈してフォームから保存しない。ソース編集の文字列は下書きとして保持し、既存の自動保存とどう合わせるか決める。少なくとも本文保存を止めたり、本文を古い状態へ戻したりしてはならない。明示的な区切り削除以外で、不正なブロックを本文へ移したり捨てたりしない。

## 5. 性能を守る設計要件

### 5.1 本文入力とYAML解析の分離

本文の入力、選択変更、IME、スクロールのたびにYAMLを解析しない。解析の入力はメタデータの原文だけとし、本文を渡さない。キャッシュの依存先を全Markdownにすると、本文入力で毎回再解析されるので避ける。

ファイルを開いた時点、またはメタデータの原文が変わった時点で解析する。本文だけが変わった場合は前の解析結果を再利用する。メタデータをUI上で未表示にしていても、本文変更を理由に解析結果を作り直さない。

フロントマターと本文の境界を扱う軽い処理と、YAMLの構造・型を扱う重い処理を分ける。閉じ区切りがないファイルを毎入力で全文走査する経路を新たに作らない。既存の文字列結合が直ちに不要になるわけではないが、今回の変更で全文の解析・コピー・比較を増やさない。

### 5.2 プロパティ更新と本文エディタの分離

プロパティだけを変えても、本文の`text`、本文用revision、`documentKey`は変えない。エディタを再マウントしたり、本文全置換のProseMirror transactionを発行したりしない。文字数、校正、本文AST、アウトライン、プラグインへの本文変更通知も、本文が変わらない限り更新対象にしない。

現在の`App.tsx`の状態更新・保存経路を点検し、必要に応じてメタデータ更新用の経路を分ける。単に`React.memo`を付けるだけで達成したと判断せず、revision、props、effect、transactionの発火条件を確認する。

UIの開閉に伴うレイアウト変更でも、カーソル、選択範囲、Undo履歴、スクロール位置、タイプライターの固定位置を保つ。必要なレイアウト調整と本文の再解析は区別する。

### 5.3 編集中の状態と保存の整合性

プロパティの入力中はローカルの編集状態を持ち、日本語IMEのcompositionを壊さない。重い検証や保存は入力中の毎イベントへ直結させず、確定時や短い待機後に行う。ただし保存待ちの間にファイル切り替え、タブを閉じる操作、終了があっても入力を失わないようにする。

遅延更新を使う場合は文書IDとメタデータのrevisionを持たせる。古い解析結果が別のタブへ反映されることや、メタデータ更新が新しい本文を古い本文で上書きすることを防ぐ。単一の保存内容を組み立てる際は、最新の本文と最新の確定済みメタデータを使う。

ファイル数に比例した監視・解析を入力経路へ入れない。プロパティ名の候補をライブラリから収集する場合は、バックグラウンド処理や保存済み索引を使い、入力のたびに全原稿を読み直さない。キャッシュは文書やライブラリの切り替えで解放し、無制限に増やさない。

## 6. 記事用プリセット案

汎用のProperties UIの上に、任意で適用できる項目セットを用意する。記事用の項目を全原稿に自動挿入しない。

| 項目 | 型 | 目的 |
| --- | --- | --- |
| `slug` | 文字列 | ファイル名と独立した記事URL |
| `date` | 日付 | 掲載日 |
| `publish` | 真偽値 | サイト側の公開対象指定 |
| `tags` | 文字列リスト | 記事の分類 |
| `description` | 文字列 | 任意の記事説明 |

適用時は既存の項目を上書きせず、不足分を追加する。公開指定の初期値は`false`とする案。タイトルは原則本文の最初のH1をサイト側で取得し、必要なときだけ`title`による上書きを許す。本文とプロパティの両方へタイトルを必須入力させない。

`publish`はサイト側が読む値であり、Thenでチェックを付けただけでCloudflareへアップロードする機能は今回の対象に含めない。型を付けたフォーム入力と、サイト側のスキーマ検証を両方行う。

## 7. 検証と受け入れ条件

### 保存・編集の確認

| ケース | 期待する結果 |
| --- | --- |
| 通常の本文編集 | フロントマターの原文を保持する |
| プロパティ値の編集 | 本文の文字列、選択位置、本文履歴を保持する |
| 真偽値、数値、数字に見える文字列、空欄、null | 明示した型と未設定の区別を保持する |
| リスト、複数行文字列、入れ子、コメント、アンカー | 対応範囲外も欠落させず保持し、必要ならソース編集へ案内する |
| 不正なYAML、重複キー、閉じ区切り欠落 | エラーを表示し、原文や本文を破壊しない |
| フォームとソースの切り替え | 値が食い違わず、表示変更だけでファイルを変更しない |
| BOM、LF／CRLF、本文先頭の空行、空ブロック | 未編集部分を不要に整形しない |
| 高速な本文編集とプロパティ更新、タブ切り替え | 古い非同期処理で新しい内容や他の原稿を上書きしない |
| 保存・再読み込み、Undo／Redo、IME | 内容を失わず、本文エディタの操作を妨げない |

### 性能の確認

改修前に同じ作業ツリーの状態で基準値を取得し、改修後と比較する。現在の作業ツリーには別件のテーマ変更などがあるため、比較条件を揃える。計測は同じPC、同じビルド種別、同じ表示設定で行い、ウォームアップ後に複数回実施する。

| 条件 | 確認対象 |
| --- | --- |
| 本文1万字・10万字 | 入力から描画までの時間、同期入力処理、文字数表示、メインスレッドの長い処理 |
| プロパティ0件・10件・100件 | メタデータの有無や量で本文入力が遅くならないこと |
| プロパティ欄が開／閉 | UIの表示状態による本文入力への影響 |
| 縦書き／横書き、タイプライター有効 | 入力位置、スクロール、選択、IMEの既存動作 |
| プロパティのみ連続編集 | 本文エディタの再マウント・本文置換・全文AST更新の回数 |

処理回数については、初回ロード後の本文だけの編集でYAML構造解析が0回、プロパティだけの編集で本文エディタの再マウント・本文置換・本文AST再構築が0回であることを計測する。読み込み時や実際の本文変更に必要な処理は区別して数える。

## 8. Claude Codeへの進め方

まず既存の保存・自動保存・revision・本文同期の経路を確認し、改修前の計測を残す。次にフロントマターの分離・更新・検証をUIから独立した処理として整え、原文保持と競合の検証を行う。その上で型付きProperties UIとソース切り替えを実装し、最後に記事用プリセットを追加する。

保存形式を変更する必要がある場合は、既存ファイルを一括変換せず、開いただけでは書き換えない。既存のライブラリと作品フォルダの構造は維持する。フロントマター改修のために本文エディタを置き換えたり、公開連携を本文入力経路へ組み込んだりしない。

実装完了時には、対応した型と対応外の構造、保存時の原文保持範囲、Undo／Redoと自動保存の扱い、性能比較結果、残った制約を報告する。
