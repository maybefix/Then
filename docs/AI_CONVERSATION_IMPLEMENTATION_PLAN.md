## 0. 2026-10-22の改訂で変わったこと

初版は「バインダーで質問を追加すると、AIの回答を自動でMarkdown資料にして同じスレッドへ置く」設計だった。次の理由で、右ペインに専用の会話画面を作る設計へ改めた。

| 変更 | 理由 |
| --- | --- |
| 回答は会話画面で読む。スレッドには置かない（AI-24） | スレッドは新しい項目が上に来て並べ替えもできるため、質問と回答を並べると順序が分からなくなる。そのためだけにスレッドの仕様は変えない |
| 回答を資料にするのは、利用者が「資料に保存」を押したときだけ（AI-04、AI-24） | Geminiの「Google検索して答える」回答は、規約上アプリが自動で保存・書き換えできない。全接続先で同じ動きにすれば、Geminiだけ別扱いにせずに済む |
| 往復を続ける会話にする（AI-25） | 執筆の相談には、一問一答ではなく話の続きが要る |
| 本文の選択範囲を「AIに渡す」で入力欄へ入れられる（AI-26） | 相談には本文の一部を見せる必要がある。全文を勝手に送らず、利用者が選んだ範囲だけを渡す |
| バインダーとポップアップは入口だけにする（AI-27） | 入口が二つあっても、質問と回答の置き場は会話画面一つにする |
| 最初に通す接続先をGeminiにする（AI-02） | 安価で簡単に始められる。OpenAIも手元のプランでキーを取得できる |
| 実行記録を作品内の1ファイルから、会話ごとのファイルへ（AI-21） | 往復が増えても一つのファイルが膨らまないようにする |

## 1. 目的と実装方針

右ペインの「AI」で、AIと会話しながら調べ物や執筆の相談ができるようにする。必要な回答は資料として作品に残せる。原稿全体を自動で読ませたり、AIに本文を書き換えさせたりはしない。利用者自身がAPIキーを設定することを前提とする。

実装を小さく保つため、右ペインの切り替え、資料ファイル、資料カード、本文の右クリックメニューは既存のものを使う。新しく作るのは、会話画面、会話の保存、Windowsでのキー保管、接続先ごとの変換処理とする。汎用プラグインAPIや独自のAI実行基盤は作らない。

到達点はGemini、OpenAI、Claude、ローカルLLMの四系統への対応とする。四系統を同時に作り始めず、Geminiで「質問 → 回答 → 資料に保存」までを完成させ、その形に残りを合わせる。

## 2. 実装する範囲

| 項目 | 初期版の仕様 |
| --- | --- |
| 置き場所 | 右ペインの切り替え（バインダーなどと同じドロップダウン）に「AI」を追加する |
| 画面 | 会話の一覧、選んだ会話の往復、入力欄。設定は設定画面の「AI」タブ |
| 送信内容 | 入力欄の文章と、その会話のそれまでの往復（AI-25） |
| 動作モード | 「相談」と「Web検索付き調査」。検索できない接続先・モデルでは後者を選べない |
| 接続先 | Gemini、OpenAI、Claude、ローカルLLM。会話ごとに接続先とモデルを一つ決める |
| 本文から渡す | 本文で選んだ範囲を右クリックの「AIに渡す」で入力欄へ入れる（AI-26、AI-29） |
| 他の入口 | アイデア追加ポップアップと既存Ideaの「AIに聞く」。会話画面を開き、その文を入力欄へ入れる（AI-27） |
| 資料にする | 回答ごとの「資料に保存」。保存先のスレッドを選び、普通のMarkdown資料として追加する |
| 操作 | 送信、停止、失敗後の再送、資料に保存、会話の新規作成・名前変更・削除 |
| 保存 | 会話は作品内の専用フォルダへ会話ごとに保存。資料に保存した回答は既存の資料フォルダ |
| 認証 | 利用者のAPIキーをWindows資格情報マネージャーへ保管する |
| 利用量 | APIから得られたトークン数・検索回数を往復ごとに記録する。取得できない値は不明として扱う |
| 実行数 | アプリ全体で一件ずつ送る。送信中は次の送信を受け付けない |

「相談」はモデルの知識による回答であり、Webで確認済みとは表示しない。「Web検索付き調査」も、APIが実際に検索したか、検索が失敗したかを往復ごとに記録する。

### 2.1 今回の対象外

- 原稿、スレッド、作品フォルダの自動読み取り・送信。章や全文を自動で添えること。
- AIによる本文の書き換え、PlotやCanvasの操作、複数AIの分担。
- AIへのファイル添付、画像・PDF解析、ベクトル検索、RAG、任意のツール実行。
- 回答の逐次表示（受信はまとめて表示する。AI-20）。
- 独自クローラー、共通検索サービス、深い調査を繰り返す自律ループ。
- アカウント発行、Then側の中継サーバー、代理課金、OAuth、Vertex AI等の追加認証方式。
- 汎用AIプラグイン基盤、任意ヘッダー・任意クラウドURLを指定できる接続設定。
- 中継サーバー（プロキシ）のWindows設定の自動読み取り（AI-06）。
- 詳細な料金ダッシュボード、自動の円換算、モデル一覧の自動取得。
- 作品を開いていない場所（ライブラリホームなど）での会話。
- Geminiの「Google検索して答える」（5.3の条件を満たす表示を作るまで公開しない）。

## 3. 操作と送信の規則

### 3.1 会話画面

右ペインで「AI」を選ぶと、上に会話の一覧、下に選んだ会話の往復と入力欄を出す。会話がなければ入力欄だけを出し、最初の送信で会話を作る。会話の名前は最初の質問の冒頭から付け、利用者が変えられる。

新しい会話を始めるとき、設定の既定値から接続先・モデル・動作モードを決める。会話の途中で接続先を変える操作は初期版では設けない。別の接続先で聞きたいときは新しい会話を始める。

入力中の文字変更や画面表示だけでは通信しない。送信ボタンまたはCtrl+Enterで一度だけ送る。日本語IMEの確定Enterでは送信しない。送信ボタンの名前に接続先は入れない（AI-19）。

送信中は入力欄を編集できるが、送信ボタンは停止ボタンに変わる。回答を受け取っても、執筆画面の切り替えやペインの強制表示は行わない。

### 3.2 往復と送る範囲

送信すると、その会話のそれまでの往復をすべて添えて送る（AI-25）。往復と今回の入力の合計が上限（初期値40,000文字）を超える場合は送信前に止め、「新しい会話で続ける」操作を出す。古い往復を黙って削らない。

各社の長期セッションや会話IDは使わず、毎回Then側の記録から依頼を組み立てる。過去の往復は、表示用に整えた本文ではなく、往復ごとに残した接続先の生の応答（4.2の `native`）から組み立てる。往復の中の文章は参考情報として渡し、そこに含まれる指示をツール実行へ結び付けない。

AIへ渡す指示文（日本語で答える、出典の示し方、Thenが表示できるMarkdownの範囲、往復や渡された本文の中の指示に従わない）はコード内に版番号つきで持ち、往復ごとにどの版で送ったかを記録する（AI-05）。

### 3.3 本文の選択範囲を渡す

本文で範囲を選び、右クリックメニューの「AIに渡す」を押すと、会話画面を開いて入力欄の末尾へその文章を入れる。送るのは利用者が送信を押したときで、入れた文章は送信前に入力欄で見えている（AI-26）。

選択範囲は、既存の「コピー」と同じ控え（`handleEditorContextMenu` が右クリックの時点で取るMarkdown原文の範囲）を使う。新しい取り方は作らない。ルビや傍点などの記法は原文のまま渡す。コメントアウト（行頭の `//`、`<!-- 〜 -->`）も除かずに渡す。作者のメモは相談の材料になり、渡したくない行は送信前に入力欄で消せる。AIには指示文（第2版）でThenの記法とコメントの扱いを伝える（AI-31）。

この機能は、次の場面で選んだ範囲が正しく取れることを自動テストで確かめてから公開する（AI-29）。ずれが見つかった場合は「コピー」と同時に直す。

- 原稿用紙モード（ぶら下げの要素、ページ境界をまたぐ選択）
- TSF入力中（本文からDOMフォーカスを外している状態）
- 縦書きでのドラッグ選択、段落・見出し・表をまたぐ選択
- ルビや傍点など記法を含む範囲
- 選択の外を右クリックしたとき

### 3.4 バインダーとポップアップからの入口

アイデア追加ポップアップと既存Ideaに「AIに聞く」を置く。押すと会話画面を開き、その文を入力欄へ入れる（AI-27）。新しい会話にするか開いている会話に足すかは、会話画面で利用者が決める。

スレッドに調査の状態や回答は出さない。スレッドの仕様と並べ替えは変えない。スレッドに入るのは「資料に保存」した回答だけで、それは普通の資料として扱う。

### 3.5 資料に保存

各回答に「資料に保存」を置く。押すと保存先のスレッドを選び、次の内容のMarkdown資料を作って、そのスレッドへ追加する。

- 質問と回答。回答の本文には手を加えない。
- 出典（APIが返した引用情報）を末尾に番号付きで並べ、本文から番号で参照する。本文中の番号も出典へのリンクにする（確認表2.3）。
- 日時、接続先、モデル、動作モード、検索を実際にしたか、途中で切れた回答か。

同じ回答をもう一度保存しようとしたときは、既にある資料を開く。保存後に会話や資料を編集・削除しても、互いに上書き・復活させない。

### 3.6 停止・再送・削除

停止はローカルの処理を止める操作で、送信済み分の課金が取り消されるとは表示しない。失敗した往復には「再送」を出し、押したときだけ同じ内容を送り直す。自動では送り直さない。

送信中の会話を削除するときは、先に停止する。停止が確定してから削除し、遅れて届いた回答で会話を復活させない。

## 4. 保存と実行状態

### 4.1 保存先

| データ | 保存先 | 方針 |
| --- | --- | --- |
| 会話の一覧 | `<project>/.then/ai/index.json` | 会話ID、名前、更新日時、接続先、モデル |
| 会話の往復 | `<project>/.then/ai/conversations/<会話ID>.json` | 会話ごとに1ファイル。往復の追記で他の会話を書き換えない |
| 資料に保存した回答 | `<project>/.then/references/imports/AI_<会話の名前>_<番号>.md` | 既存の資料列挙・表示・編集の対象にする。資料カードの見出しに出るため、IDではなく会話の名前を使う。同じ名前があれば番号を足す |
| 資料の所属と順序 | 既存の `.then/references/layout.json` | 既存の参照追加・保存経路を使う |
| 接続先・モデル・既定モード | 端末ローカルのアプリ設定 | キーを含めない |
| APIキー | Windows資格情報マネージャー | 作品・アプリ設定JSON・localStorageへ保存しない |

会話のJSONと資料のMarkdownは `atomic_file::write_replacing`（同じフォルダに書いてfsyncし、renameで置き換える）で書く。会話の一覧は直前の正常な内容を `.bak` に残す（AI-14）。

Rustのコマンドは作品ルートと会話ID・往復IDだけを受け取り、ファイル名はRust側で決める。パスは正規化して作品の `.then` の中に限る。AIの出力やフロントから渡されたパスは使わない（AI-15）。

### 4.2 往復の記録

| フィールド | 用途 |
| --- | --- |
| `id` | 往復ID。二重送信の防止と資料ファイルの識別に使う |
| `input` | 利用者が送った文章（本文から渡した部分を含む） |
| `answer?` | 正規化した回答本文 |
| `citations?` | 出典の一覧と本文中の位置 |
| `provider`, `model`, `mode`, `promptVersion` | 送ったときの接続設定と指示文の版 |
| `status`, `createdAt`, `updatedAt` | 状態と復旧判断 |
| `searchPerformed?`, `truncated?`, `usage?`, `errorCode?` | 検索の実施、途中で切れたか、利用量、機密情報を含まないエラー |
| `native?` | 接続先の生の応答のうち、往復を続けるときに手を加えず送り返す部分（検索結果の暗号化された中身、思考など）。[接続先の確認表](AI_PROVIDER_CHECKS.md) 2.1 |
| `savedReferencePath?` | 資料に保存した場合の保存先 |

キーは記録しない。送信直前にRust側で現在のキーを取得する。キー削除・差し替えは次の送信から反映し、削除済みキーをメモリへ抱えて送らない。

### 4.3 状態と復旧

往復の状態は「送信中・完了・失敗・中止・中断」の五つとする。

| 条件 | 処理 |
| --- | --- |
| 送信 | 押した時点で往復IDを作って記録し、それから送る。同じ往復IDの送信はRust側で一度だけ受け付ける（AI-18） |
| 受信完了 | 正規化した回答を記録し、完了にする |
| キー未設定・認証失敗・制限超過・通信失敗 | 原因を分類して表示する。自動で有料の送信を繰り返さない |
| 利用者が停止 | 中止にする。遅れて届いた回答は捨てる |
| 作品切り替え・作品を閉じる | 送信中を停止し中断にする。次の作品で続けない |
| アプリ再起動 | 送信中のまま残った往復を中断として表示する。自動で送らない |
| 検索だけ失敗・検索なし・出力上限で終了 | 正常な完了と同じ扱いにせず、往復と資料にその旨を残す |

作品を開くたびに世代番号を一つ進め、送信時に作品ルートと世代番号を控える。回答が届いたとき、控えと今の作品が違えば画面に適用しない。今のApp.tsxには作品の世代番号がないため新設する（AI-16）。

会話の状態はApp.tsxに置かず、`src/research/`（新設。名前は着手時に `src/ai/` 等へ合わせる）の中に閉じ込める。App.tsxが渡すのは、作品ルート、世代番号、資料参照の追加口、本文の選択範囲だけにする（AI-17）。

資料に保存は、Markdownの保存、参照の追加、往復への `savedReferencePath` 記録の順で進める。途中で失敗しても、同じ操作をもう一度行えばファイルと参照が一つになるようにする。参照の追加は既存のReact側の経路を使い、Rustから `layout.json` を書き換えない。

## 5. 接続先

### 5.1 共通の形

接続処理の入力は、往復の一覧、今回の入力、指示文、モデル、動作モード、出力上限とする。出力は回答本文、出典と本文中の位置、実際に検索したか、利用量、途中で切れたかの区別とする。

共通処理は状態、停止、保存、表示を受け持つ。接続先ごとの処理は、依頼の組み立て、応答の読み取り、出典の変換、エラーの分類だけを受け持つ。

受信は画面に逐次表示しないが、各社が長い応答に推奨する受け取り方（ストリーミング）が必要なら、Rust側で受けてまとめる（AI-20）。

### 5.2 接続先ごとの方針と順序

| 順 | 接続先 | 相談 | Web検索付き調査 | 接続方式 |
| --- | --- | --- | --- | --- |
| 1 | Gemini | 対応 | 初期版では公開しない（5.3） | Gemini APIのAPIキー、`generateContent`。Vertex AIは対象外 |
| 2 | OpenAI | 対応 | 対応モデルの組み込みWeb検索 | APIキー、Responses API。検索付き調査を最初に作る接続先 |
| 3 | ローカルLLM | 対応 | 非対応 | ローカルで既に起動したOpenAI互換のChat Completions |
| 4 | Claude | 対応 | 対応モデルのWeb search tool | APIキー、Messages API。検索回数の上限も設定する |

Geminiを無料枠で使うと、送った内容をGoogleが製品改善に使い、人が読むことがある。無料枠か有料かは利用者の判断とし、Thenは区別も制限もしない（AI-23）。

ローカルLLMの確認にはOllamaを使う。接続先とモデル名は利用者が設定し、Thenからサーバー起動やモデルのダウンロードは行わない。URLはloopback（`127.0.0.1`、`localhost`、`[::1]`）に限り、リダイレクトは追わない。ローカルの回答を「Web調査済み」とは表示しない。

モデルの選択肢は、工程0で確認した少数の推奨値とモデルIDの手入力で始める。対応能力は接続先と確認済みモデルの小さな表で管理する。検索非対応のときに黙って通常の回答へ切り替えない。

### 5.3 Geminiの「Google検索して答える」

Gemini API追加規約（2026-03-23発効、2026-10-22確認）では、Google検索を使った回答に次の条件がある。

- アプリが自動で保存するのは原則禁止。例外は「利用者に自分の履歴を見せる」等の目的で最大2年。利用者が1件ずつ自分で保存するのはよい。
- 回答を書き換えたり、他の文章と混ぜたりしない。
- 回答と一緒に、Googleが返す検索候補を表示する。

会話画面は「履歴を見せる」例外に、「資料に保存」は「利用者が1件ずつ保存する」に当たる。本文に手を加えず出典を末尾に並べる保存形式も、この条件に合わせたもの。残るのは検索候補の表示で、Googleが返すHTMLを本体から隔離して出す必要がある。この表示を作るまで、Geminiの検索付きは公開しない。公開するときに、会話の記録を2年を超えて持たない扱いも決める。[Gemini API追加規約](https://ai.google.dev/gemini-api/terms#grounding_with_google_search)

### 5.4 引用と利用量

出典はAIが本文に書いたURLだけに頼らず、APIが返す引用情報から組み立てる。各社の帰属表示の条件は工程0の確認表に従う。[OpenAI: Web search](https://developers.openai.com/api/docs/guides/tools-web-search)・[Claude: Web search tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/web-search-tool)・[Gemini: Grounding](https://ai.google.dev/gemini-api/docs/google-search)

利用量は取得できた実数を保存し、不明値をゼロにしない。料金は自動計算しない。

## 6. 認証・通信・表示の安全

### 6.1 キーと通信

| 対象 | 扱い |
| --- | --- |
| キーの保管 | Windows資格情報マネージャー。`CRED_TYPE_GENERIC`、`CRED_PERSIST_LOCAL_MACHINE`（他のPCへローミングしない）、名前は `Then/ai/<接続先>`。`windows` crateに `Win32_Security_Credentials` を足す（AI-07） |
| キーの参照 | フロントへ返すのは設定済みかどうかだけ。保存済みキーを読むコマンドは作らない |
| 設定操作 | 保存、差し替え、削除、接続テスト。接続テストはボタン名で送信を伴うと分かるようにする。接続テストは実際の接続先と一緒に工程4で足す |
| 通信部品 | `reqwest`＋`native-tls`。接続先が本物かの確認はWindowsの仕組みを使う。中継サーバーは環境変数だけ（AI-06） |
| クラウド通信 | 公式HTTPSエンドポイントをRust側で固定し、キーは送信直前に付ける。別ホストへのリダイレクトは追わない |
| 呼び出せる窓 | 会話・キーのコマンドは、各コマンドの中で呼び出し元の窓が本体（main）かを確かめ、それ以外は断る。プラグインのiframeへは公開しない（AI-08）。`build.rs` のAppManifestは、置くとThenの全コマンドが許可一覧の対象になるため使わない |
| ログ・エラー | 認証ヘッダー、キーを含むURL、送受信の全文を通常ログへ出さない。APIの応答本文をそのまま画面へ返さない |
| 上限 | 入力（往復込み）40,000文字、出力16,000トークン（思考も数えるため。確認表2.2）、応答2MiB、クラウド180秒、ローカル300秒、検索は最大5回から。実装時に調整する |

資格情報マネージャーは、同じWindowsユーザーで動く悪意あるプログラムからの完全な隔離を保証しない。目標は、作品共有や通常ログへの混入と、画面側への不要なキー露出を減らすこととする。

### 6.2 回答の表示

回答の表示には、資料カードと同じMarkdown表示を使う。`ReferenceLayer.tsx` の表示部分を切り出して共用し、会話画面用に別の表示を作らない。そのうえで次を直す。

| 課題 | 対応 |
| --- | --- |
| リンクのスキームを確かめていない（AI-10、今の版の不具合） | http・https・mailto だけをリンクにし、他は文字として表示する |
| リンクを押した先が未確認（AI-11） | 既定のブラウザで開く経路を確かめ、なければ用意する |
| http(s)の画像を自動で読み込む（AI-12） | 利用者が書いた資料の挙動は変えない。AIの回答は、保存・表示の前に画像をリンクへ置き換える |
| 表示できる書式が狭い（AI-13） | 表示側を大きく作り替えず、回答をRust側でThenが表示できる範囲のMarkdownへ整える |
| CSPが無効（AI-09） | 公開前にThen基盤課題表TH-07を片付け、`connect-src` と `img-src` を絞る |

## 8. 実装手順

着手前に、mainから切った作業ブランチでチェックポイントのコミットを作る。

### 工程0: 確認と準備

1. 各社の公式資料から、推奨モデルID、検索ツールの指定方法と回数上限、出力上限、引用の返り方、帰属表示の条件、長い応答の受け取り方、料金ページを確認し、確認日つきの表にする（AI-03）。→ [AI接続先の確認表](AI_PROVIDER_CHECKS.md)
2. 指示文の初版を決め、版番号を付ける（AI-05）。
3. キーを使わない固定応答の接続先をRust側に用意し、`test:ai` を足す（AI-22）。

完了条件: 実APIなしで後続工程を確かめられる。

### 工程1: 表示の安全

1. `ReferenceLayer.tsx` のMarkdown表示を切り出す。
2. リンクのスキーム制限（AI-10）と、外部ブラウザで開く経路（AI-11）を入れる。今の版の資料にも効く。
3. AIの回答を整えて画像をリンクへ置き換える処理を、Rust側に用意する（AI-12、AI-13）。

完了条件: 危険なリンクや外部画像を含む回答の見本が、安全に表示される。

### 工程2: 通信なしで会話と保存を完成させる

1. 会話の一覧と往復の読み書きを実装する（4.1、4.2）。
2. 右ペインの「AI」、会話画面、入力欄を作り、固定応答の接続先で往復できるようにする。
3. 作品の世代番号を新設し、作品切り替え・停止・再起動の扱いを入れる（4.3）。
4. 「資料に保存」を実装し、二度押し・途中失敗・再起動で重複や上書きが起きないことを確かめる。

完了条件: APIキーなしで「質問 → 回答 → 資料に保存 → 再起動後に会話と資料を読める」が成り立つ。

### 工程3: キーと通信の共通処理

1. 資格情報マネージャーへの保存・差し替え・削除・設定済みの照会を実装する。
2. HTTP処理、公式接続先の固定、タイムアウト、応答サイズの制限、停止を実装する。
3. コマンドをmainに限る（AI-08）。
4. エラーを、認証、制限超過、通信、モデル非対応、検索失敗、途中で切れた回答に分類する。

完了条件: テスト用の資格情報でキーを保管でき、キーを画面・JSON・通常ログへ出さずに送れる。

### 工程4: Geminiで一連の実動作を完成させる

1. Geminiの相談（検索なし）を接続する。
2. 利用者のキーで、短い相談、往復の続き、資料に保存を各一件確かめる。有料の実API試験は通常のテストから分ける。

完了条件: 執筆を続けながら会話でき、回答を資料にして読め、再起動後も確かめられる。

### 工程5: 残りの接続先

1. OpenAIの相談とWeb検索付き調査を接続する。検索の実施状態、出典、利用量を共通の形へ変換する。
2. ローカルLLMを接続する。
3. ClaudeのMessages APIとWeb検索を接続する。HTTPが成功しても検索ツールが失敗する場合を判定する。
4. 各社の実応答を機密情報なしの見本に整え、出典とエラー変換を回帰テストにする。

完了条件: 四系統の相談と、OpenAI・ClaudeのWeb検索付き調査が同じ画面で動く。

### 工程6: 入口

1. 選択範囲が3.3の場面で正しく取れることを自動テストで確かめ、ずれがあれば直す（AI-29）。
2. 右クリックの「AIに渡す」を足す。
3. ポップアップと既存Ideaの「AIに聞く」を足す。

完了条件: 本文・ポップアップ・Ideaのどこからでも会話画面へ文章を渡せ、送る前に入力欄で確かめられる。

### 工程7: 公開前の確認と説明

1. CSPを有効にする（AI-09、TH-07）。
2. 次節の受け入れ試験と既存の関連テストを実行する。
3. 操作マニュアルに、設定方法、送る範囲（往復と、渡した本文だけ）、ローカルLLMの検索制限、資料に保存、停止・再送を書く。
4. 作品のバックアップに会話と資料が含まれ、キーは含まれないことを書く。
5. リリースノートには実装済みの能力だけを書く。

完了条件: 文書と実装の能力が一致し、全体の完了条件を満たす。

## 9. 検証

### 9.1 自動テスト

| 対象 | 確かめる振る舞い |
| --- | --- |
| 状態 | 一往復一回の送信、二度押しで二重に送らない、明示の再送、停止後の遅延応答を捨てる、再起動で自動送信しない |
| 往復 | 往復がすべて送られる、上限超過で送信前に止まる、古い往復を黙って削らない |
| 作品分離 | 作品Aの回答が作品Bへ入らない |
| 保存 | 会話ファイルの書込失敗、資料に保存の途中失敗と再実行、利用者が編集した資料の保護 |
| 接続変換 | 正常、拒否、空応答、検索非対応、検索ツール失敗、引用なし、出力上限、未知フィールド |
| キー | テスト用資格情報の作成・取得・削除、未設定、差し替え、JSON・例外への混入防止 |
| 表示 | 危険なURL、raw HTML、外部画像、長い回答、表、引用リンク |
| 選択範囲 | 3.3の各場面で、取れる範囲が選んだ範囲と一致する |
| 制限 | 入力超過、応答超過、タイムアウト、loopback以外への接続拒否、リダイレクト拒否、main以外の窓からの呼び出し拒否 |

APIは通常のテストでは固定応答を使う。資格情報の実動作は専用のダミー名を使う明示的なWindows試験に分け、試験後に削除する。開発者の既存キーは読まない。

### 9.2 手動の受け入れ試験

- 右ペインの「AI」とバインダーなど他のペインを行き来しても、会話と入力中の文章が失われない。
- 各接続先で相談し、選んだモデルと回答が会話に残る。往復を続けると話がつながる。
- OpenAIとClaudeで、検索の実施と本文・出典の対応を実データで確かめる。
- ローカルLLMではWeb検索を選べず、通常の回答を検索済みと表示しない。
- 回答を待つ間も本文の入力を続けられ、回答後に画面が勝手に切り替わらない。
- 本文で選んだ範囲を「AIに渡す」で入れ、送った内容が選んだ範囲と一致する。原稿用紙モードとTSF入力中でも確かめる。
- ポップアップとIdeaの「AIに聞く」で会話画面が開き、文が入力欄に入る。スレッドの表示と並べ替えは変わらない。
- 資料に保存した回答が選んだスレッドに普通の資料として入り、出典をクリックすると既定のブラウザで開く。
- 送信中の停止、キー削除、作品切り替え、会話の削除、アプリ終了を確かめる。
- 作品を別のフォルダへコピーして会話と資料を開ける。キーはコピーされず、勝手に通信しない。
- AIを使わない環境では、キー未設定や接続失敗が執筆・資料操作を妨げない。

### 9.3 関連する既存チェック

実装後に `npm run build`、`npm run test:binder`、`npm run test:v066-idea`、`npm run test:project-portability`、`npm run test:v058-selection`、新設する `test:ai`、`cargo check` と関連Rustテストを実行する。UIは明色・暗色と狭いサイドバーで確かめる。

## 10. 作業を増やさない判断基準

既存の画面・資料・設定で表せるものは流用する。共通化は二つ目の接続先で必要になった部分に限る。逐次表示、料金計算、モデル一覧の自動取得は、基本動作の完成に必要でなければ足さない。

優先順位は、質問と回答が残ること、二重送信と作品の取り違えを防ぐこと、表示の安全、各社の出典を保つこと、操作の仕上げの順とする。

次の場合は、その工程の仕様を見直す。独自の認証サービスが要る、別ランタイムの同梱が要る、一社の事情で全資料の保存方式を変える、利用者が渡していない原稿や資料を読む必要が出る、検索を共通化するために独自クローラーが要る場合。これらを黙って実装しない。
