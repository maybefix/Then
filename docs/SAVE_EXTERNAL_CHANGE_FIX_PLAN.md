## 工程1: 調査の結果

### いちばん大事な発見: 原稿の保存は `save_markdown_file` を通っていない

- 計画書は `save_markdown_file`（`src-tauri/src/lib.rs:1127`）を直す対象に挙げているが、画面の側からこの命令を呼んでいる所は**ない**（`src/` を `save_markdown_file` で検索して0件。命令の登録 `lib.rs:705` だけが残っている）。
- 開いている原稿の保存は、すべて **保存の記録（save journal）** を通る `journal_save`（`lib.rs:1187` → `src-tauri/src/save_journal/mod.rs:180` の `save` → `core.rs:438` の `save_inner`）。
- その `save_inner` には、**すでに外部の変更の確かめがある**（`core.rs:460-468`）。書く直前にファイルを読み、Then が最後に知っている内容のハッシュ（`disk_hash`）とファイルの識別子（`disk_id`）を比べ、違えば「ファイルが外部で変更されたため保存しませんでした（content changed / file identity changed）」で断る。

したがって、直すべき穴は次の2つと、断ったあとの扱いになる。

1. **比べる基準を持ち始めるのが遅い**（黙って消える。重さ: 高）。保存の記録は、原稿を開いたときではなく、**最初に1文字打ったとき**（`record_edits` → `Journal::start`、`core.rs:331`）に始まり、その時点のファイルを読んで基準にする（`core.rs:333-335`）。開いてから最初に打つまでのあいだに外部で書き換えられると、外部の内容が基準になり、次の自動保存が Then の本文で上書きする。外部の変更は黙って消える。開いたときのハッシュはタブが持っている（`DocumentTab.contentHash`、`src/editor/documentTabState.ts:125`）のに、保存の記録へは渡していない。
2. **記録を通らない書き込みは何も確かめない**（黙って消える。重さ: 高〜中）。`save_text_file`（`lib.rs:1227` → `write_text_file`、`lib.rs:3988`）はそのまま `std::fs::write` で上書きする。呼んでいるのは:
   - プロジェクト全体の置換（`src/projectSearchActions.ts:239`）。**開いているタブの原稿は、タブの本文を元に置換してファイルへ書く**ので、そのタブを開いたあとに外部で変わっていれば、外部の変更が消える。開いていない原稿は直前に読んでから書くので、窓は数ミリ秒。
   - チェックポイントからの復元（`src/App.tsx:4947`、`5168`）。直前に読んで本文だけ差し替えて書く。窓は数ミリ秒。復元は利用者が「この版に戻す」と選んだ操作。
3. **断ったあとに、利用者が何もできない**（消えはしないが、保存できない状態が続く。重さ: 中）。断られると、ステータスバーに英語混じりのエラー文が出て、タブが「保存エラー」になるだけ（`App.tsx:1883-1890`）。打つたびに 0.7 秒後の自動保存がまた断られる。外部の内容を読み込む手段も、上書きする手段もない。タブを閉じると「破棄して閉じる」しか選べない（この場合、記録は消える）。

### expected_hash の今の作法

## 工程2: 仕組みの説明

### 言葉

- **ハッシュ**: ファイルの中身から計算する短い指紋（SHA-256、64文字の16進）。中身が1バイトでも違えば別の値になる。
- **基準のハッシュ**: 「Then が最後に知っているファイルの中身」の指紋。開いたとき、または Then が最後に保存したときの中身。
- **保存の記録（save journal）**: 打った変更を、原稿とは別の場所（アプリのデータフォルダの `recovery/`）へその場で書いておく仕組み。原稿へは自動保存のときにその場で書く。途中で落ちても、次の起動で戻せる。
- **ファイルの識別子**: Windows がファイルごとに付けている番号。外部のエディタが「別名で書いてから入れ替える」保存をすると、中身が同じでも番号が変わる。

### 1. データの形

- タブ（`DocumentTab`）: `markdown`（今の本文）、`savedMarkdown`（最後に保存した本文）、`contentHash`（開いたとき／保存したときのファイルのハッシュ）、`fileId`。
- 保存の記録（Rust、`Journal`）: `content`（記録上の今の本文）、`disk_hash`・`disk_id`（基準）、`gen`（変更の番号）。

### 2. 利用者の操作と内部の処理

| 操作 | 内部で起きること |
|---|---|
| 原稿を開く | `read_text_file` で読み、タブに本文と `contentHash` を入れる。保存の記録はまだ始まらない |
| 1文字打つ | `recordDocumentChange`（`saveJournal.ts:126`）が記録を始める。Rust はこのときファイルを読み、そのハッシュを基準にする |
| 0.7 秒待つ／Ctrl+S | `journal_save`。基準とファイルを比べ、同じなら書いて読み直し、基準を新しい中身に替える。違えば断る |
| 外部で書き換える | 何も起きない（Then は気づかない） |
| 断られた | ステータスバーにエラー文。タブが保存エラー。次に打つとまた自動保存して、また断られる |

### 3. 保存

- 書き方は、原稿をその場で書き換える（新しく作って入れ替えない。`atomic_file.rs:7` の注記）。書く前に記録へ「これから書く」を残し、書いたあとに読み直して確かめる。
- 比べてから書くまでのあいだ（数ミリ秒）に外部で書かれた場合は、**Then が勝つ**（外部の変更が消える）。原稿のファイルを他のプロセスから閉め出して開いてはいない（`fs.rs:83`）。閉め出すと、外部のエディタが保存に失敗するため、今回も閉め出さない。
- 外部のエディタが「別名で書いて入れ替える」保存をした場合は、ファイルの識別子が変わるので、中身の比較の前に気づける。

### 4. ほかの機能との関係

- 復旧（次の起動で戻す）: 外部で変わっていた原稿は、原稿に触らずチェックポイントへ入れる。今回の変更と同じ考え方。
- 名前の変更・移動: 前に書き切ってから記録を閉じ（`closeDocumentJournal`）、新しい場所で記録を始め直す。始め直しのときも、基準はその時点のファイル。
- チェックポイントの比較画面: 開いているタブの本文を「今の原稿」として使う（`App.tsx:2070-2130`）。外部で変わったファイルの中身は見ない。

| 癖2 | 打ったあとに外部で書き換えると、保存は断られるが、エラー文が出るだけで、読み込む・上書きする手段がない | 直した（ダイアログ）。実機で確かめた |

## 工程5: 案

### 5-1. 方針

- 基準を、**開いたとき（タブの `contentHash`）**にそろえる。保存の記録を始めるときに、画面がこのハッシュを渡し、Rust はファイルがそれと違えば記録を始めても保存はしない（断る）。
- 断ったときは、そのタブの自動保存を止め、ダイアログを出す。

  - タイトル: 「ほかのアプリでファイルが変更されました」
  - 本文: ファイル名だけ
  - ボタン: 「ファイルの内容を読み込む」／「この内容で上書きする」／（閉じる＝あとで選ぶ）
- 「この内容で上書きする」: Rust がいまのファイルのハッシュを基準にし直して保存する（`expected_hash` にいまのファイルのハッシュを渡す形。チェックポイントの作法と同じく、比べた値を渡して命令を通す）。
- 「ファイルの内容を読み込む」: ファイルを読み直し、タブの本文と `savedMarkdown`・`contentHash` を替え、記録の基準をその中身にする。
- `expected_hash` の作法にそろえる: 命令の引数名は `expected_hash`、空や `None` なら比べない（古い呼び出しは今のまま）、断りの文は `... conflict: ...` で始め、画面はその種類で分ける。

### 5-2. 直し方の選択肢（どこで比べるか）

| 案 | 中身 | 利用者から見て | 手間 |
|---|---|---|---|
| **A（勧め）** | 保存の記録の `Journal::start` に基準のハッシュを渡す。記録の中の比べる処理（`core.rs:460-468`）は今のものを使う | 開いてから打つまでの変更も、打ったあとの変更も、同じダイアログになる | 小〜中 |
| B | `journal_save` の前に、画面が `read_text_file` でハッシュを取って比べる | 同じに見えるが、比べてから書くまでの窓が広がる（画面と Rust の往復）。比べる処理が2か所になる | 小 |
| C | `save_markdown_file` に `expected_hash` を足す（計画書の書き方どおり） | 何も変わらない（この命令は使われていない） | ― |

A を勧める理由: すでに正しく比べている処理があり、穴は基準を取る時点だけ。比べる所を1か所に保てる。

### 5-3. 決めてほしいこと

- **Q1 ダイアログを出す場面**
  - a（勧め）: 保存しようとして違いに気づいたとき（自動保存・Ctrl+S・名前の変更の前の書き切り）。タブが表示中ならその場で、裏のタブなら表に出したときに出す。

- **Q2 比べるハッシュの範囲**
  - a（勧め）: ファイルの全バイト（今のまま）。改行だけ・フロントマターだけの違いも「変わった」とする。Obsidian がプロパティを書き換えた場合も知らせる。誤って消すより、尋ねるほうが安全。
  - b: 改行をそろえてから比べる（CRLF ⇔ LF だけの違いは同じとみなす）。Git の改行の変換などで、中身が同じなのにダイアログが出るのを避けられるが、上書きすると改行が Then 側に戻る。
  - c: 本文だけ比べる（フロントマターの違いは無視して上書き）。フロントマターの外部の変更が黙って消えるので勧めない。
- **Q3 消える側を残すか**
  - a（勧め）: 「この内容で上書きする」の前に外部の内容を、「ファイルの内容を読み込む」の前に Then 側の本文を、チェックポイントに入れる。復旧（外部で変わった原稿はチェックポイントへ）と同じ考え方。ボタンの文言は変えない。
  - b: 残さない（選んだほうがそのまま勝つ）。
- **Q4 閉じるときと、作品を切り替えるとき**

  - b: 閉じる前・切り替える前に、未保存の原稿を書き切り、違いがあればダイアログを出してから閉じる・切り替える。閉じる処理の2秒の待ち（`close_gate.rs`）の中ではダイアログを待てないため、閉じる処理の作りを変える必要がある。
- **Q5 プロジェクト全体の置換（癖3）**

  - b: 今回は直さず、記録だけ残す。

### 変わる挙動

- 原稿を開いたあと、最初に打つ前に外部で書き換えられていた場合も、保存は断られる（今までは黙って上書き）。
- 保存が断られると、そのタブが表に出ているとき「ほかのアプリでファイルが変更されました」のダイアログが出る。本文はファイル名、詳しくはパス。ボタンは「ファイルの内容を読み込む」と「この内容で上書きする」。閉じると何もせず、次の保存でまた尋ねる。
  - 「ファイルの内容を読み込む」: Then の本文をチェックポイントに入れてから、記録を捨て、ファイルの中身をタブに読み込む（表示位置は変えない）。通知「「<名前>」を読み込みました」。
  - 「この内容で上書きする」: ファイルの中身をチェックポイントに入れてから、そのハッシュを基準にして保存する。選ぶまでのあいだにファイルがまた変わっていたら、上書きせずにもう一度尋ねる。通知「「<名前>」を上書きしました」。
  - 作品の外のファイルは、チェックポイントに入れる場所がないので、入れずに実行する。チェックポイントに入れられなかったときは、何もせずに「チェックポイントに保存できなかったため、読み込みませんでした／上書きしませんでした」。
- 選ぶまで、そのタブの自動保存は止まる（ステータスは「保存エラー」のまま）。Ctrl+S はまた尋ねる。
- ステータスバーのエラー文から、見分け用の前置き（`document content conflict: `）を外して出す。
- プロジェクト全体の置換: ほかのアプリで変わっていたファイルは置換せず、通知に「（ほかのアプリで変更されたNファイルは置換していません）」を足す。全部がそうなら「ほかのアプリで変更されたNファイルは置換していません」。置換したタブは、新しいハッシュを持つ。

### 誤って断らないための仕組み

Then がほかの経路（置換・チェックポイントからの復元・見出しの移動など、`write_text_file` を通るもの）や記録で書いた中身のハッシュを、ファイルごとに覚える（`then_writes`）。記録を始めるときにファイルがこの中身なら、タブのハッシュが古くても外部の変更とはしない。

### 変えていないもの

- 保存の記録の形式、原稿の書き方、`journal_save` の比べ方（`save_inner`）。
- 閉じるとき・作品を切り替えるとき（Q4）。チェックポイントからの復元・名前を付けて保存。
- 使われていない `save_markdown_file` は、引数を合わせただけで残した。
