# 異字同訓・同音異義語・主述の対応

同じ読みの漢字の使い分けを、近くの語との組合せから確認する3つのルールの設計。いずれもアプリ内で完結し、外部の解析器や追加のランタイムを必要としない。配布インストーラーに増えるのは辞書テーブルのソース（約87KB、圧縮後はそれ以下）だけである。

## 経緯

先行実装は、答・応、熱・暑、乾・渇、直・治、習・倣の5組を正規表現で書いたものだった。あわせて、SudachiPyとGiNZAを別プロセスで動かす「文脈解析（試験機能）」も試した。

文脈解析は取りやめた。実行環境が583MB（SudachiDict-core 207MB、spaCy 86MB、ja_ginza 75MB ほか）あり、35MBのインストーラーに載せられる規模ではない。開発環境限定にしたり、利用者にPythonのパスを設定させたりするのは製品として成立しない。

取りやめる前に、常時動作するルールと文脈解析の指摘を1件ずつ突き合わせた。文脈解析が多く出していた分は、すべて常時動作側の当て方の穴だった。それを直した後の比較は次のとおり。

| 対象 | 常時動作 | 文脈解析（GiNZA係り受け） | 文脈解析だけ | 常時動作だけ |
|---|---|---|---|---|
| こころ（16.6万字） | 7件 | 5件 | 0件 | 2件 |
| 坊っちゃん（9万字） | 8件 | 8件 | 0件 | 0件 |

文脈解析だけが拾うものは無く、常時動作側が2件多い。文脈解析だけが持っていた「主述の対応」も、文の切り出しと語尾の形だけで同じ範囲を見られたため `topic-predicate` としてTSへ移した。

## 異字同訓（`ijidokun`）

報告の**全項目**を対象にする。連語をひとつずつ書く方式をやめ、報告の用例から起こした手掛かり語の表を引いて、文脈が別の表記を指すときだけ確認を出す。

対象は128項目・299表記・1,000語の手掛かり。報告の133項目のうち、用例から手掛かりを取れなかった5項目（016 ある、022 うた、048 かま、120 まわり、127 よ）は入らない。

### 何を手掛かりにするか

本文に現れた表記の周りから、次の関係にある語を取り出して表と照合する。

- **格の項**：「期待に答える」の「期待に」。述語の直前へ8文字までさかのぼる。句読点・鉤括弧・マスクをまたぐものは結び付けない。いちばん近い助詞が項とは限らない（「声を微かに聞いた」の「微かに」）ので、窓の中の助詞をすべて候補にする。
- **連体修飾の被修飾名詞**：「暑い湯」の「湯」。「乾いた土」のように助動詞が挟まる形も見る。形容詞や自動詞ではガ格の項と同じ語になるため、ガ格と連体は同じ手掛かりとして扱う。
- **複合・述語**（名詞の項目）：「立つ鳥後を濁さず」の直前の「鳥」、「脚の裏」の「の裏」、「足が出る」の述語「出る」。

活用は見出し形の最後の仮名から語尾の行を作って当てる。品詞解析はしないので拾いすぎるが、手掛かり語が一致しない限り指摘は出ない。

### 出さないための条件

- 同じ語が同じ項目の複数の表記に現れる場合は、関係が違っても手掛かりにしない（004 あく・あける の「目」など）。
- 別の表記を示す長い語の一部になっている語も採らない。051 きく の「声」は「話し声を聞く」の一部でもあり、どちらを指すか決められない。
- 報告が注記（\*）や併記（（　））を付けた用例は、報告自身が使い分けの分かれる例だと述べているので手掛かりにしない（「子供が生まれる\*」「体重を量る\*」など）。
- 見出しが「上がる・上げる」「揚がる・揚げる」のように自動詞・他動詞で対になる項目では、並びの位置か送り仮名がそろう語だけを候補にする。「国を建てる」を根拠に「国を立つ」を疑わない。
- 直前が漢字・片仮名のときは複合語の一部とみなし、前に付く語が決め手になる形だけを見る（「正直」「最後」「都合」を拾わない）。
- 語の切れ目は仮名で判断する。「蝉の声」の「声」は採るが、「大根」の「根」のように漢字が続く末尾と、「お金」の「金」のように接頭辞（お・ご・み）が付いた末尾は採らない。
- 同じ関係で長い手掛かり語が当たっていて、それが書かれている表記を指すなら黙る。「話し声を聞く」で、より短い「声」（聴く）だけを見て言い換えを勧めない。

指摘は「参考」で、候補・語義・出典の項目番号とページを表示し、置換ボタンは出さない。項目別の停止（`ijidokun/<項目番号>`、ルール一覧では畳んで表示）、会話文除外、辞書の保護に対応。コード・URL・ルビの読みは既存のマスクに従って除外する。引用・比喩を完全には判別できないため、著者による確認を前提とする。

### データの作り方

`src/proofread/ijidokunData.ts` は生成物で、手では直さない。報告のPDFから項目・語義・用例を取り出し、用例をSudachiで解析して共起語を集める。**この解析は開発時のテーブル生成にだけ使い、アプリには入らない。**

```powershell
python -m venv .venv-build
.venv-build/Scripts/python.exe -m pip install -r scripts/nlp/requirements-build.txt
.venv-build/Scripts/python.exe scripts/nlp/build-ijidokun.py <報告のPDF>
```

報告の用例に無い日常語（「質問に答える」「洗濯物が乾く」「司会を務める」など）は、報告が示した語義の範囲を出ない形で `src/proofread/ijidokunExtra.ts` に足す。見出しは表記そのままで書き、番号への解決と、同じ項目で既に別の表記に割り当てられている語の除外は読み込み時に行う。解決できない行は `npm run test:proofread` が落とす。

根拠：文化審議会国語分科会『「異字同訓」の漢字の使い分け例（報告）』（2014年2月21日）。前書きは、異なる使い分けを否定しないと明記する。資料の語義を参考にThen独自の検出条件を作成した。

https://www.bunka.go.jp/seisaku/bunkashingikai/kokugo/hokoku/pdf/93927001_12.pdf

## 同音異義語（`homophone`）

同じ音読みで意味の違う漢語を34組扱う。異字同訓と同じ考え方で、接する語が別の表記でしか使わない語のときだけ確認を出す。

- **直前に付く語**：「品質保証」の「品質」。「損害の補償」「損害を補償する」のように助詞で続く形も、助詞を落として名詞を見る。
- **直後に付く語**：「保証人」の「人」、「対照的」の「的」。
- **直後の述語**：「関心を持つ」の「持つ」、「感心する」の「する」。サ変動詞の活用は別に持つ。

どちらの表記でも使う語（「解放感」と「開放感」、「想像力」と「創造力」、「配付」と「配布」）は決め手にならないので入れない。判断が割れる語も入れない。

異字同訓の表と違い、同音の漢語の使い分けを定めた告示・報告は無い。根拠は『記者ハンドブック』が示す使い分けの考え方で、一覧そのものは語義に沿ってThenが編んだものであることを、指摘の説明にも明記している。

## 主述の対応（`topic-predicate`）

「趣味は」「楽しみは」「目標は」「目的は」で始まる文が動詞で終わっているとき、「〜することだ」のような結びが適切か確認する。文の切り出しと語尾の形だけを見る。

目的語や到達点（を・に・へ）を伴う文に限り、名詞述語（「趣味は登山です」）や形容詞（「目標は高い」）、主語の状態を述べただけの文（「楽しみは増えました」）では出さない。主語と述語の間に別の節が挟まる文（「目標は達成できたが、次の課題が残る」）も見送る。省略や語り口を誤りとは断定しない。

## 精度の目安

| 対象 | 分量 | 指摘 | 1万字あたり |
|---|---|---|---|
| 青空文庫（こころ・坊っちゃん・羅生門・蜘蛛の糸） | 27.2万字 | 15件 | 0.55件 |
| 本リポジトリの日本語ドキュメント | 25.1万字 | 14件 | 0.56件 |

青空文庫の指摘は「便宜を計る→図る」「腰を卸す→下ろす」「支度を整える→調える」「気に触る→障る」のように、確認する価値のあるものが中心。リポジトリ側の14件は、この文書とREADMEが誤用例そのもの（「期待に答える→応える」など）を載せているための一致で、地の文での誤検出ではない。同音異義語と主述の対応は、この52万字でいずれも0件。処理はこの分量で60〜110ミリ秒。

同音異義語は別に、誤りの例74件で71件を検出し、正しい用法では0件だった（残る3件は「補障」「対勢」など実在しない表記を試したもの）。

## 検証

```powershell
npm run test:proofread
npm run test:proofread-ui
npm run build
```

`test:proofread` はルールの棚卸し（種類数・出典の有無・語を指すか文を指すか）、手掛かり語の表の整合（実在する見出しを指すか、同じ語が複数の表記を指していないか、手で足した語がすべて取り込まれたか）、各ルールの検出例と非検出例を見る。`test:proofread-ui` は校正ペインを実際に描画し、指摘の一覧と、項目の多いルールを畳んで出す表示を確認する。利用者の原稿はテストに使わない。

## 今後の拡張

手掛かり語の補いを、試験原稿での誤検出を見ながら増やす。同音異義語は組数を増やす余地があるが、判断が割れる語を入れないことを優先する。人物・時系列・省略された主語の推測は、別の推敲機能として検討する。
