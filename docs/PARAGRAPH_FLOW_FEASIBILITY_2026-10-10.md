# 全段落の座標再取得を外せるか：配置依存関係の検証

2026-10-10。調査・隔離ブラウザでの試作のみ。本番コード、配布物、インストール環境は変更していない。

## 結論

現在の組版を維持したまま、局所編集で全段落の外接矩形を再取得する処理を外せる実測根拠が得られた。変更段落の実寸を測り、後続段落の位置を実寸の累計から求める試作が、125状態で全文実測と一致した。

ただし「ResizeObserverを付ければ解決」ではない。寸法通知前の座標利用と、外寸が変わらない内部文字配置変更に失敗する対照実験も成立した。本文・装飾・全体の組版設定から、座標を利用する前に再計測対象を確定する必要がある。

したがって、問題を直ちにフレームワークの限界やネイティブ移行の必要性と結び付ける根拠はない。今回確認したのは、Then側の座標管理を変更できる条件である。ブラウザ内部のレイアウト処理まで文書長に依存しなくなることや、製品全体の速度向上率は、この試作の結果ではない。

## 実際の配置規則

`src/editor/pageBreaks.ts` と `src/App.css` を確認した。現在のページ表示はCSS multicolによる段落の分断ではなく、連続配置の本文を自前のページ割りで移動・クリップする方式である。連続／ページ表示とも、段落は一つのブロック方向に順番に配置される。

確認した段落にはブロック方向の余白、float、段落自体のtransformがなく、隣接段落間のマージン相殺もない。表は段落単位のgridで、列幅の共有は装飾属性の更新として現れる。見出し、リスト、ルビ等による内部形状の差は残る。

この条件では、段落先頭の本文内座標は「本文の先頭余白＋前にある表示段落の実測ブロック寸法の合計」で求められる。縦書きでは幅を右から左へ、横書きでは高さを上から下へ累計する。`display:none`の段落は流れの寸法を消費しない。ゼロ寸法の表罫線段落は保持する。

ここで累計するのは行送り×推定行数ではなく、ブラウザが確定した段落のborder boxの実寸である。既存のページ処理が警戒している行送りの丸め誤差とは区別する。段落内部の文字断片は段落からの相対座標で保持し、本文全体の画面上の移動は本文rootの座標に分離する。

## 検証方法と結果

`scripts/audit-paragraph-flow-browser.mjs` は実際のアプリを隔離したheadless Edgeで開き、メモリ上のmock backendを使用する。既存の本番処理はそのまま動いている。

試作側は初回のみ全段落を計測する。その後は段落内のDOM変更と段落の寸法通知から再計測対象を集める。書字方向・折り返し寸法・フォント等の全体条件が変わった場合は全体を再計測する。座標照合のための全段落実測は独立した正解判定側で行い、試作のキャッシュや更新対象へ値を渡さない。

| 対象 | 結果 |
| --- | --- |
| 縦横書き×連続／ページ表示を含む125状態 | 不一致0 |
| 段落の外接矩形 | 延べ47,099段落、座標差最大0px |
| 内部の文字断片 | 延べ981,167断片、座標差最大0px |
| 通常の局所編集・240段落の連続表示 | 再計測1段落 |
| 局所編集・2,139段落のページ表示 | 再計測2段落、8回とも一致 |
| 画面寸法・フォント・書字方向等の全体変更 | 全体再計測後に一致 |

対象操作は局所追記、折り返し増加、段落分割、Undo/Redo、太字、表の共有列幅、見出し化、ルビ、コメント表示切替、IME変換中／確定、遠方への選択移動、ページ送り方向、画面サイズ変更、小数の文字サイズ・行送り、フォント変更。

「変更した本文1段落だけが常に再計測される」とは言えない。ページ表示ではコメント段落の属性更新も入り、240段落中17段落の再計測になった。表の変更では17〜19段落、最初の段落分割では156段落にDOM更新が波及した。これらは実際の装飾・DOM更新を検出した結果で、全段落の座標比較から更新対象を見つけたわけではない。

## 更新タイミングと検出漏れの対照実験

追加10ケースで、変更直後と通知後を比較した。

本文編集、表の共有列幅更新、段落分割、Undo、rootのフォント設定、段落自身のstyle変更は、DOM変更記録を同期的に回収し、必要な全体設定を確認することで、変更直後から全文実測と一致した。

一方、試作へ明示的に知らせず外部stylesheetから段落の文字サイズを変更すると、寸法通知前には段落座標が最大97.953125pxずれた。通知後に該当段落だけ再計測すると0pxに戻った。RAF内で変更した場合も、そのRAFでの照合は失敗し、次のRAFでは一致した。寸法通知を待つだけでは、同じ更新内の座標利用を保証できない。

さらに、見出しの字間だけをstylesheetから変更した。段落の外接矩形は変わらず差0pxだったが、内部文字断片は12.546875pxずれた。二つのRAF後も寸法通知による再計測は0段落で、ずれは残った。明示的に組版条件を無効化して再計測すると0pxに戻った。

これは検出経路を意図的に外した試作の対照実験であり、現行製品のバグを再現したという意味ではない。寸法監視だけでは文字配置のキャッシュを正しく更新できないことを確認するためのもの。

## 性能について測れたこと

2,139段落の長いルビ入り文書で、安定した配置を読み出す処理を80回比較した。

| 測定した処理 | 中央値 | p95 |
| --- | ---: | ---: |
| 全段落のgetBoundingClientRect | 10.1ms | 14.4ms |
| rootと全体条件の確認＋キャッシュから全段落座標を組み立て | 1.1ms | 1.9ms |

この値は未変更状態の座標取得・組み立て部分の比較である。入力処理全体や、変更段落の再計測、observerの通知処理、初回登録の費用を含めた高速化率ではない。固定した順序で測った一実行の値なので、製品の速度保証にも使わない。試作はまだ全段落の座標をJSで組み立てており、全処理がO(変更段落数)になったわけでもない。

監視を追加する費用も別途測った。101,560文字・2,139段落、縦書き・連続表示で、局所の同じ長さの1文字置換を24回測定し、各条件で別の24回をウォームアップした。3反復で比較順序を交互にした。本番の全段落取得は両条件に残しているため、これは置き換え後の完成版比較ではなく「既存処理に試作の監視・差分更新を追加した費用」の確認である。

| 反復 | 既存処理のみのTaskDuration／操作 | 試作を追加したTaskDuration／操作 |
| --- | ---: | ---: |
| 0 | 18.808ms | 18.815ms |
| 1 | 20.215ms | 18.008ms |
| 2 | 19.141ms | 30.063ms |

試作側の段落再計測は各反復24回、つまり1操作1段落だった。最後の試作追加条件の増大は除外していない。この結果から監視追加の負荷が常に小さいとも、増大の原因がobserverだけだとも判断しない。監視には対象段落数に応じたブラウザ側の管理が残り、今回の局所更新の成立と、製品全体の純利益は別の検証対象である。

## 実装する場合に必要な変更の境界

1. 段落の寸法・内部文字配置・本文内の位置を分離する。変更段落の実寸と形だけを更新し、後続位置は実寸の累計で求める。初回と全体の組版条件変更には全体計測を残す。
2. 本文transaction、装飾DOM更新、文字寸法設定、フォント読み込みを明示的な更新理由にする。寸法監視は補助とし、座標利用前に反映する。表などの共有依存範囲も対象に含める。
3. 行番号等の補助表示とページ割りが同じ段落計測結果を使う。現状は補助表示側の全段落取得と、`measureParagraphs`側の全段落取得が別に存在するため、一方だけの変更では全体の取得をなくせない。
4. 本文の移動だけと組版変更を区別する。現在はrootのstyle/class変更で表示行の全体revisionを進めるため、ページ移動用の位置指定も内部文字形状の再計測につながり得る。
5. 累計の更新・可視範囲探索・ページ割りの再計算も測る。DOM取得をなくしても、毎回全段落の配列を作る実装のままならJS側の文書長依存は残る。

この調査では上記を本番へ実装・配布していない。実WebView2、OSのIME候補ウィンドウ、全設定を含む長時間操作の認定でもない。
