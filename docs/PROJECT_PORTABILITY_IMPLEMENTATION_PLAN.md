# Then プロジェクト可搬化 実装計画

作成日: 2026-09-21

## 1. 目的

Then のプロジェクトフォルダをクラウドストレージや外部ドライブ経由で別端末へ移した場合に、原稿だけでなく、執筆上の意味を持つプロジェクト状態も同じ状態で利用できるようにする。

今回の中心対象は次の2つとする。

- ファイルの進捗ラベル
- チェックポイント／復元前の退避

Obsidian の vault に近い「フォルダが正本」という性質を目標にする。ただし、クラウドサービスそのものを実装したり、複数端末からのリアルタイム同時編集を保証したりはしない。

## 2. 完了条件

次のシナリオがすべて成立した時点を完了とする。

1. 端末Aで既存プロジェクトを開き、進捗ラベルとチェックポイントを作成する。
2. Then を終了し、プロジェクトフォルダ全体を別の絶対パスへコピーする。
3. Then のアプリデータが空の端末B相当の環境から、そのコピーを開く。
4. 進捗ラベル、手動チェックポイント、復元前の退避が表示される。
5. 端末Bで新しいチェックポイントを作成し、比較と復元ができる。
6. テーマ、ウィンドウ位置、最近開いたプロジェクトなどの端末設定は共有されない。
7. 旧バージョンのローカルデータからの移行に失敗しても、元データは失われない。
8. 保存中にアプリが終了しても、直前まで有効だったプロジェクト状態を読み込める。

## 3. 保存境界

### 3.1 プロジェクトと一緒に保存するもの

- 原稿ファイルとフォルダ
- Idea、Plot、作品用 Canvas
- ファイルの並び順
- プロジェクト固有の校正辞書と無視設定
- プロジェクト資料と資料レイアウト
- ファイルの進捗ラベル
- 手動チェックポイント
- チェックポイント復元前の自動退避

### 3.2 端末ローカルのままにするもの

- 最近開いたプロジェクトと最後に開いた絶対パス
- ウィンドウ位置とサイズ
- テーマ、UI倍率、端末上のフォント選択
- インストール済みプラグイン
- プロファイル用 Idea、共通 Canvas、共通資料
- 開いているタブ、カーソル、スクロール位置、UIの折りたたみ状態
- 保存中の未確定入力や一時的な回復データ

開いているタブなどは将来「ワークスペース状態」として共有可能だが、今回の変更へ混ぜない。意味データの可搬化と端末UIの同期は別テーマとして扱う。

## 4. 現状と問題点

現在、進捗ラベルとチェックポイントは `AppState` に含まれ、アプリデータの `app-state.json` に保存される。

- `fileProgress` は絶対ファイルパスをキーにしている。
- `snapshots` は全プロジェクト分を1つの配列に保持している。
- snapshot の `workspacePath`、`projectTree`、各 file の `path` は絶対パスである。
- app state は別のUI状態が変わった場合にも全体が再保存される。
- チェックポイントは各時点の全原稿本文を保持するため、データ量が大きい。

この形式をそのまま `.then/project.json` へ移すと、書き込み増幅、クラウド競合、巨大JSON、絶対パス依存を持ち込む。そのため進捗とチェックポイントで保存方式を分ける。

## 5. 採用する保存形式

```text
<project>/
├─ 原稿.md
└─ .then/
   ├─ project.json
   └─ checkpoints/
      ├─ snapshot-....json
      └─ shelter-....json
```

### 5.1 進捗ラベル

進捗ラベルは小さく、ファイルの並び順と同様にファイル構造へ追従するため、`.then/project.json` の `fileProgress` に保存する。

永続化形式では絶対パスを使わず、プロジェクトルートからの相対パスを `/` 区切りで保存する。

```json
{
  "schemaVersion": 1,
  "revision": 12,
  "fileProgress": {
    "01_本文/第一章.md": {
      "status": "writing",
      "updatedAt": 1789945200000
    }
  }
}
```

方針:

- `todo` は既定値なので保存しない。
- 絶対パス、空パス、`..`、プロジェクト外、`.then` 配下を拒否する。
- rename / move / delete と同じバックエンド処理内でキーを更新または削除する。
- フォルダ操作では配下のキーもまとめて更新する。
- 大文字小文字の比較は現在のWindows挙動を維持しつつ、保存時の表記は実ファイルの相対パスを保持する。
- `updatedAt` は移行時および将来の競合説明に使う。自動的な last-write-wins の根拠として盲目的には使わない。

### 5.2 チェックポイント

チェックポイントは `.then/project.json` に埋め込まず、1チェックポイントにつき1つのJSONファイルとして保存する。

```json
{
  "schemaVersion": 1,
  "revision": 1,
  "id": "snapshot-...",
  "createdAt": 1789945200000,
  "reason": "manual",
  "label": "終盤改稿前",
  "memo": "会話のテンポを変更する前",
  "parentIds": [],
  "projectTree": {
    "path": ".",
    "name": "作品名",
    "children": []
  },
  "files": [
    {
      "path": "01_本文/第一章.md",
      "name": "第一章.md",
      "text": "...",
      "textHash": "...",
      "semanticHash": "...",
      "lineCount": 100,
      "textLength": 3200,
      "visibleTextLength": 2900,
      "outlineCount": 4
    }
  ]
}
```

方針:

- 永続化形式には `workspacePath` を持たせない。
- `projectTree` と `files` の path はすべて相対パスにする。
- 読み込み時だけ、現在開いているプロジェクトルートと結合して既存UIが扱うランタイム形式へ変換する。
- 新規作成後の本文部分は変更しない。タイトルとメモの変更時だけ、その1ファイルを安全に置換する。
- 一覧のための中央 `index.json` は初期実装では置かない。単一の共有インデックスを競合点にしないことを優先する。
- ファイル名と snapshot ID を厳格に検証する。
- 壊れた1件があっても正常な他のチェックポイントは読み込む。読み込み結果は `snapshots` と `warnings` を分けて返す。
- 現行仕様どおり、原稿テキストの意味ある版管理であり、画像やPDFを含む完全バックアップとは表示上も区別する。

チェックポイント数が増え、全ファイルの解析コストが問題になった場合は、後続スキーマで軽量manifestと本文blobへ分割する。初回移行で複雑な二相コミットを導入しない。

## 6. 書き込み安全性

### 6.1 共通の原則

プロジェクト管理ファイルの保存は次の順序で行う。

1. 現在ファイルを読み込み、スキーマとrevisionを検証する。
2. 同一プロセス内の保存をロックして直列化する。
3. 同じディレクトリ内の一時ファイルへUTF-8で書く。
4. `flush` と `sync_all` を行う。
5. 一時ファイルを再読込し、JSONとして検証する。
6. 旧ファイルを `.bak` へ退避する。
7. 一時ファイルを正本へ昇格する。
8. 失敗時は `.bak` から戻す。

Windowsで既存ファイルへのrenameが失敗する挙動も含めて実装し、現在の `reference-layout`、Canvas、中間稿で似た処理が重複している部分は、検証済みの共通helperへ段階的に寄せる。

### 6.2 競合の扱い

この計画は同時編集を解決しないが、無言の上書きは減らす。

- `.then/project.json` に `revision` を導入する。
- 進捗変更は「マップ全体を保存」ではなく「1パスを更新するcommand」とし、バックエンドが直前の正本へpatchする。
- チェックポイント作成は新しい一意ファイルの追加なので、既存チェックポイントを上書きしない。
- タイトル／メモ変更には snapshot 単位の `expectedRevision` を渡し、不一致なら再読込を要求する。
- アプリがフォーカスを取り戻した時、またはチェックポイント画面を開いた時にプロジェクト状態を再読込する。
- 既知のrevisionより小さい値や、同一revisionで内容hashが異なる状態を検出した場合は、同期巻き戻りの可能性を通知し、自動保存を止める。

クラウド事業者が作る「競合コピー」のファイル名は統一されていないため、名称依存の自動マージは行わない。

## 7. バックエンドAPI

新しい永続化処理は `src-tauri/src/project_state.rs` と `src-tauri/src/checkpoint_store.rs` に分離し、`lib.rs` はcommand登録と既存ファイル操作との連携に留める。

想定command:

- `load_project_file_progress(root_path)`
- `set_project_file_progress(root_path, relative_path, status)`
- `load_project_checkpoints(root_path)`
- `create_project_checkpoint(root_path, checkpoint)`
- `update_project_checkpoint_metadata(root_path, checkpoint_id, expected_revision, label, memo)`
- `delete_project_checkpoint(root_path, checkpoint_id, expected_revision)`

復元処理そのものは第1段階では既存UIフローを維持する。バックエンドから返すランタイムデータを現在の絶対パス形式へ展開し、既存の比較・部分復元ロジックを壊さず保存元だけを切り替える。

永続化移行が安定した後、復元全体をバックエンドのトランザクションへ移すかは別の改善として判断する。

## 8. 旧データ移行

移行はプロジェクトを開いた時に実行し、冪等にする。

### 8.1 進捗ラベル

1. `AppState.fileProgress` から現在のプロジェクト配下のキーだけを抽出する。
2. プロジェクト相対パスへ変換する。
3. 共有側に同じキーがなければ取り込む。
4. 共有側に値がある場合は共有側を優先する。旧データには更新時刻がなく、安全な新旧判定ができないためである。
5. 成功後も旧データはそのリリース中は削除せず、ローカルの移行済み記録を残す。

### 8.2 チェックポイント

1. `AppState.snapshots` から `workspacePath` が現在のプロジェクトと一致するものを抽出する。
2. すべての保存パスがプロジェクト配下であることを検証する。
3. 相対パス形式へ変換する。
4. 同じIDのファイルがなければ作成する。
5. 同じIDと同じ内容なら成功済みとして扱う。
6. 同じIDで内容が異なる場合は上書きせず、警告とともに別IDでの取り込み候補にする。
7. すべての対象が保存・再読込・hash検証できてから移行完了を記録する。

端末Aと端末Bがそれぞれ異なる旧チェックポイントを持つ場合でも、順番にプロジェクトを開けば両方を追加できる。移行は既存共有データを置換しない。

### 8.3 互換期間

最初の1リリースは次の動作にする。

- 読み込みの正本はプロジェクト側。
- プロジェクト側が空で未移行の場合のみ旧ローカルデータを取り込む。
- 新しい変更はプロジェクト側へ先に保存する。
- 保存成功後、旧 `AppState` にも互換用ミラーを残す。
- プロジェクト保存に失敗した場合はUI上の成功扱いにせず、ローカルだけを更新しない。

次の安定版で旧ミラー書き込みを停止する。旧フィールドの読み込み互換と手動回収手段は、さらに1リリース残してから削除を検討する。

## 9. 実装フェーズ

### Phase 0: 基準固定と失敗時設計

- 現行の進捗、チェックポイント作成、比較、全体復元、部分復元、rename/move/deleteの回帰テストを追加する。
- `AppState` の現行fixtureを作り、移行前データを固定する。
- 破損JSON、書込不可、途中終了を想定した期待動作をテストとして先に置く。

完了条件: 保存先を変える前に、現行動作の差分を検知できる。

### Phase 1: プロジェクト保存基盤の強化

- `ProjectConfig` に `schemaVersion`、`revision`、`fileProgress` を追加する。
- 欠落フィールドを既定値で読む後方互換を維持する。
- project config のload-modify-saveをプロセス内で直列化する。
- 検証付きatomic writeと`.bak`復旧を実装する。
- 既存のIdea、Plot、並び順、校正辞書の保存テストも追加する。

完了条件: 新旧project.jsonを読み書きでき、保存失敗時に旧正本が残る。

実装状況（2026-09-21）: Phase 0–1 実装済み。旧AppState fixtureと現行チェックポイント／ファイル操作の回帰基準を追加し、ProjectConfigのversion/revision、プロセス内直列化、検証付きatomic write、`.bak`復旧、旧形式・既存領域の往復テストを導入した。

### Phase 2: 進捗ラベルの共有化

- project-relative path変換／検証helperをバックエンドへ追加する。
- 進捗のload/set commandを追加する。
- プロジェクトを開いた際に共有進捗を読み込む。
- 旧 `AppState.fileProgress` の冪等移行を追加する。
- rename / single move / multi move / deleteへprogress更新を統合する。
- 互換期間中はローカルミラーを維持する。

完了条件: プロジェクトを別パスで開いても進捗が一致し、ファイル操作後も対応が崩れない。

### Phase 3: チェックポイントストアの導入

- checkpoint永続化DTOとpath検証を実装する。
- create/list/load/update metadata/deleteを実装する。
- 1件破損時に他を読み込めるwarning付き結果を実装する。
- 旧snapshotの冪等移行と互換ミラーを追加する。
- UIの比較／復元用には現在ルートで展開した既存ランタイム型を返す。
- 自動退避3件の上限をプロジェクトストア側で適用する。

完了条件: 空のアプリデータから別パスのプロジェクトを開き、履歴表示・比較・復元ができる。

### Phase 4: 外部変更と同期遅延への防御

- ウィンドウ再フォーカス時とチェックポイント画面表示時に再読込する。
- revision/hashの巻き戻り・分岐を検出する。
- 外部変更がある状態で未保存の進捗操作があれば、patch再適用またはユーザーへの再読込要求を行う。
- 同期中／読込専用／プレースホルダー未取得のエラーを、データ消失と誤認しない文言で表示する。

完了条件: 遅れて同期されたファイルを無言で古い状態へ上書きしない。

### Phase 5: 互換整理とドキュメント

- 互換期間終了後に `AppState.fileProgress` と `AppState.snapshots` の常用経路を削除する。
- 必要な読み込みmigrationだけを期限付きで残す。
- ユーザーマニュアルへ「端末を移る手順」「同期完了確認」「完全バックアップではないこと」を追加する。
- `.then` を同期除外しないよう明記する。

完了条件: 正本が1か所になり、通常操作でローカル旧データへ戻らない。

## 11. リリースとロールバック

- 進捗共有化とチェックポイント共有化は別コミット、可能なら別リリースに分ける。
- 最初のリリースでは旧AppStateデータを削除しない。
- 新形式の書き込みに失敗した場合、旧形式へ黙ってフォールバックして成功扱いにしない。
- migration完了記録はプロジェクトファイルの再読込検証後にだけ書く。
- 問題発生時はfeature flagでproject storeの読み込みを止め、旧ローカルデータを再表示できる期間を確保する。
- `.then/checkpoints` は新バージョン専用の追加ディレクトリなので、旧バージョンが無視しても原稿編集を妨げない。

## 12. 意図的に今回やらないこと

- 複数端末からの同時編集
- クラウドアカウント連携やThen独自同期サービス
- CRDT／自動三者マージ
- チェックポイントの画像、PDF、プラグインデータを含む完全バックアップ化
- チェックポイント本文の差分圧縮やcontent-addressed storage
- 開いているタブ、スクロール位置、テーマの共有
- macOS/Linux対応そのもの

これらを同時に導入すると、可搬化の成否と同期機構の成否を切り分けられなくなる。まずは「1台ずつ使う限り、フォルダを持っていけば執筆上の意味データが揃う」を完成させる。

## 13. 推奨実装順

最初の着手単位は Phase 0 と Phase 1 とする。その後、低リスクな進捗ラベルを先に実運用へ入れ、保存基盤と移行方式を検証してから、大容量で復元操作を伴うチェックポイントへ進む。

順序を入れ替えてチェックポイントから始めない。進捗ラベルで相対パス、atomic write、rename/move/delete追従、旧データ移行の共通部を先に固めることで、チェックポイント移行時の危険範囲を小さくできる。
