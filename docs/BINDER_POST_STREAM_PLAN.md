## 工程2: 仕組みの説明

### 言葉

| 言葉 | 意味 |
|---|---|
| 投稿 | 右のペインに書き流す短い記録。1件ずつ、書いた時刻と、書いたときに開いていた作品を持つ |
| 投稿ストリーム（流れ） | 投稿を新しい順に縦に並べた表示。モックの 1 |
| 受信箱 | まだ片付けていない投稿の集まり（意味は工程5で決める） |
| Idea スレッド | 今の Idea。題名の付いたスレッドの中に断片（短い文）と資料リンクが並ぶ |
| JSON Lines（JSONL） | 1行に1つの JSON を書くテキストの形式。行ごとに独立して読めるので、末尾に1行足すだけで記録を増やせる |
| 追記 | ファイルを書き直さず、末尾に足すこと |

### 1. データの形（今の Idea）

- スレッド: `id`・`kind`（`inbox`／`thread`）・`title`・`starred`・`createdAt`・`updatedAt`・`fragments`。インボックスは必ず1つ、先頭。
- 断片: `id`・`body`・`used`・`createdAt`・`updatedAt`・`originRef`（Canvas から来たときの元のカード）。
- スレッドの中の並びと資料リンクは、資料ボードのファイル（`referenceLayout.ideaThreads`）に別に持つ。

### 2. 利用者の操作と内部の処理（今の Idea）

| 操作 | 内部 |
|---|---|
| 入力欄に書いて Enter | `onCapture` → 追加先スレッドの末尾に断片を足す。App の `appState.snippets` が変わる |
| Ctrl+Alt+I | `QuickIdeaModal` を開き、同じ `captureFragment` を呼ぶ |
| 断片をドラッグして Canvas へ | 本文を文字列として渡し、Canvas がカード（コピー）を作る |
| Canvas の「Ideaへ送る」 | 選んだカードの文をスレッドへコピーし、`originRef` を付ける |
| 「すべて／スター」 | スレッド一覧の絞り込み |

### 3. 保存（今の Idea）

- 設定「Ideaの管理単位」が「作品ごと」（既定）なら、作品の `project.json` の `ideaThreads`。開いた作品が変わると読み直し、`appState.snippets` が変わるたびに書く（`App.tsx:3054`）。
- 「全作品で共有」なら、アプリのデータフォルダの `profileSnippets`。
- 書くときは `ideaThreads` を丸ごと差し替える。

### 4. ほかの機能との関係

- バインダーの投稿の段は「アイデア」1行で、押すと右のペイン「アイデア」を開く（1-4）。数はスレッドの数。
- Canvas の別ウィンドウへは、スレッドの一覧（送り先の選択肢）を `then-canvas-live-data` で届けている。
- ライブラリの中では、スレッド・断片・資料を別の作品やライブラリ直下へ送れる（`transfer`）。

### 5. 今の挙動の癖（直さないもの）

- バインダーの「アイデア」の数は、スレッドの数で、断片の数ではない（インボックスだけなら常に 1）。
- 作品を開いていない（ファイルを1本だけ開いた）ときも、Idea はアプリの状態に持って表示される。

## 工程5: 案

### 5-1. 方針

- 投稿は**新しい部品として作り**、今の Idea のコードを使わない（工程3）。`IdeaPane.tsx` は作り直さずに残し、2-4 で消す。計画書の「IdeaPane.tsx の作り直し」は、右のペイン「アイデア」の中身を新しい `PostStreamPane` に置き換えることとして行う。
- 投稿のファイルは Rust だけが読み書きする。画面は「この投稿をこう変える」という1件ごとの操作を送り、Rust がそのときのファイルの中身に当てて書く。画面が持っている古い一覧で、ファイルを丸ごと書き直すことはしない。

### 5-2. 保存形式（案）

**ファイル**: `<ライブラリ>/.then/posts.jsonl`。単独で開いた作品では `<作品>/.then/posts.jsonl`。

**1件の区切り**: 1行に1件の JSON（JSON Lines、UTF-8、改行は `\n`）。1行がその投稿の今の状態を表す。

```jsonl
{"v":1,"id":"p-mhz3k2a1-7f3c","at":"2026-11-14T10:42:05+09:00","work":{"id":"w-2b8e…","name":"潮待ち郵便局"},"body":"閉局の日に、町じゅうから返事が集まってくる。"}
{"v":1,"id":"p-mhz3m8q0-a91d","at":"2026-11-14T10:44:31+09:00","work":{"id":"w-2b8e…","name":"潮待ち郵便局"},"replyTo":"p-mhz3k2a1-7f3c","body":"返事を書くのは町の人。"}
{"v":1,"id":"p-mhz1x0b4-02ee","at":"2026-11-14T09:15:12+09:00","body":"汽笛は時刻の代わり。","edited":"2026-11-14T09:20:00+09:00","filed":true}
```

| 欄 | 必須 | 意味 |
|---|---|---|
| `v` | ○ | 形式の版。今は 1。知らない版の行は読み飛ばし、書き換えない |
| `id` | ○ | 投稿の ID。`p-<時刻の36進>-<乱数>`。時刻の順に並ぶ |
| `at` | ○ | 書いた時刻。時差つきの ISO 8601（ファイルを開いて人が読めるように） |
| `work` | — | 書いたときに開いていた作品。`id` は作品の固定の ID、`name` は書いたときのフォルダ名（作品が消えたり移ったりしても表示できるように）。ライブラリ直下やファイル単独のときは書かない |
| `body` | ○ | 本文。改行は JSON の `\n` |
| `replyTo` | — | 返信先の投稿の `id`。返信でつながった列がスレッドの代わりになる（モックの 1） |
| `edited` | — | 最後に本文を直した時刻 |
| `filed` | — | 受信箱から外したか（5-4） |
| `note` | — | 2-3 で使う。「ノートにする」で作ったノートの場所（作品の ID と `素材/` からのパス） |
| `from` | — | 2-4 で使う。移行元（例: `{"idea":"<作品のID>/<スレッドID>/<断片ID>"}`）。移行のやり直しで二重にしないため |

`note`・`from` は 2-1 では書かないが、読み込みで知らない欄を落とさないように、Rust は1行を「知っている欄＋そのほかの欄」として読み、書き直すときにそのほかの欄も残す。

**作品の ID**: `project.json` に `workId`（`w-` で始まる乱数）を足す。作品を開いたときに、なければ付ける。フォルダを改名しても、別の端末へフォルダごと移しても変わらない。作品フォルダを丸ごと複製すると同じ ID の作品が2つになるが、そのときは両方を「この作品」とみなす（実害は絞り込みが重なるだけ）。

**書き方**:

| 操作 | ファイルへの書き方 |
|---|---|
| 投稿する・返信する | 末尾に1行足す（追記）。ファイルの末尾が改行で終わっていなければ、先に改行を足す |
| 本文を直す・受信箱から外す／戻す・削除 | Rust が、いまのファイルを読み、その `id` の行だけを差し替え（削除は取り除き）、ほかの行は1文字も変えずに、`write_replacing` で丸ごと置き換える |

- 読めない行（壊れた行、知らない版の行）は、表示しないがファイルには残す。
- 同じ `id` の行が2つあったら（同期ツールの重ね書きなど）、後ろの行を使う。書き直すときに前の行は消さない。
- 削除は行を消す。削除の直後に「元に戻す」を出す（トースト）。押すと同じ行を元の位置に戻す。

### 5-3. 外部の変更と、同時に開いたとき（3.9・1-3a との関係）

- **追記は上書きしない**ので、外部での変更を消さない。
- **差し替えは、そのときのファイルに当てる**ので、ほかの投稿を外部で直していても、それは残る。消えうるのは「同じ投稿を、外部とアプリの両方で直した」ときだけ。そこで、本文を直す・削除の操作は、画面が見ていたその投稿の行のハッシュ（SHA-256）を付けて送る。Rust はいまの行と比べ、違えば書かずに知らせる。画面は読み直して、その投稿を外部の内容で出し直し、トーストで知らせる（直した文は入力欄に残す）。1-3a の「開いたときのハッシュと比べ、違えば上書きしない」を、ファイル全体でなく投稿1件の単位で行う形。1件が短いので、1-3a のような2択のダイアログは出さない。
- **読み直す時機**: 右のペイン「アイデア」を開いたとき、アプリに戻ったとき（ウィンドウの focus）、自分が書いたあと。ファイルの大きさと更新日時が前回と同じなら読まない。
- **同時に開いたとき**: Then は1つしか起動しない（`single_instance.rs`）。Canvas の別ウィンドウは 2-1 では投稿を読み書きしない。2台の端末で同期しているときは、追記が行の単位なので、同期ツールが衝突を作っても行は失われない（同期ツールが作る「競合コピー」のファイルは読まない。2-1 では扱わない）。
- 書き込みは `atomic_file` の鍵で1ファイル1本ずつにする（追記も同じ鍵を取る）。

### 5-4. 絞り込みの意味（案）

| 絞り込み | 出すもの |
|---|---|
| 受信箱 | まだ片付けていない投稿。片付けるのは、2-1 では「受信箱から外す」、2-3 では「ノートにする」も（`filed` か `note` があれば外れる）。どの作品で書いたかは問わない |
| すべて | ファイルにある投稿の全部 |

- 並びは新しい順。日の区切り（今日・昨日・日付）を入れる（モックの 1）。

### 5-6. 決めてほしいこと

1. **2-1 と 2-4 のあいだの扱い**（5-5）: A（勧め）／B／C。
2. **保存形式**（5-2）: ファイル名 `posts.jsonl`、1行1件の JSON Lines、新しい投稿は追記、直す・外す・削除はその行だけを差し替えて置き換える（勧め）。
   - ほかの案: (b) 直す・削除も「変更の行」を追記して、読むときに重ねる（ファイルを一度も書き直さない）。外部との衝突はさらに起きにくいが、消した投稿の文がファイルに残り続け、ファイルを開いて読んでも今の状態が分からない。(c) Markdown（`posts.md`、見出しに時刻と作品）。人が読みやすいが、ID や返信先を見出しに埋め込むことになり、外部で直されると読み違えやすい。
   - 勧める理由: 1行が今の状態なので、ファイルを開けば読める。消した文は残らない。差し替えはそのときのファイルに当て、同じ投稿の衝突だけをハッシュで止めるので、外部の変更は黙って消えない。
3. **絞り込みの既定**: 受信箱（勧め。モックと同じ）／この作品／すべて。前回選んだものは再起動しても戻す（勧め）か、毎回既定に戻すか。
4. **Ctrl+Alt+I の行き先**: 投稿にする（勧め。思いつきの入口を流れに揃える。追加先スレッドの選択はなくなる）／2-4 まで古い Idea のまま。
5. **Canvas の「Ideaへ送る」「Ideaで開く」**: 2-1 では古い Idea のまま（勧め。Canvas の側を変えずに済み、4-2 でカードが投稿を参照する形に作り直すため）／投稿へ送る。
6. **返信**: 2-1 で返信の操作も入れる（勧め。モックの 1 の「返信でつなげたものがスレッドになる」が投稿の流れの骨組みで、2-4 で古いスレッドを返信の列として移すときに、出し方がすでにあると確かめやすい）／形式（`replyTo`）だけ用意し、操作は後で。
7. **バインダーの「アイデア」1行の数**: 受信箱の投稿の数にする（勧め）／今のまま（スレッドの数）／数を出さない。
8. **単独で開いた作品を、あとでライブラリに入れたとき**: 作品の `.then/posts.jsonl` の投稿を、ライブラリの `posts.jsonl` に足し（同じ `id` は足さない）、作品の側は `posts.imported-<日時>.jsonl` に名前を変えて残す。作品を開いたときに行う（勧め）／2-4 の移行と一緒に行う（それまでは見えない）。

### 5-7. 2-3・2-4 で困らないか

- **2-3「ノートにする」**: 投稿の行に `note`（作品の ID と `素材/` からのパス）を足すだけで済む。ノートは「いま開いている作品」に作る（3.8）ので、ライブラリの投稿から別の作品のノートを指すことになるが、作品の ID を持つので、作品のフォルダを改名しても指し先は分かる。ノートの側に「元の投稿」（3-4）を持たせるときは、投稿の `id` を書けばよい。
- **2-4 の移行**（確認1で方向を決めた。下の工程6）: インボックスの断片は、その作品の `workId` と `name` を `work` に入れて受信箱の投稿として追記する。名前の付いたスレッドは投稿にせず、スレッド名をノートの名前、断片を段落にしたノートを、その作品の `素材/` に作る（なければ 1-6 と同じく「素材」を作る）。投稿の形式に題名やスレッドの欄は要らない。`createdAt`（ミリ秒）は `at` に直し、`from` に移行元を書いて、やり直しで二重にしない。`profileSnippets` の名前の付いたスレッドの置き場（ライブラリ直下など）と、資料リンクの扱いは、2-4・2-5 の確認1で決める。
